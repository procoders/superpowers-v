# Probe — do native enforcement points reach workflow-spawned agents? (2026-09-01)

**Verdict: YES, and the payload carries enough to attribute a call to a job.** This decides Feature E.

## Method

A log-only `PreToolUse` hook (matcher `Write|Edit`, never blocks, `exit 0`) was installed in the gitignored `.claude/settings.local.json`, then a two-agent workflow was run: one agent with `isolation: 'worktree'`, one without. The hook logged the raw stdin payload. Hook and markers removed afterwards; `git worktree list` shows no residue.

## Observed (verbatim from the probe log)

```
cwd=/Users/oleg/Dev/superpowers-v
  tool=Write file=…/scratchpad/PROBE_LOCAL_MARKER.txt session=e619cb38
  keys=agent_id,agent_type,cwd,effort,hook_event_name,permission_mode,
       prompt_id,session_id,tool_input,tool_name,tool_use_id,transcript_path

cwd=/Users/oleg/Dev/superpowers-v/.claude/worktrees/wf_e3ac4698-328-1
  tool=Write file=/Users/oleg/Dev/superpowers-v/.claude/worktrees/wf_e3ac4698-328-1/PROBE_WORKTREE_MARKER.txt
  keys=… (same)
```

## Findings

1. **`PreToolUse` fires for agents spawned by a workflow.** Both agents triggered it. This was the open question gating Feature E.
2. **The payload carries `agent_id` AND `agent_type`**, not merely `session_id`. Attribution of a tool call to a specific concurrent worker is therefore possible without inferring it from the path.
3. **`cwd` is the agent's worktree**, and `tool_input.file_path` is absolute inside it. So even without `agent_id`, a worktree→job map would work.
4. **Workflow worktrees live at `.claude/worktrees/<runId>-<n>`**, under the main checkout's path namespace, with a per-worktree git dir (`.git/worktrees/<id>`) and a shared object store — a linked worktree, not a clone. Confirmed by the probe agent via `rev-parse --show-toplevel`, `--git-dir`, `--git-common-dir`.
5. Writes inside the worktree were **unblocked** with no permission prompt, so the hook is the control point, not an existing default deny.

## The hole this probe also exposed

The worktree agent **flagged an instruction conflict rather than silently obeying it**: a harness-injected reminder in tool output told it to prefer `cat`/`sed`/heredocs over the `Write` tool. It followed the task instead, and said so.

That is a finding about Feature E, not about the agent. **A `Write|Edit` matcher is trivially bypassed by writing through the shell.** Any lane enforcement built only on those two tool names is decorative: `sed -i`, a heredoc, `cp`, `git checkout`, or a build step will write wherever they like and never reach the matcher.

Feature E must therefore match `Bash` as well and inspect the command, and — because command inspection is a parsing problem with unbounded evasions — must **keep** the git-derived post-hoc verdict rather than replacing it. `bashCommandClamp` narrows what a spawned agent's shell may run at all and is the right partner mechanism.

## Consequence

Lane enforcement moves from **detection after the fact** to **prevention before the write**, for the tool-based write paths, with the git-derived check retained as the authority for everything else. That is a change of guarantee class, and it is the strongest single result in the 3.0 investigation.
