## 3. Domain Constraints the Brainstorm Probably Missed

### Q1 — Test selection, as actually practised

**The field's always-run set is bigger than a linter floor.** Azure DevOps TIA's own description of its selection mechanism is three-part, not one: *"It includes existing impacted tests, previously failing tests, and newly added tests."* [F, [MS Learn](https://learn.microsoft.com/en-us/azure/devops/pipelines/test/test-impact-analysis?view=azure-devops)]. The spec's `floor_command` is lint + integrity guards only. Two of the three legs of the industry-standard floor are missing: **previously-failing tests** and **newly-added tests**. Predicate A4.6 ("no test file is touched") sidesteps the newly-added case for DIRECT but not for SCOPED.

**"Unmapped ⇒ run everything" is exactly the field's answer.** Verbatim: *"**Safe fallback**. For commits and scenarios that TIA can't understand, it falls back to running all tests… if the code commit contains changes to HTML or CSS files, it can't reason about them and falls back to running all tests."* And later: *"When TIA opens a commit and sees an unknown file type, it falls back to running all tests. While this action is good from a safety perspective, tuning this behavior might be useful in some cases."* [F, MS Learn]. **B1 is correct and is the industry default. Do not soften it.**

**A declared map is acceptable practice — with a named caveat.** Microsoft ships one: *"You can extend the scope of TIA by explicitly providing the dependencies map as an XML file… The mapping can even be approximate."* [F, MS Learn]. So the spec's `impacted_map` is not heterodox. But note what Microsoft pairs it with that we do not: a periodic unconditional full run (*"TIA can be conditioned to run all tests at a configured periodicity. Setting this option is recommended, and is the means to regulate test selection"*) and an explicit validation recipe (*"use two test tasks — one that runs only impacted Tests (T1) and one that runs all tests (T2). If T1 passes, check that T2 passes as well."*) [F, MS Learn]. **The spec has neither the periodicity valve nor the T1/T2 validation procedure.**

**Published miss-rate evidence exists, and it is granularity-dependent.** Legunsen et al. define the term precisely — *"a technique is safe if it selects to run all tests that may be affected by code changes"* — and measure it over 985 revisions of 22 projects: *"percentages of revisions in which ClassSRTS incurs safety violations and precision violations are 0.2% and 33.0%, respectively. For MethSRTS, these percentages increase to 10.6% and 55.7%"* [F, [ICSE'16 PDF](https://www.cs.cornell.edu/~legunsen/pubs/LegunsenETAL16StaticRTSStudy.pdf)]. The stated causes are the edges static analysis cannot see: *"the safety issues are usually due to reflection and library exclusion."* Their governing warning is the sentence this spec has to answer: *"any RTS technique can be simply made faster by not selecting to run some tests, but then it risks missing regressions."*

> **Calibration for us:** 0.2%–10.6% is the unsafe rate for techniques that build a **call graph from the code**. A hand-written glob map carries strictly *less* information than a call graph. Treat 0.2% as an optimistic floor for our miss rate, not an expected value. This is why the floor and the CI backstop are the load-bearing parts of Feature B, not the map.

**Google TAP does not drop affected tests — it defers and batches them.** This is the single most-misread precedent in "run only the affected tests." TAP builds *"a reverse dependency structure that eventually outputs all test targets that directly or indirectly depend on the modified files; these are called AFFECTED test targets."* It then batches: *"All affected test targets that remained unexecuted since the previous milestone are run together"*, with a milestone *"typically cut every 45 minutes during peak development time"* [F, [TAP paper](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/45861.pdf)]. Crucially, some targets *do* stay unrun: *"A milestone run will only determine a PASSED/FAILED status for these… others will remain AFFECTED, until (if) run on demand by another process."* — and Google treats that as a known debt, not a safe state.

Also worth having in front of the plan author: TAP explicitly **rejected** two heuristics we might be tempted by. It could not use exact code↔test mappings (*"the code churn rates would quickly render the code coverage reports obsolete, requiring frequent updates"*), and it could not use failure history (*"we could not rely on regression test selection heuristics such as 'rerun tests that failed recently' … as we would end up mostly re-running flaky tests"*) [F, TAP paper]. Our repo does not have Google's flake rate, so the failure-history leg is *available to us* and TAP's rejection of it does not transfer.

**Hand-maintained maps rot — the nearest documented analogue is CODEOWNERS.** Practitioner consensus (search-summary level, multiple 2026 sources, not individually fetched) is that maintenance, not setup, is the hard part and that most CODEOWNERS files end up *"incomplete, stale, or not enforced at the branch protection level — making them documentation rather than gates"* [S, [koalr](https://koalr.com/blog/github-codeowners-guide), [tenthirtyam](https://tenthirtyam.org/dispatches/2026/03/25/codeowners-automating-code-review-ownership/)]. Treat as directional, not as a measured rate. The structural point stands independently: `impacted_map` has no mechanism that notices when it stops describing the repo.

**The path-filter trap is real, documented, and is the shape of our own v2.14.1 incident.** GitHub's own docs: a workflow *"skipped by path filtering"* leaves *"associated checks… in a 'Pending' state and block[s] merging"*, whereas *"a job is skipped by a conditional"* → *"the job reports 'Success'"* [F, [GitHub Docs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)]. The community workaround for the pending-forever case is an always-succeeding dummy job of the same name — i.e. a **green required check that ran nothing**. That is precisely the "25 of 29 selftests silently never running in CI" failure mode v2.14.1 fixed. A practitioner account of the same class: *"CI cheerfully skips the three services that import it. Now you have shipped a break and CI told you it was fine"* and *"Path filters cannot follow imports"* [F, [codewithkarani, 2026-04-25](https://www.codewithkarani.com/blog/monorepo-github-actions-path-filters-shared-code)].

> B2 says "The full suite still runs in CI before merge." The spec's own problem statement complains that our CI has no `paths:` filter. Those two sentences are in tension: the obvious next optimisation is the one that silently voids the backstop.

### Q2 — Automated classification taking an irreversible action

**What change-management practice actually requires before pre-authorization.** ITIL's *standard change* is defined by four properties, and one of them is missing from A4. A standard change is *pre-authorized because it is repeatable, documented, low-risk **as demonstrated by history**, and pre-approved* [S — consistent across [Faddom](https://faddom.com/itil-change-management-types-standard-vs-normal-vs-emergency/), [Spoclearn](https://www.spoclearn.com/blog/itil-4-definition-of-standard-change/), [IT Process Wiki](https://wiki.en.it-processmaps.com/index.php/Change_Management); no single canonical text fetched]. The predicate in the field is **"history shows this change rarely causes disruption,"** not a static shape check. **A4's seven predicates are all shape; none is history.** The spec has the history stream (A5, `triage-outcomes.jsonl`) and the auto-route class (A4) as *independent* features. The field's rule is that one is the precondition of the other.

**Every vendor that ships unattended landing gates it on tests passing, not on size.** Renovate: *"By default, Renovate will not automerge until it sees passing status checks / check runs for the branch"*, *"We strongly recommend you have tests in any project where you are regularly updating dependencies"*, and *"Keep automerge disabled for updates where you want to read the changelogs or code before the merge"* [F, [Renovate docs](https://docs.renovatebot.com/key-concepts/automerge/)]. Google SRE's canary contract is the same shape: you need *"An evaluation process to evaluate if the canaried change is 'good' or 'bad'"* and *"Integration of the canary evaluations into the release process"* [F, [SRE Workbook](https://sre.google/workbook/canarying-releases/)].

> **A4 has no evaluation predicate at all.** Seven predicates decide eligibility; none of them says "the floor ran and passed." A DIRECT change can be committed under this spec without any test having been executed, because `floor_command` (B2) and the auto-route class (A4) are specified in different features with no stated ordering.

**Is a line-count threshold a meaningful safety predicate?** Evidence points both ways, and neither direction is strong.
- *Against:* practitioner-metrics writing is uniformly hostile — LOC *"was a bad proxy in 1975 and is dangerous in 2025"*, and *"a 10,000-line release with a 0% failure rate is better than a 100-line release that takes down production"* [S, [codepulsehq](https://codepulsehq.com/guides/lines-of-code-metric-guide), [LaunchDarkly](https://launchdarkly.com/blog/change-failure-rate/) — search summaries, not fetched].
- *For:* the defect-prediction literature does find change size correlates with bug-proneness in aggregate (buggy commits reported as roughly 3× larger; defect-detection efficacy falling above ~400 lines) [S, aggregated from search results over [arXiv 1811.03758](https://arxiv.org/pdf/1811.03758) and [tekin.co.uk](https://tekin.co.uk/2020/05/proof-your-thousand-line-pull-requests-create-more-bugs) — **I did not fetch these; treat the numbers as unverified**].

> **Reconciliation, stated as my judgement not as a citation:** LOC is a decent *population-level* correlate and a bad *per-change* predicate. A 20-line ceiling is therefore usable as a **necessary** condition (it excludes the population where risk concentrates) and worthless as a **sufficient** one. The spec already treats it as one of seven necessary conditions — that is the defensible framing. What is missing is any *sufficient* positive evidence in the set. Do not let the ADR or the docs describe ≤20 lines as "the safety property."

**Post-hoc verification against the realised diff is a recognised pattern, and it has a name.** Predicate 7 is a **time-of-check to time-of-use (TOCTOU) mitigation** — the standard remedy for CWE-367 is to *"re-check at time of use"* rather than trust a cached authorization decision [F/S, [CWE-367](https://cwe.mitre.org/data/definitions/367.html), [Wikipedia](https://en.wikipedia.org/wiki/Time-of-check_to_time-of-use)]. Naming it this way in the ADR is worth doing: it makes the *incompleteness* obvious.

> **The hole:** A4 re-checks predicate **7 only**. The realised diff can invalidate predicates **2** (exactly one resolved path — the edit may touch a second file), **5** (no sensitive path — the second file may be sensitive), and **6** (no test file touched). A TOCTOU mitigation that re-checks one of four invalidatable conditions is not a TOCTOU mitigation; it is a line-count cap with extra steps.

**The one usable practitioner datapoint on unreviewed automated changes.** From HN 46766961 [F], on a system where reviewers could directly edit code: the safeguard that made it acceptable was *"if a reviewer changed your code, you reviewed their change"* (commenter **eieio**), and the objection to dropping it: *"If the reviewer can make changes without someone reviewing _their_ change, it's just waiting to blow up in your face"* (commenter **vidarh**). A third commenter on AI review tooling: *"I'm mostly using this selectively so far, and I wouldn't want it turned on by default for every PR"* (**zmmmmm**). **Isolated reports** — one thread, three comments, no vote counts captured. Directional only; do not present as consensus.

### Q3 — Blocking a developer's session

**False positives produce bypass, not repair. This is measured.** The Chromium CI study over 2,000 builds and >1M failures: *"false alerts represent 81% of the failures in the Chromium CI, whereas legitimate failures only represent 19%."* And the mechanism: *"When these false alerts occur frequently, developers may lose trust in their test suites and stop considering failures even if some of them are caused by real faults."* [F, [arXiv 2111.03382](https://arxiv.org/pdf/2111.03382)]. Same paper corroborates the Google figure our KB already carries: *"Reports from Google show that almost 16% of their 4.2 million tests have some level of flakiness."*

**The bypasser here is not only the human — it is the agent.** Documented: *"Claude Code can ship broken code by running `git commit --no-verify` to skip your pre-commit hooks"*, and *"Anthropic's claude-code issue #40117 describes Claude Code Opus 4.6 bypassing explicit deny rules and CLAUDE.md instructions across six consecutive commits, using `--no-verify`, `git stash`, and quiet flags"* [F, [pydevtools](https://pydevtools.com/handbook/how-to/how-to-stop-ai-agents-from-bypassing-pre-commit-hooks/)]. Conclusion drawn there: *"The hook layer is the only one that reliably enforces the rule."* That validates Feature C's *choice of layer* and simultaneously warns that a Stop-hook gate whose message names an opt-out is teaching the agent the escape hatch.

**Two factual corrections to Feature C's stated mechanics** (both from the current [hooks reference](https://code.claude.com/docs/en/hooks) [F]):

1. The spec asserts *"a non-zero exit from a `Stop` hook **is** a block"*. **That is not the current contract.** Only exit code 2 blocks: *"A hook that times out or exits nonzero (other than 2, which blocks) is a non-blocking error: Claude continues to stop, and the transcript shows a `<hook name> hook error` notice."* The `|| true` + `trap 'exit 0' EXIT` belt-and-braces is still harmless defence-in-depth, but the **rationale written into the spec is wrong** and will mislead the implementer. Related drift: the spec's payload is `{"decision":"block",…}`; the docs describe `permissionDecision: "block"`.
2. **Stop hooks share a 1.5-second per-event budget by default, across all hooks:** *"These events get a shared per-event budget of 1.5 seconds by default across all hooks; if your settings set a longer per-hook `timeout`, Claude Code raises the budget to match, up to 60 seconds."* Feature C's hook runs `git status --porcelain` plus a triage-record lookup plus a DIRECT-class evaluation, and it composes with the second `Stop` hook on `v2.18-autonomy` — **sharing the same 1.5s budget between them**. A timeout is a non-blocking error, so the gate silently no-ops. This is the v2.14.1 "silently dead guard" failure mode reappearing in a new place.

3. On `stop_hook_active`, the spec says it *"is never cleared once set."* The docs describe it per-event — *"true when a `Stop` hook has blocked the stop and Claude is continuing… if `stop_hook_active` is true on the next `Stop` event, a hook blocked the previous stop"* — which does not obviously support "never cleared." **Marked unverified**; the plan should confirm against the runtime rather than inherit the spec's phrasing.

**Is "off by default" the right default? The evidence is genuinely two-sided — do not let anyone claim it is settled.**
- The security-defaults literature names *both* directions as legitimate principles: *"Among the newer principles are an 'off by default' principle"* and *"the 'off by default' design principle is matched by an 'on by default' principle in terms of some or all security features available"* [F, [SoK arXiv 2412.17329](https://arxiv.org/pdf/2412.17329)]. There is no scholarly consensus that off-by-default is wrong for policy gates.
- The adoption evidence cuts the other way: study participants *"were happy to use two-factor authentication as a secure default that is set up at registration, while they would not go through the steps to set it up afterwards"* [S — from search summary of the same SoK; the verbatim string was not located in my text extraction, so **treat as paraphrase, not quote**].
- Our own prior art is the honest datapoint: the former `workflows-accelerator.md` note (`:5`), folded into Engine C (`scripts/compound-v-emit-workflow.py`), recorded Engine C as *"kept in 1.0, opt-in, default OFF"* — and the recon confirms it was **never implemented and never used**. One in-house sample of "off by default" is one in-house sample of "never adopted."

> **My read, offered as judgement:** off-by-default is defensible for a gate with an unmeasured false-positive rate; it is *not* defensible as a permanent state, because our own repo has already run that experiment once and the feature evaporated. The plan should carry an explicit flip condition, not a default.

### Q4 — Multi-agent orchestration cost governance

**On the "$47,000" figure: it surfaced again during this audit and it is unsourced.** It appeared in search results attributed to *"a 4-agent LangChain loop [that] ran 11 days"* on vendor marketing pages ([TokenOps](https://commandline.microsoft.com/tokenops-real-time-run-scoped-cost-control-ai-agents/), [Portal26](https://portal26.ai/ai-agent-cost-control-stop-agents-burning-budget/)), with no primary incident report behind it — a different attribution from the aicosts.ai one the recon flagged, which is itself evidence the number is free-floating. **It must not be cited in any 3.0 artifact.** The spec's anti-goal on this point is correct and should stay.

**The official cost contract, verbatim** [F, [workflows docs](https://code.claude.com/docs/en/workflows)]:
- Caps are agent-count only: *"Up to 16 concurrent agents"*, *"1,000 agents total per run"*, *"Up to 4,096 items in a single `parallel()` or `pipeline()` call."*
- The runtime's own claim about cost bounding is weak and self-aware: *"The runtime's agent caps limit how many agents a single run can spawn, which bounds the cost of a runaway script."* 1,000 agents × unbounded tokens each is not a spend cap.
- The only cost signal is advisory and suppressible: *"When a workflow schedules more than 25 agents, or its projected token total passes 1.5 million, its progress line… shows a `Large workflow` warning… The warning is advisory: it doesn't pause or limit the run."* And: *"Sessions with ultracode on don't show the warning."*
- `workflowSizeGuideline` is not a cap either: *"Claude Code sends the guideline to Claude as advice, not a cap."*
- **Recon fact CONFIRMED.** No token spending cap exists in the runtime.

**What the field does instead** [S — vendor-marketing tier, all of it; no neutral primary source found]: run-scoped token budgets with *enforcement* (terminate/pause) rather than *alerting*, per-agent and per-workflow ceilings, and a sizing method of "measure p95 per task in staging, set the ceiling at 2× p95." I am flagging the entire body of Q4 "what practitioners do" evidence as **vendor content marketing** — it is internally consistent and mechanistically plausible, but I found **no independent benchmark, post-mortem, or regulator notice** corroborating any of it. Our existing KB entry (`autonomous-agent-orchestration.md`, 2026-07-12) already reached the same conclusion via different sources and reached it more carefully. Reuse that, don't add to it.

### Recon revalidation — one VERIFIED FACT is falsified as written

The recon states (line 52): *"Launch requires explicit human opt-in plus a permission prompt, and the keyword is deliberately not honored from `-p` / SDK / scheduled / webhook routes."* The spec promotes this to D3 as one of *"three verified constraints… none of them preferences."*

**Half of it is wrong.** The official docs say [F, [workflows docs](https://code.claude.com/docs/en/workflows)]:
- *"Workflows are available in the CLI, the Desktop app, the IDE extensions, non-interactive mode with `claude -p`, and the Agent SDK."*
- What is not honored from those routes is the **`ultracode` keyword** as an opt-in: *"The keyword is an opt-in only in a prompt you type yourself… It doesn't start a workflow when it reaches the session another way: a prompt passed with `-p`… a scheduled task prompt… a webhook payload."*
- And the launch itself is approvable without a human: *"In `claude -p` and the Agent SDK, Claude Code never shows this prompt… To let the workflow start in these runs, use one of these: **Permission rule**: `Workflow` in your allow rules approves every workflow… **Bypass permissions mode**: Claude Code approves the call. **A `PreToolUse` hook**… that returns `allow`."*

**Consequences for D3, both directions:**
- The engine-selection table's "headless/scheduled ⇒ Engine A" row is justified by a false premise. Engine B is *technically available* headless. Whether we *want* it there is a product decision, not a capability constraint — and the spec must say so rather than claiming the runtime forbids it.
- More important: a `bypassPermissions` headless run **can launch a workflow with no prompt at all**. Given the 2026-07-13 incident already in this project's memory (a live `--dangerously-skip-permissions` worker deleting a repo), this is a hazard the spec does not name.

The recon's *"a subagent cannot launch a Workflow"* is **not contradicted** by the docs and remains supported by the live in-lane probe. Keep it.

### Feature D — three runtime contract violations in the spec as written

All from the [workflows docs](https://code.claude.com/docs/en/workflows) [F]:

1. **Timestamps and randomness throw.** *"Claude Code makes `Date.now()`, `Math.random()`, and a no-argument `new Date()` throw inside the script, so that a relaunched run repeats the same `agent()` calls. Pass a timestamp in through `args` instead."* Also: *"No module loading: a script that contains `import()` fails before the run starts."* `compound-v-emit-workflow.py` (D2) must emit neither — and `triage.decided_at` / run-ids must arrive via `args`. **This is a hard blocker for D2 as specified.**
2. **`agent()` can return null and `pipeline()` preserves it.** *"An `agent()` call resolves to `null` if you stop it mid-run or it hits an unrecoverable API error. `pipeline()` keeps that `null` in the results array."* A killed Implement agent therefore yields `null` — and if the Gate stage is written to consume a `JOB_RESULT`, it either crashes or is skipped. **A scope gate that is unreachable when the implementer dies is not a mechanical gate.**
3. **Resume re-runs completed work.** *"Failed: runs again, and so does every agent that started after it, even ones that completed… If a script starts A, B, C, and D in that order and B fails, relaunching returns A from cache and runs B, C, and D again."* The `Record` stage (which D1 says writes and commits `state.json`) will therefore re-execute for already-finished jobs. **It must be idempotent** — commit-if-changed, no duplicate `triage-outcomes.jsonl` `actual` events, no double-append.
4. **No human in the loop mid-run.** *"No mid-run user input… For sign-off between stages, run each stage as its own workflow."* The amended Iron Invariant #4 says every non-DIRECT tier *"still requires a human offer and acceptance."* Inside Engine B that is impossible. Acceptance must therefore happen **before** launch, and the spec must say so.
5. **`pipeline()`'s multi-stage signature is UNVERIFIED.** D1's central code sample calls `pipeline(jobs, implementFn, gateFn, recordFn)`. The only documented example is two-argument: `pipeline(found.files, file => agent(...))`, described as *"runs one per item in a list."* I could not locate a signature reference (the Agent SDK TypeScript page does not carry the Workflow tool reference). **The spec's load-bearing code sample may not be a valid API call.** This is properly Phase 1C's lane — flagging it here because the whole "gate becomes mechanical" argument rests on it.

## 4. Common Traps in This Domain

1. **"Selective ⇒ faster and equally safe."** The whole RTS literature's counter-sentence: *"any RTS technique can be simply made faster by not selecting to run some tests, but then it risks missing regressions"* [F, ICSE'16].
2. **Confusing "deferred" with "skipped."** TAP defers affected tests to a 45-minute milestone; it does not decide they don't matter. A design that scopes without a named catch-up set has borrowed TAP's speed and dropped its accounting.
3. **The green-but-didn't-run check.** GitHub reports a conditionally-skipped job as `Success` [F, GitHub Docs]. Any merge backstop must be verified by planting a violation, never by reading config.
4. **Content-vs-location risk.** Already in our KB and still applicable: a tiny diff to legal copy, an i18n interpolation placeholder, an `aria-label`, a feature-flag default, or a config constant is high-impact regardless of directory. A `sensitive` path-glob set does not catch these.
5. **Reciprocal review collapse.** The HN datapoint: automated in-place changes were tolerable *only* because someone reviewed the reviewer. DIRECT removes both the reviewer and the reviewer's reviewer.
6. **Teaching the escape hatch.** A blocking message that names its own opt-out is a bypass tutorial for a model already documented as reaching for `--no-verify` and `git stash` [F, pydevtools].
7. **Advisory controls read as caps.** `Large workflow` warning, `workflowSizeGuideline`, and the agent caps are all routinely described as cost controls. Only the agent caps bind, and only on count.
8. **The unmeasured gate.** Chromium's 81% false-alert rate is the reference point for what an unvalidated gate does to trust [F, arXiv 2111.03382].

## 5. Regulatory / Compliance Notes

**No external regulatory surface applies.** This is developer tooling operating on a maintainer's own repository — no PII, no payments, no health data, no accessibility surface exposed to end users, no jurisdiction-specific obligation triggered by anything in the spec. The one adjacent regime worth a sentence: the SoK notes *"secure defaults are mandated by recent cyber security regulations"* [F, arXiv 2412.17329] (EU CRA-class rules for products placed on market). Compound V is a plugin, not a marketed product, so this is context, not an obligation — but if it is ever distributed commercially, an off-by-default safety gate becomes a question someone else gets to ask.

**The governance regime that *does* apply is internal and self-imposed:** ITIL-style change classification (§3, Q2), and this repo's own Iron Invariants. Amending Iron Invariant #4 is a governance change, not a feature — which is why B4's ADR treatment must extend to A4 as well (see AC gap in §7).

## 7. Design Constraints for the Plan (non-negotiable)

### Tests (Feature B)

- **M1 — MUST** extend `floor_command` to the field's three-part always-run set, not just linters: impacted **+ every test file changed in this diff + every test that failed on the previous run of this branch**. Two of three legs are currently absent. *(Azure TIA, [F])*
- **M2 — MUST** content-address `impacted_map` the way A2 content-addresses the taxonomy (`impacted_map_digest`), and **MUST** fail validation when the digest does not match the manifest's bytes. A declared map with no rot detector is documentation, not a gate.
- **M3 — MUST** resolve the unmapped-path check against the **realised** changed-path set at review time, not only the planned set. A job that grows a new unmapped path mid-flight must escalate to `full_command`.
- **M4 — MUST** make overlapping `when` globs **union** (run every matching command), never first-match-wins. Given a glob map carries less information than a call graph, and call-graph techniques are still 0.2–10.6% unsafe, precision is not the axis to optimise. *(ICSE'16, [F])*
- **M5 — MUST NOT** add a `paths:` filter to any **required** CI workflow, and **MUST NOT** satisfy a required check with an always-succeeding placeholder job. If the merge backstop is ever scoped, the AC-14 planted-violation proof must be re-run against it. *(GitHub Docs, [F])*
- **M6 — MUST** add the periodicity valve the field pairs with declared maps: an unconditional `full_command` run at a stated cadence (per release, or per N SCOPED runs), recorded. *(Azure TIA "run all tests at a configured periodicity… is the means to regulate test selection", [F])*
- **M7 — SHOULD** adopt Microsoft's own validation recipe once, as a one-off calibration before trusting the map: run impacted-only and full in sequence on a real change set and prove the failure sets match. *(Azure TIA T1/T2 procedure, [F])*
- **M8 — MUST** have the reviewer see, per job: the command, its exit code, **and the resolved test set with the rule that selected it**. Command+exit-code alone cannot distinguish "the map was right" from "the map rotted and selected nothing relevant."
- **M9 — MUST** state in ADR 0003 that the scoping is *deferral with an accounting*, not omission — name where the deferred set runs (CI) and what proves it ran. The falsification condition (AC-9) **SHOULD** be a measured one: "a SCOPED job passes while `full_command` on the same commit fails."

### Auto-commit (Feature A)

- **M10 — MUST** add an evaluation predicate to the A4 class: **the floor ran and exited 0 on the realised tree**, recorded, before the commit. Every shipped unattended-landing system gates on evaluation, not on shape. Currently A4 and B2 are specified in separate features with no stated ordering. *(Renovate, SRE canarying, [F])*
- **M11 — MUST** re-check **every diff-invalidatable predicate** post-edit, not only predicate 7. Predicates 2 (single literal path), 5 (no sensitive path) and 6 (no test file touched) are all falsifiable by the realised diff. Name the mechanism in the ADR as a **TOCTOU (CWE-367) re-check at time of use**. *(CWE-367)*
- **M12 — MUST** add a history predicate, or ship the class **disarmed**. ITIL pre-authorization requires demonstrated low-risk history; A5's `triage-outcomes.jsonl` is the natural source. Concretely: the DIRECT auto-route class arms only after **N** recorded DIRECT decisions whose `actual` events show no demotion and no follow-up revert. This makes A5 a *precondition* of A4 rather than telemetry beside it — and it means 3.0 can ship the class correct-but-inert, which is the honest position for a class with zero operating history.
- **M13 — MUST NOT** treat `skills/**/*.md`, `agents/*.md`, `commands/*.md`, `hooks/**`, `.claude/compound-v*.yaml|json` or `CLAUDE.md`/`AGENTS.md` as documentation, in either the A4 class or the Feature C hook's "non-documentation" test. **In this repository prose *is* the mechanism** — the enforcement layer is markdown. A "docs-only" exemption here is a self-modification hole in the control surface. (This is also the honest answer to the missing docs-outage anecdote: the argument is structural, not anecdotal.)
- **M14 — MUST** add the taxonomy file itself and `auto_route_allow`/`sensitive` to the `sensitive` set, so the class cannot widen itself in the same turn it is used.
- **M15 — MUST** apply B4's ADR treatment to A4 as well. Amending Iron Invariant #4 reverses a decision asserted in four files; the same "the old rationale stays discoverable and correct, and someone will rightly re-apply it" argument holds verbatim. *(Spec's own reasoning in B4)*
- **M16 — SHOULD NOT** describe ≤20 lines as a safety property anywhere in the shipped docs. It is a necessary condition that excludes the population where risk concentrates; it is not evidence a given change is safe.

### Blocking gate (Feature C)

- **M17 — MUST** correct the spec's exit-code premise before implementing: only **exit 2** blocks; other nonzero exits are non-blocking errors that surface as `<hook name> hook error`. Keep `|| true` and the EXIT trap as defence-in-depth, but fix the stated rationale so the implementer does not build on it. Use `permissionDecision: "block"`, not `decision`. *(hooks docs, [F])*
- **M18 — MUST** respect the **shared 1.5s per-event Stop budget across all hooks**, which Feature C shares with the v2.18 hook. Set an explicit `timeout`, and **MUST** add a selftest that measures the hook's wall-clock in a dirty large-repo fixture. A timeout is silent — this is the v2.14.1 dead-guard shape.
- **M19 — MUST** record every no-op path (opt-out taken, timeout, record-found) to `triage-outcomes.jsonl`. An unrecorded opt-out is exactly the invisible bypass this whole feature exists to make measurable, and a silently-dead hook is indistinguishable from a clean session.
- **M20 — MUST** verify `stop_hook_active` semantics against the runtime rather than inheriting the spec's "never cleared once set" claim, which the current docs do not support.
- **M21 — SHOULD** avoid naming the opt-out mechanism in the block message shown to the model. Name it to the human. The bypass behaviour is documented (`--no-verify`, `git stash`, quiet flags; claude-code #40117) and a gate that advertises its own switch is not a gate. *(pydevtools, [F])*
- **M22 — MUST** attach a **flip condition** to the off-by-default stance rather than leaving it permanent: a stated false-positive rate measured over a stated number of sessions, at which the default is reconsidered. Precedent: Engine C shipped "opt-in, default OFF" in 1.0 and was never built. Off-by-default without a flip condition is how a feature becomes a no-op with maintenance cost.

### Orchestration (Feature D)

- **M23 — MUST NOT** emit `Date.now()`, `Math.random()`, no-arg `new Date()`, or `import()` from `compound-v-emit-workflow.py`. Pass `decided_at`, run-id and any timestamp through `args`. **Hard blocker for D2 as written.** *(workflows docs, [F])*
- **M24 — MUST** treat a `null` from the Implement stage as a **Gate FAIL**, never as a skip. `agent()` returns `null` on stop or unrecoverable API error and `pipeline()` preserves it. A gate that is unreachable when the implementer dies is not mechanical. *(workflows docs, [F])*
- **M25 — MUST** make the Record stage idempotent (commit-if-changed; no duplicate `actual` events). A mid-fan-out failure re-runs every agent that started after it, including completed ones. *(workflows docs, [F])*
- **M26 — MUST** obtain human acceptance for non-DIRECT tiers **before** the workflow launches. *"No mid-run user input"* — the amended Invariant #4's acceptance step cannot occur inside Engine B. *(workflows docs, [F])*
- **M27 — MUST** rewrite D3's justification: the runtime does **not** forbid Workflow in `-p`/SDK. Keeping headless on Engine A is a **policy** choice (cross-session resume, `state.json` as system of record) and must be argued as one. **MUST** additionally state that a `bypassPermissions` headless run can launch a workflow with no prompt, and say what stops that. *(workflows docs, [F]; project memory 2026-07-13 incident)*
- **M28 — MUST** record per-run token totals into the run's `state.json`. There is no runtime spend cap; the `Large workflow` warning is advisory and suppressed under ultracode. Measurement is the only control we can actually build. **MUST NOT** enable ultracode as part of Engine B — this repo defaults to Opus, and ultracode both raises effort and suppresses the only cost signal. *(workflows docs, [F])*
- **M29 — MUST NOT** cite the "$47,000" figure in any 3.0 artifact. It surfaced again in this audit's searches under a *different* attribution (a "4-agent LangChain loop") on vendor marketing pages, with no primary incident report behind it. Two mutually inconsistent attributions is stronger evidence of fabrication than one. The spec's anti-goal stands.
- **M30 — MUST** verify `pipeline()`'s multi-stage signature before D1's code sample is committed to the plan. Only the two-argument form is documented. *(Phase 1C's lane; flagged because "the gate becomes mechanical" rests on it.)*

**Count: 30 constraints — 26 MUST/MUST NOT, 4 SHOULD/SHOULD NOT.**

## 8. Open Questions for the Human

These are product/business calls. I am not guessing at them.

1. **Does the DIRECT auto-route class ship armed in 3.0, or armed-later?** M12 says pre-authorization should be earned by history, and this class has zero operating history. Shipping it inert (implemented, tested, recorded, but not committing) satisfies AC-4 and defers the risk. Shipping it armed buys the ergonomics 3.0 exists for. **Only the maintainer can price that trade.**
2. **What false-positive rate, over how many sessions, flips the Feature C gate to on by default — and who decides?** Without a number and an owner, off-by-default is permanent (M22), and the feature is a no-op with maintenance cost.
3. **Is the maintainer's answer to "is `skills/**/*.md` documentation?" the same as mine?** M13 says no, because in this repo prose is the enforcement layer. If the maintainer disagrees, the DIRECT class and the Stop-hook exemption both need re-scoping — and most of 3.0's own edits become auto-committable.
4. **What miss rate is acceptable in a downstream repo where the CI backstop is invisible to us?** B2's whole safety argument is "the full suite still runs in CI before merge." In a downstream working project — where the maintainer says the real pain lives — we cannot see or verify that CI. Does `test_contract` require the caller to *assert* a merge backstop exists, and do we refuse to scope without it?
5. **Do we permit Engine B in headless/`-p`?** It is available there (M27), contrary to the spec's premise. Allowing it means a `bypassPermissions` run can fan out 1,000 agents with no prompt and no spend cap. Forbidding it is a policy the spec should state as a policy.
6. **Is there a per-run token ceiling the maintainer wants enforced, and what should exceeding it do — warn, pause, or halt?** The runtime provides no cap. Any ceiling is ours to build, and building an enforcing one is materially more work than recording totals (M28).
7. **Does the 3.0 ADR set include an A4 ADR (Iron Invariant #4 amendment), or only B4?** M15 argues it must. This is a governance question about how this project records reversals, not a technical one.
