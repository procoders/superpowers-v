## Findings

Ordered by severity. Anchor is `file:line` in the PR-6 worktree unless stated otherwise.

### Blocking

**1. [CONFIRMED] `scripts/compound-v-pool-state.py:258-262` — the "never recompute a recorded assignment" guard is vacuous.**
The guard that's supposed to make `freeze_assignments` idempotent — skip a job that already has `assigned_backend` + `assigned_model` — was deleted (replaced with `if False: pass`) in a scratch copy. `--selftest` still reported **60 ok, 0 fail**. Behaviorally the deletion is real: re-freezing a job that was rerouted by `out_of_credits` to a fallback backend (`assignment_source: "fallback"`, outside the pool ring) either silently recomputes it back onto a pool member, or — if the config the caller passes doesn't carry a model for that member — errors out where the original quietly returns the untouched record. I reproduced this twice independently (once via a full-repo mirror with real config, once with a minimal fixture) with consistent results: the guard changes real behavior, and no test in the suite depends on it existing. Hits AC-8, AC-10 and AC-11 from the spec — the guarantee that a frozen/rerouted assignment survives a later freeze call.
*Why it matters*: this is the exact "53/53 while 4/8 classes were wrong" failure mode the handoff brief warned about, on the single most safety-critical invariant in the PR (a resumed job must never land on a different backend than the one whose worktree/diff it already has).

**2. [CONFIRMED] `scripts/compound-v-failure-policy.py:266` — the pool anti-retry-storm budget cap is untested; disabling it flips `halt` to infinite `reroute`.**
`if in_pool and total_retries >= max_total_retries:` was mutated to `if False and ...` in a scratch copy. `--selftest` still reported **35 ok, 0 fail**. I then ran the same `decide()` call through both the original and the mutant with an exhausted run budget (`total_retries=12, max_total_retries=12`) and a pool that still has a live member: original → `{"action":"halt", "reason":"run-level retry budget exhausted (12/12)…"}`; mutant → `{"action":"reroute", "reroute_to":"zai", "consume_total_retry":true}`. The nearest selftest fixture (`pool-terminal-halt-reset-and-budget`) also circuit-opens the fallback member, so both the real code and the mutant halt for a *different* reason, and the assertion never actually exercises this branch.
*Why it matters*: this is the specific failure the spec's own §5 warns about — an exhausted run-level budget must stop the run, not let a pool paper over it forever.

**3. [CONFIRMED] `scripts/compound-v-project-config.py:78` / `scripts/compound-v-pool-state.py:27` vs. `scripts/compound-v-resolve-model.py:144` — three-way backend-vocabulary mismatch means the shipped `zai` pool example is only safe by accident of PR ordering.**
`VALID_POOL_BACKENDS` (config reader) and `VALID_CONCRETE_BACKENDS` (pool-state) both include `"zai"`; the resolver's own `BACKENDS` tuple does not (`zai` ships on PR #5, still open). Manifest validation is fine — `validate-manifest.py` catches the mismatch through `resolve_pool()` and reports a clean `pool member … failed concrete model resolution: unknown backend 'zai'` — but `compound-v-pool-state.py`'s own `freeze_pool_members`, called directly by the dispatcher at run start (not through the manifest validator), raises the same `ValueError` with **no mention of zai, the adapter, or PR #5** whenever `ZAI_API_KEY` happens to be set. If `ZAI_API_KEY` is unset instead, the same shipped config (`commands/v-init.md:557-565`, the seeded Codex+zai pool) freezes cleanly but silently collapses to a codex-only pool — the exact "one provider absorbs the whole run" outcome the feature exists to prevent, with no warning anywhere. Neither branch has a selftest fixture: every zai fixture in `compound-v-pool-state.py` pins an explicit `model` and runs with `env={}`, so it always takes the tombstone path and never reaches either the resolver's raise or the "key set, no explicit model" combination.
*Why it matters*: this is a live landmine for exactly the operator this feature targets — anyone who follows `/v:init`'s own seeded default before PR #5 merges gets either an opaque crash or a silent single-provider pool, and CI cannot see it because no tracked manifest contains a `backend: pool` job (Finding 9).

### Important

**4. [CONFIRMED] `skills/compound-v/failure-policy.md:144` vs. `scripts/compound-v-failure-policy.py:266,317` — a single pool job can exhaust the whole run's retry budget, contradicting this repo's own documented invariant.**
The doc states plainly: "One job spinning on 429s must not exhaust the whole run." On `main`, a job's ceiling across all failure classes was 9 (3 retries × up to 3 relevant classes) against a default 12-retry budget. Under this PR, `rate_limited` retries are now budget-consuming (`:317`) and the per-class counter resets on every pool reroute (as spec §5 explicitly says it must), so one job on a 3-member pool can legitimately spend `3 retries × 3 members = 9` plus 3 reroutes = **12/12**, alone. Every other job in the run then halts at the guard from Finding 2 (when that guard is intact) with no path forward except hand-editing `state.json`. This is very likely an accepted, if under-documented, consequence of the spec's own instruction to decrement the run-level budget across reroutes — but the doc line it contradicts was not updated to say so.

**5. [CONFIRMED] `scripts/compound-v-pool-state.py:117` (vs. `scripts/compound-v-validate-manifest.py:1877`) — a case-variant `backend: Pool` passes manifest validation, then silently gets no assignment at all.**
The manifest validator lowercases the backend string before comparing; `pool-state.py`'s own ordinal/assignment logic does not. A manifest with `backend: Pool` validates clean, then `freeze` produces a job record with `status: pending` and no `assigned_backend`/`assigned_model`, and `pool-state validate` reports it as valid. Minor in isolation (a manifest author would have to typo the case), but it means the two gates the brief calls out — "worktree invariant" and "reviewer prohibition" — are both bypassable the same way, since they also key off the literal lowercase string.

**6. [CONFIRMED] `scripts/compound-v-pool-state.py` (freeze/select) — a pool that collapses to one available member freezes, assigns, and validates with zero warning.**
Reproduced directly: with one member's availability predicate false (e.g., no `codex` on `PATH`), the ring still freezes, every ordinal maps to the sole survivor, and `validate` reports no errors. Nothing in `parallel-dispatcher.md`, `v-status.md`, or `state-machine.md` mentions detecting or reporting this. The spec's stated claim — "a deterministic rotation that stops one provider absorbing an entire run" — is quietly false in exactly this state, at exit 0. Same underlying gap as Finding 3's second branch, but general (any single-member collapse, not just the zai case).

**7. [CONFIRMED] `scripts/compound-v-pool-state.py:317-319` and `commands/v-resume.md:32` — two documented recovery paths produce a state the PR's own validator rejects, with no way back in.**

**8. [CONFIRMED] `scripts/compound-v-liveness.py:224` — the hang detector doesn't recognize the PR's own new `dispatched` status.**

A job stalled between "assignment written" and "process actually running" — the exact window this PR introduces — is invisible to `STALE`/`DEAD` classification.

### Rejected (checked, no defect)

- **Determinism, the feature's central promise, holds under direct attack.** Same manifest/config → byte-identical assignments across 8 different `PYTHONHASHSEED` values. Weight expansion reproduces the spec's own AC-6 example exactly (`codex,codex,cursor,codex,codex,cursor` for weights 2:1). An unavailable member is skipped while the ring keeps its length and later positions keep their would-be occupants (AC-7, reproduced). A mid-run `pools` config edit changes nothing for the frozen run (AC-8, reproduced by diffing state before/after). `resolve()`/`resolve_pool()` carry no module-level mutable state (checked by grep for `random`/`time`/`datetime`/counters/`lru_cache`, and by deep-copying every module-level container before and after 23 mixed calls). The manifest-validator's independent re-implementation of the same rotation logic and `pool-state.py`'s real one agree on 2880 differential test cases (1-4 members × weights 1-3 × 24 indices).
- **All five `backend: pool` gates from the brief fire on real rejecting fixtures**, not just on reading the source: worktree-required (direct isolation rejected), reviewer prohibition (fires even when the deep/opus check would separately pass, using a deep-tier reviewer fixture built specifically to test this), `advisor_backend` scoping (rejected as an advisor value, accepted as `job.backend`), and — the one flagged as trickiest — the never-Haiku check genuinely runs on the *resolved* model: three independent haiku sources (explicit member override, per-stance config cell, legacy flat config shape) were each built as fixtures and each rejected with the same policy message. `FALLBACK` and the classifier's argparse both reject the literal string `"pool"` outright, and a corrupted `state.json` that puts `"pool"` inside a frozen ring is also rejected before it can reach either.
- **Existing (non-pool) failure-policy behavior is unchanged.** `rate_limited` still retries the same backend with cap 3; `out_of_credits` still reroutes to `FALLBACK[backend]` (== `claude`) for non-pool jobs; verified by reading the actual assertion content of the pre-existing selftest cases (not just their presence) and by direct CLI calls.
- **No reroute oscillation, and the exhaustion/fallback boundary is correct**: a job reroutes to the next viable member, falls back to the old chain only once the pool is exhausted, and every hop opens a breaker on the backend it leaves, so the ring drains monotonically rather than cycling. A single healthy member absorbing an unbounded stampede is real but is the spec's own declared non-goal (§6, no enforced concurrency gate).
- **Config fails closed as designed, at both the structural and the member level**, and the plan's specific two-tier rule — top-level malformation raises, member-level malformation warns-and-drops — is genuinely implemented on both sides, with the drops surfaced as validator `problems` (not silently absorbed).
- **Weight bounds (1-100) and the 256-slot ring cap are really enforced**, at three independent sites with matching constants, including the `bool`-is-an-`int` trap (`True`/`False` explicitly rejected, not coerced). The worst legal configuration (every stance/tier/backend at max weight) materializes at most 200 slots for any one tier — the per-backend dedup caps membership before the 256 limit is ever the binding constraint, so the memory-exhaustion path the spec worries about is structurally closed today (even though its *test coverage* is thin — see Minor findings).
- **No fabricated-metrics language anywhere in the diff.** The CI anti-ruflo regex was reproduced by hand against the full diff: 0 hits. Every "balanced"/percentage/savings-adjacent phrase found by manual sweep is either the pre-existing stance name, explicitly job-count-framed, or a sourced provider fact. `skills/compound-v/failure-policy.md` actually *removed* a pre-existing "est. cost ↑" line in favor of recorded-state-only language.
- **`backend_max_parallel` enforcement claims are hedged everywhere they appear** ("not a claim that a scheduler/semaphore gate exists," "prose-enforced… not a semaphore claim," "validation proves shape, not enforcement") — no site claims a gate that doesn't exist.
- **896 lines in a new file is not a convention violation.** This repo's `CLAUDE.md`/`CONVENTIONS.md` set no file-size limit, the linter config explicitly turns that check off, and `main` already ships several `scripts/*.py` between 1500 and 5500 lines. (The 500-line rule some readers may expect lives in the operator's personal global config, not this project's.)
- **The never-Haiku documentation is accurate** — `execution-manifest.md` states plainly that the gate lives in the validator against the resolved model, not in `resolve_pool()` itself, matching the code exactly.
- **The merge-order claim, read carefully, is more precise than the spec's own summary of it — but the underlying dependency is real.** Contrary to the spec's line 14 ("every shipped example needs zai"), **zero shipped manifest examples reference zai** — all 12 tracked manifests, run through `main`'s own validator, pass clean. The actual dependency lives one layer up, in the shipped `pools` **config** examples (Finding 3) — those do need PR #5, and the PR body correctly discloses this ("Do not merge this PR before #5… this PR does not claim it has merged," confirmed against the live PR body and a fresh `gh pr view 5` showing it still open). So: the dependency is real and currently unresolved, disclosure is honest, but the spec text pointing reviewers at "examples" sends them to the wrong layer, and (Finding 3/9) nothing tests the layer where it actually bites.

## Answering the brief's item 8 directly

PR #5 is not merged (`state: OPEN`, `mergedAt: null`, confirmed freshly). PR #6's body states this correctly as a merge prerequisite and does not claim otherwise. But the risk isn't at the manifest layer the spec points to — it's the config layer: the shipped `pools` example in `commands/v-init.md` names `zai`, and depending on whether `ZAI_API_KEY` happens to be set on the operator's machine, using that example before PR #5 merges either throws an opaque `unknown backend 'zai'` at run start (Finding 3) or silently runs every pool job through `codex` alone with no warning (Finding 3/6). Recommendation: don't merge on the strength of "no manifest needs zai" — the config example does, and it's untested either way.

## Merge verdict

**Not mergeable as-is.** The rotation core (determinism, the five gates, fail-closed config, weight bounds) is genuinely solid under direct execution — most of what the brief worried about turned out fine. But two selftest guards over Blocking-severity behavior are provably vacuous (Findings 1–2: reroute-idempotence and the run-level retry ceiling — the exact class of defect this repo has been burned by before), and the shipped zai pool example is unsafe either way it fails until PR #5 merges (Finding 3), with zero CI coverage of the pool path that would have caught any of the three (Finding 9).

**Single most serious surviving issue:** Finding 1 — `compound-v-pool-state.py`'s recorded-assignment guard is not just untested but demonstrably removable without moving a single one of 60 green checks, and it's the guard protecting the one invariant the spec calls load-bearing for resume: a job must never be silently reassigned to a different backend once one is recorded. That combination — Blocking-severity, silently vacuous, on the resume-safety invariant — is worse than any of the individually larger findings.

## What to fix before merge (recommended)

1. Findings 1–2 (add fixtures that actually kill the mutation used here, then confirm they do).
2. Finding 3 (either surface a clear "PR #5 not merged" message from `freeze_pool_members`, or add a selftest fixture for `ZAI_API_KEY` set + no explicit model, or both).
3. Finding 9 (add one pool-routed job to a CI-tracked manifest so the whole pool path in `validate-manifest.py` is exercised by CI, not just by hand-built fixtures).
4. Findings 5–8, 10 are all real behavior gaps reachable through documented operator steps; Finding 6's silent single-member collapse deserves at least a warning line given it directly negates the feature's stated purpose.
5. Minor findings are genuine but non-blocking; the doc-drift ones (state-machine.md's `deep` pool_tier, the failure-policy.md table rewrite) are cheap to fix and worth doing in the same pass since they'll otherwise mislead the next person who reads them as ground truth.
