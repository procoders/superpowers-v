## Verdict

**ISSUES.** Three of four feature acceptance criteria are met and the deliverable itself is good:
a Codex worker on a second backend wrote a correct, tested, shellcheck-clean helper in its own
worktree outside the repository, the gate measured that tree (r2's findings 78/79 are verifiably
closed), and exactly its lane merged. One sub-claim of the criterion this run exists to prove does
not hold, and the release notes assert it anyway.

1. **`ACCEPTANCE_GAP` / `CONSTRAINT_VIOLATION` — `results/sandbox-helper.json` carries
   `"session_id": ""`, not a UUID.** Criterion 2 and design §Decision 5 both require a UUID from the
   `--json` stream. The UUID exists and was captured — `logs/sandbox-helper.events.jsonl:1` holds
   `01a0660c-d369-7553-b57c-2c5276b35ae6` — it just never reaches the result. It appears **nowhere
   else in the run directory**; `grep -rl` over the whole run dir returns only the events log. Root
   cause, located and confirmed: the worker's own parser is fine (I re-ran
   `compound-v-run-codex-worker.sh:545–564`'s pipeline verbatim against this run's events log — it
   yields `01a0660c-d369-7553-b57c-2c5276b35ae6` and passes the UUID-shape gate), but
   `scripts/compound-v-emit-workflow.py:3504` builds the result from
   `state_job.get("session_id") or ""`, `state.json` has `"session_id": null` for
   `sandbox-helper`, and the generated `dispatch.workflow.js` **does not contain the string
   `session_id` at all** — nothing on Engine C reads the worker's `job_result.session_id` back into
   state. The consequence is not cosmetic: `session_id` is what `codex exec resume <uuid>` needs, so
   `/v:resume` cannot resume a codex job on Engine C today.
   → Wire the external worker's emitted `job_result.session_id` into `state.json` (and thus the
   result); re-run to prove criterion 2 whole. Do not fix by hand-editing the result file — that
   would be a fabricated receipt.

2. **`QUALITY` (accuracy) — `CHANGELOG.md:11` ships a claim this run does not support.** It says the
   release proves the multi-model contract *"(worktree outside the repository, **UUID session id**,
   the scope gate measuring the worker's own tree) end to end"*. Two of those three are demonstrated;
   the UUID session id is not, per finding 1. This is not a fabricated metric — there is no number —
   but it is an unmeasured claim in shipped release notes, which is the same failure mode one
   register down.
   → Either fix finding 1 first, or strike "UUID session id" from that sentence.

3. **`QUALITY` — `hooks/lane-guard.sh:1474–1485` denies read-only `git` commands.** The `git` branch
   treats every token after `--` as a write target regardless of subcommand, so
   `git show <sha> -- <path>`, `git log … -- <path>` and `git diff -- <path>` are all denied for any
   path outside the lane. Three live denials during this review, e.g.
   `git show d210e92 -- scripts/compound-v-sandbox-checkout.sh` →
   *"job 'spec-review' is not allowed to write 'scripts/compound-v-sandbox-checkout.sh'"*. A reviewer
   whose lane is one file cannot read the diff it is reviewing by the ordinary means; I worked around
   it via `jobs/*.patch` and whole-commit `git show`. Pre-existing, not from this diff — introduced
   in `7359af3` (v3.0 task-15) — but it lands squarely on the reviewer role and is worth closing.
   → Restrict the `--` path rule to the subcommands that actually write (`checkout`, `restore`,
   `rm`, `mv`, `clean`, `apply`); leave `show`/`log`/`diff`/`grep` alone.

4. **`QUALITY` (dispatch config) — the agent definition served to this job is stale against
   `agents/spec-reviewer.md` at HEAD, and the drift is on the §3.3 tier table.** The §3.3 table in
   this job's *runtime* prompt reads, for FULL: *"`full_command` — ran, exit 0"*, full stop. The file
   in the repository — unchanged by this run; Task B's patch adds only line 193 — reads at
   `agents/spec-reviewer.md:175` that FULL *"follows the derived-default rule, same as every other
   tier: a declared, non-empty `impacted_map` is honoured … plus `full_command` for each changed path
   matching no rule"*, and at `:178` that *"demanding `full_command` of a FULL job that has a
   declared `impacted_map` and no changed path outside it is a review error too."* Code wins over
   prose, and here the repo file is the code: both implement jobs correctly resolved `impacted` at
   `triage.tier: FULL`, exactly as `default_scope_for`
   (`skills/compound-v/execution-manifest.md:153`) and the gate receipt document — *"no `test_scope`
   declared, defaulted to 'impacted' … the repository has said which tests relate to which paths"*.
   **A reviewer trusting the stale runtime copy would have filed a false `BUILD_RED` against correct
   behaviour** — I nearly did, and only the repo file stopped it. No repo-side inconsistency exists;
   the defect is that the dispatched definition and the checked-in one disagree (the known
   installed-plugin-cache lag, now with teeth: it can invert a gate verdict).
   → Make the dispatched agent definition read from the checked-in file, or refresh the plugin cache
   before a run whose reviewer is gating on that table.

5. **`TEST_GAP` — `--taxonomy-from` has no test.** It is spec'd (design §Decision 1, plan Task A
   Step 2: *"copies one file over `.claude/compound-v-impact-taxonomy.yaml`"*) and implemented
   (`scripts/compound-v-sandbox-checkout.sh:54–58`, `:87–94`, `:115–119`), and
   `tests/test-sandbox-checkout.sh` never exercises it — the string does not appear in the file.
   Plan Step 1 does not enumerate it, so this is a gap in the plan as much as in the test; the flag
   still ships untested, and finding 6 is what an untested path produces.
   → Add one case: build with `--taxonomy-from <file>` and assert the sandbox's
   `.claude/compound-v-impact-taxonomy.yaml` is byte-identical to the supplied file.

6. **`QUALITY` — the `files:` count is off by one when `--taxonomy-from` replaces a tracked path.**
   `scripts/compound-v-sandbox-checkout.sh:118` does `files=$((files + 1))` unconditionally after the
   taxonomy copy, but `.claude/compound-v-impact-taxonomy.yaml` **is** tracked in this repository
   (`git ls-files .claude/`), so it was already counted at `:111`. `sandbox: … files: <n>` therefore
   overstates by exactly 1 on the ordinary `--taxonomy-from` invocation. Small, and the printed count
   is a real measurement, not an invented one — but it is a measurement that is wrong.
   → Only increment when the copy created a new path.

7. **`QUALITY` (dispatch config) — the review job's Bash clamp cannot run the command its own
   acceptance requires.** The `spec-review` job's acceptance asks the review to quote
   `codex --version`; the per-spawn `bashCommandClamp` for this job admits 55 command heads and
   `codex` is not among them (`"the span \"codex --version\" matches none of them"`). I obtained the
   version through the allowlisted `env` wrapper and am disclosing that rather than leaving it
   implicit.
