### ISSUE 1 — SPEC: the interpreter preference never asks whether an interpreter can run

Job acceptance criterion 1 asks for:

> *"prefers an interpreter that can `import yaml` (CV_PYTHON first, then the first of
> /usr/bin/python3, python3 **that imports yaml**, else the first found)"*

What shipped selects on executability alone
([`hooks/lane-guard.sh:245-251`](../../../hooks/lane-guard.sh)):

```bash
for _cv_cand in /usr/bin/python3 "$_cv_path_py"; do
  [ -n "$_cv_cand" ] || continue
  [ -x "$_cv_cand" ] || continue
  …
PY="${CV_PY_CANDIDATES%%:*}"
```

`/usr/bin/python3` is now the **unconditional first pick** on every machine, and the `import yaml`
question is never asked of it — the yaml preference was moved to `load_manifest_data`, which
delegates the *manifest read* to a candidate that has PyYAML. For reading a manifest, that is
equivalent and I verified it end to end. For **choosing the interpreter the whole payload runs
under**, it is not, and the deviation is what creates the hazard below.

The consequence is reproduced, on this machine, with the guard's own wrapper
([`hooks/lane-guard.sh:1260`](../../../hooks/lane-guard.sh)):

| Invocation | Result |
|---|---|
| an executable interpreter that does not work (`CV_PYTHON=/usr/bin/false`), out-of-lane `Write` | **no decision at all** — empty stdout, exit 0, and **not even a log line**, because the log is written by the payload that never ran |

So an executable-but-non-functional first candidate silently disarms the guard, with no trace: the
identical failure mode this commit was written to close, relocated from "the interpreter cannot read
the manifest" to "the interpreter cannot start". The population is different and I did **not**
reproduce it on a real machine — stated as inference, not evidence: on macOS without Xcode Command
Line Tools, `/usr/bin/python3` exists and satisfies `[ -x ]` while failing to execute, and a working
Homebrew `python3` sits on `PATH` behind it. Under the shipped order that machine gets the broken
one; under the criterion's order (`that imports yaml`) it would be skipped, because a probe that
fails to run also fails to import.

The lazy-resolution rationale at `hooks/lane-guard.sh:215-237` is well argued and I am not disputing
it — probing every candidate on every tool call would double the ambient cost for a question that
path never asks. But the argument only covers *probing candidates that are not being used*. It does
not cover the candidate actually selected, whose viability the wrapper already learns for free at
`:1260`: an empty `out` is exactly the signal, and iterating `CV_PY_CANDIDATES` there costs nothing
on the happy path.

→ Restore the property the criterion names — the chosen interpreter must be one that runs — without
paying for it on the unresolved path. Either re-derive the order the criterion specifies, or make the
existing empty-output branch at `:1260` fall through to the next candidate instead of to silence.

### ISSUE 3 — QUALITY: the interpreter under the hot hook changed, and the published cost was not re-measured

`AGENTS.md` publishes the lane guard's ambient cost as **the one thing to know before installing**
— 47 ms unresolved / 81 ms resolved, re-measured 2026-09-01, with a reproduce recipe — and it is
explicit that those numbers *supersede* two earlier published figures that re-measurement did not

call in every session: previously `command -v python3`, now `/usr/bin/python3` first.
[`CHANGELOG.md:55`](../../../CHANGELOG.md) carries the `~47 ms` figure forward and says
*"(No re-measurement was taken; this is a structural claim about which paths run what, not a new
number.)"*

The structural claim is **true** and I verified it: the unresolved path spawns no subprocess, and a
resolved read on a yaml-capable interpreter does the plain import. What it does not cover is that the
interpreter itself changed, from 3.14.7 to 3.9.6. Measured here, back to back, same load, 50
invocations of the unresolved path per row, twice:

| Row | run 1 real / user | run 2 real / user |
|---|---|---|
| `CV_PYTHON=/usr/bin/python3` — the new default pick | 6.50 s / 4.41 s | 8.71 s / 4.56 s |
| `CV_PYTHON=/opt/homebrew/bin/python3` — the old `PATH` pick | 5.70 s / 3.82 s | 5.81 s / 3.74 s |
| `CV_PYTHON` unset — what ships | 6.66 s / 4.44 s | 6.54 s / 4.31 s |

Wall clock on this box is noisy; **user CPU is not**, and it moves the same way both times: **+16 % to
+22 %** on the path an ordinary human session takes. Reported honestly: I could not reproduce 47 ms in
absolute terms for *any* row — every variant costs ~115–175 ms per invocation here — so this is a
finding about **direction and cause**, not a replacement figure, and the absolute discrepancy is
pre-existing and not this commit's to answer.

→ Either re-measure the two published paths and update `AGENTS.md` (the recipe is already in it), or
state in the CHANGELOG that the default interpreter changed and the published figure is now
un-re-measured. Carrying `~47 ms` forward as still describing a path whose interpreter you just
swapped is the shape `AGENTS.md` itself warns about two paragraphs earlier.
