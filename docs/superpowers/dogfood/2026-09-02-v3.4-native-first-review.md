### ISSUE 2 — CONSTRAINT_VIOLATION: the monkey-patch pre-flight amendment 2 retired was relocated, not retired

Spec, *Pre-flight amendments* §2 (a blocking 1A finding folded into the spec):
> `run_preeval()` gains a real `binding=None` parameter threaded to its `build_record` call; the
> `triage` subcommand uses it — **the T2 monkey-patch is retired**.

Shipped (`scripts/compound-v-preeval.py:1338-1346`):

```python
orig_build_record = build_record
def _bound_build_record(pre_eval_id, req, verdict, localization, *a, **kw): ...
globals()["build_record"] = _bound_build_record
try:
    res = run_preeval(request, repo=repo, t3_category=t3_category, ts=ts, **kwargs)
finally:
    globals()["build_record"] = orig_build_record
```

`run_preeval`'s signature at `:993` carries no `binding` parameter. The patch was moved out of
`commands/v-triage.md` prose and into the library — which is where it is now harder to notice, not gone.

**Failure scenario.** `orig_build_record = build_record` resolves the *module global at call time*, so the
construct is not re-entrant. Two `triage_request` calls in one interpreter (a batch caller, a future
`--selftest` that parallelises, any embedding of the engine) interleave like this: call 2 captures call 1's
patched closure as its "original", and whichever `finally` runs **last** wins. If call 2 finishes after
call 1, the module global is left pointing at call 1's closure permanently — every subsequent record in
that process is bound to call 1's `session_id` and inherits its `refused_box`. A record bound to the wrong
session claims Stop-gate coverage it does not have, which is the exact fail-open direction
`triage_request`'s own docstring (`:1308-1310`) says must never happen. It does not fire today because
both callers are single-shot processes — the amendment existed to keep it that way by construction.

→ Add `binding=None` to `run_preeval` and thread it to the `build_record` call; delete the `globals()`
assignment. Keep `refused_box` by returning the refusals from `run_preeval` rather than by closure.

### ISSUE 3 — SPEC_GAP: `--from-runs` never counts rework

source now contributing a constant 0, a backend that needed three attempts on every job scores exactly as
one that succeeded first time, and the routing input the release moved *to* is strictly weaker on this
axis than the legacy `task-outcomes.jsonl` it replaced. Guarding it is a one-line `glob` on
`results/attempts/`.

### ISSUE 4 — SPEC_GAP: the once-per-session marker was not retired

Spec WS2: *"The once-per-session marker is retired: the record itself is the marker (`_has_session_record`)."*
Shipped: both. `hooks/triage-prompt-nudge.sh:399-404` computes `marker="${store}/nudged-${key}"` and

re-scored on the next prompt; with the marker, that session is spent and only `/v:triage` can recover it.

header. Do not leave the two disagreeing.

### ISSUE 8 — the recorded `tests.scope` does not match what a FULL-tier run owes

The manifest's `triage.tier` is `FULL`, so every job owes `full_command` and the resolved scope is `full`.
Both results record `scope: "impacted"`. The cause is at `scripts/compound-v-emit-workflow.py:2620`:

```python
scope = "impacted" if isinstance(rows, list) and rows else "full"
```

The label is derived purely from *whether any `impacted_map` rule matched*, and is blind to the manifest
tier. **The substance is fine** — `full_command` is in both `tests.command` strings and both exited 0 —
so this is a record defect, not a coverage gap. It matters because `tests.scope` is exactly the field a
reviewer is told to check against the tier: a future FULL run that genuinely ran only the impacted set
would produce a byte-identical `scope` value, and this gate would have no way to tell the two apart.

→ Resolve `scope` from the tier when the tier demands `full`, or record both (`scope` and
`tier_owed`).
