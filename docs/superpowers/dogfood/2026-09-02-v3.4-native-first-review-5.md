### ISSUE 1 — INTEGRATION: the lane guard fails open on **every** write in this run, because the interpreter it picks cannot read the manifest

The fourth pass's item 1 turns on one fact: the guard loads the matcher on every tool call, so a
forged `.pyc` executes there. The fix is correct and I verified it. But driving the **live** hook
against this run's own lane map, with synthetic stdin for an out-of-lane `Write` to `README.md`:

```json
{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext":
 "Compound V lane-guard FAILED OPEN: job spec-review-5 resolved, but its lane could not be read
  (job 'spec-review-5' not in …/2026-09-02-v3.4-native-first-r8/manifest.yaml).
  This write was NOT checked against the job's write_allowed."}}
```

The job **is** in that manifest. The cause is the interpreter:

1. [`lane-guard.sh:191-195`](../../../hooks/lane-guard.sh) picks `command -v python3` — on this machine
   `/opt/homebrew/bin/python3`, **3.14.7** (the same interpreter whose `cpython-314` cache the third
   pass found, and the one the forged-pyc demonstration runs on).
2. That interpreter has **no PyYAML**. [`compound-v-validate-manifest.py:138-144`](../../../scripts/compound-v-validate-manifest.py)
   catches every exception from `import yaml` / `safe_load` and falls back to `_mini_yaml` **silently**.
3. `_mini_yaml` on this manifest returns top-level keys `['feature', 'run_id']` and `jobs: []`. So
   [`lane-guard.sh:553-573`](../../../hooks/lane-guard.sh) raises `job … not in <manifest>` and the guard
   fails open — by contract, loudly in `additionalContext`, and with no enforcement.

Minimal reproduction of the trigger: a top-level scalar that PyYAML's dumper wrapped across two lines.
`feature: 'plain but⏎  folded'` → the fallback returns `jobs: 0` and drops every key after it;
the same manifest with a one-line `feature` → `jobs: 1`. This manifest's `feature` is 106 characters,
so `safe_dump` folded it.

**Blast radius, measured, not estimated.** Over all 45 run manifests in
`docs/superpowers/execution/*/manifest.yaml`, the fallback parser reads the jobs list of 39 and
returns **zero jobs for 6** — `…-native-first-r3`, `r4`, `r5`, `r6`, `r7` and `r8`. Every run of this
feature since r3, this one included, has had a lane guard that enforced nothing on this machine.

**The mechanism is fine; only the manifest read is broken.** Forcing the interpreter that has PyYAML:

| Invocation | Verdict |
|---|---|
| default `python3` (3.14.7, no PyYAML), out-of-lane `README.md` | **FAILED OPEN** |
| `CV_PYTHON=/usr/bin/python3` (3.9.6, PyYAML 6.0.1), same write | **`permissionDecision: "deny"`** |
| `CV_PYTHON=/usr/bin/python3` **plus a forged `.pyc` beside the matcher** | **`permissionDecision: "deny"`** — item 1's fix works |
| `CV_PYTHON=/usr/bin/python3`, in-lane write | silent allow, correct |

**Why this is a finding of this pass and not only of the environment.** The commit added
`tests/test-lane-guard.sh:580-646` to prove the guard denies with a forged pyc beside it. That test
passes — 197/197 — because its sandbox manifest (`tests/test-lane-guard.sh:68-75`) is four short lines
the fallback parser handles. So the new test asserts the guard denies, in a repository where the guard
does not deny for any real run, and nothing in the suite would notice. That is a test that certifies a
control it is not exercising, in the same commit whose argument is that the control matters.

Bounding it honestly: the root cause predates `defb2cd` and lies outside `gate-strict`'s lane; the
guard is defence in depth and the git-derived authority is unaffected (it runs under
`sys.executable`, and both selftest and my probes confirm it BLOCKS correctly). The fourth pass's
mitigation claim — *"`Write`/`Edit` to that path is still denied by the lane guard"* — is what is
false here.

→ Three cheap closures, in order: make `load_yaml`'s fallback **fail loudly** rather than silently
return a truncated document (or have `write_allowed_for` refuse a parse that yields zero jobs, so the
guard's open-notice names the real cause); teach the guard to prefer an interpreter that can
`import yaml`; and add a lane-guard case whose sandbox manifest carries a folded top-level scalar, so
the suite can see this class at all.
