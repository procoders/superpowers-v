# Dogfood — four Engine C runs, 2026-09-02

Four runs, three of which found something. The two that found real defects found
them in ways no selftest could have.

## Run 1 — the derived test scope

`docs/superpowers/execution/2026-09-02-df1-test-scope/`

**It failed before it started.** Resolving the job's test contract by hand, ahead of
the dispatch, produced `scope: impacted` — and then `full_command` anyway, because
twelve changed paths matched no `when` glob and the "unmapped ⇒ unknown blast radius
⇒ run everything" rule fired. All twelve were `.claude/worktrees/**` and
`__pycache__/*.pyc`: gitignored leftovers from earlier runs.

The cause: test selection took its changed set from `compound-v-scope-check.py`'s
`changed_files`, which unions tracked edits, untracked files **and gitignored ones**
— deliberately, because a worker writing `.env` or into `dist/` must be caught, and
dropping ignored paths there was a real exploit fixed in 2.8. The same union is wrong
as an input to test selection. One function, two questions — the defect `isolation`
had in 3.0.4, in a different place.

In any repository with ordinary untracked churn, the scoping shipped in 3.1.0 would
have been defeated on arrival.

The first fix was itself broken: `Popen` without `universal_newlines` hands
`communicate()` a `str` on a bytes pipe, raises `TypeError`, and the `except` returns
`None` — indistinguishable from "nothing was ignored". Caught because the path count
did not move: 13 before, 13 after, 4 once fixed.

**After the fix, live:** `scope: impacted`, `selected_count: 2` — the floor plus the
scoped command, not `WOULD-RUN-EVERYTHING`.

## Run 2 — three tiers and a dependent wave

`docs/superpowers/execution/2026-09-02-df2-frontier/`

Wave 1 routed `frontier`→Fable, `deep`→Opus, `standard`→Sonnet, all three from the
tier alone. **The first time `frontier` reached a live agent.** All three merged as
one commit.

Wave 2's dependent job then came back `blocked`, and the wave refused integration as
`forged`. It had done its work correctly. The gate blocked it for three files:

```
jobs/<id>.baseline
jobs/<id>.test-contract.json
preexisting/<id>.txt
```

All three written by `register-lane` — **our own machinery, on the job's behalf,
before it started**. In `direct` mode the run directory sits inside the tree the gate
measures, and the pre-existing snapshot is taken *first* precisely so it precedes the
work, which means it cannot contain the two files written after it.

`forged` is the authority's strongest verdict. It sends whoever reads it hunting a
forgery that never happened.

**Why nothing caught it earlier.** 3.0.4's two-wave dogfood could not: there the
dependent job wrote nothing, so its changed set was empty and the no-work check
answered first. A worktree job never sees it — its run directory is outside its
worktree. The only direct-mode job in the pipeline is exactly where it hid.

The fix appends those paths to the snapshot the gate already subtracts. Not an
exemption of `<run_dir>/**`: a worker writing into some *other* job's run directory
is still a violation.

## Run 3 — a deliberate out-of-lane write

`docs/superpowers/execution/2026-09-02-df3-scope-violation/`

The failure path, end-to-end, for the first time on Engine C. One job was told —
explicitly, in its own task body — to write one file inside its lane and one outside
it.

```
changed   : df3-declared.md, df3-undeclared.md
allowed   : df3-declared.md
violations: df3-undeclared.md
verdict   : blocked
```

The wave refused integration (`{"pass": 1, "blocked": 1}`), **nothing merged, nothing
was committed**, and the run halted. The tree was left untouched.

**Observed and worth stating:** the clean neighbour did not merge either. A wave
integrates atomically or not at all. That is the design — a partition that produced
one out-of-lane write has not earned a partial merge — but it is a real property, not
an accident, and anyone reading a halted wave should know the good work is still
sitting in its worktree rather than lost.

## Run 4 — the direct-mode shape, after the fix

`docs/superpowers/execution/2026-09-02-df2b-direct-bookkeeping/`

The narrowest possible reproduction of run 2's defect: one job, `isolation: direct`,
one write inside its lane. Result recorded in the run directory.

## What these four say about the method

Two defects, both in seams: between the scope gate and test selection, and between
`register-lane` and the gate. Each component was correct on its own terms and passed
its own selftests. Neither defect was reachable from inside one component's tests,
and one of them was only reachable by a job that *both* ran in direct mode *and*
actually wrote something — a combination that had never occurred in a dogfood before.
