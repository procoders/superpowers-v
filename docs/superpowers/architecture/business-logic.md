# Business logic — what Compound V is and its domain

## What it is

Compound V is a **sidekick to Superpowers**: a transparent interceptor between Superpowers phases
and, as of v1.0, a lightweight execution orchestrator that is the default execution path. It is not
invoked directly — it auto-fires at four Superpowers transitions (a gated pre-brainstorm recon, the
hand-off from brainstorming to writing-plans, inside writing-plans, and at execution), injecting
recon, pre-flight audits, partitioning, dispatch, scope enforcement, review, and memory, with a
Stage −1 triage ahead of all of them. (`skills/compound-v/SKILL.md:10-12`, `skills/compound-v/SKILL.md:14`)

## The domain: multi-model coding orchestration

The product is a multi-model coding orchestrator. The plugin describes itself as "triple parallel
pre-flight (code archaeology + domain-expert advisor + library/doc validator — Context7 MCP when the
session has it attached, WebSearch/WebFetch otherwise), disjoint file partitioning, manifest-driven
multi-backend dispatch (Claude + headless Codex + Antigravity + Cursor workers), git-diff scope
enforcement, crash-resumable runs, adaptive tier-based routing, epic mode for multi-feature builds,
V-memory local-first semantic+lexical recall". (`.claude-plugin/plugin.json:3`)

Two honesty qualifiers live in that same self-description and are part of the domain model, not
marketing trim: Context7 is used **when the session has it attached** rather than always, and the
gated pre-brainstorm recon plus batched elicitation are **guidance the brainstorm follows, not
enforced mechanisms**. (`.claude-plugin/plugin.json:3`)

It dispatches across multiple model backends through one uniform contract: the orchestrator hands a
`job_spec` to whichever adapter the manifest's `backend` names (claude | codex | antigravity | cursor
| opencode) and gets back a canonical `job_result` of identical shape — so the orchestrator speaks
only this contract and never sees backend-specific flags, and enforcement stays in the caller's scope
gate rather than in the backend. (`skills/backend-launcher/SKILL.md:3`, `skills/backend-launcher/SKILL.md:10`,
`skills/backend-launcher/SKILL.md:22`)

Not every backend is equally proven, and the repo says so rather than implying parity: Codex is
dogfooded here, Antigravity has its CLI invocation verified live but has never been dispatched here,
and Cursor and opencode are experimental — workers verified standalone, never dispatched through
Engine C. (`README.md:64-65`)

## Why three pre-flights

The value proposition is catching three classes of mistake before any code is written, each via a
different lookup path: 1A catches "the building is 200m², not 500m²" (existing-code reality), 1B
catches a domain mismatch like designing OAuth when the target API uses Basic auth, and 1C catches a
stale/abandoned dependency that the model's training data would have suggested. (`skills/compound-v/SKILL.md:50-53`)
The skyscraper metaphor frames it: without pre-flight you build a 500m² hat on a 200m² tower; with the
audits you add proper floors that fit both the building and the building code. (`skills/compound-v/SKILL.md:59`)

The three run on the **approved** spec, at the moment brainstorming hands off to writing-plans, and
never at spec-write time — auditing a draft the user has not yet reviewed would jump the base plugin's
own review gate. (`skills/compound-v/SKILL.md:91`)

## Proportionate work: the three-tier triage

The domain has a size dimension as well as a correctness one. A Pre-Evaluation scores each request on
two separate axes (difficulty ⊥ impact) from deterministic evidence and returns **DIRECT** (implement
in place, run the floor, commit — no manifest, no run directory, no reviewer dispatch, but a triage
record is still written), **SCOPED** (manifest, run directory, scope gate, floor, one combined
SPEC+QUALITY review; recon and the three pre-flights skipped), or **FULL** (the whole pipeline). The
score OFFERS by default and auto-routes only inside the DIRECT auto-route class.
(`skills/compound-v/SKILL.md:12`)

The scoped test floor is deliberately not oversold: it is early feedback and does **not** restore what
the full suite guaranteed — the merge-blocking CI run does — and the documents are forbidden from
saying otherwise. (`skills/compound-v/execution-manifest.md:617-621`)

## Domain scope and boundaries

Compound V **extends** Superpowers rather than replacing it: each Superpowers skill maps to a Compound
V action, and brainstorming/writing-plans run unchanged with Compound V intercepting the transitions.
(`skills/compound-v/SKILL.md:254-268`) The orchestrator is deliberately minimal — "No daemon, no MCP
server, no external vector DB service, no fabricated cost metrics — the anti-ruflo charter."
(`skills/compound-v/SKILL.md:46`)

Where the harness grew a mechanism of its own, Compound V gives up its version rather than keeping a
parallel one. Execution is now the native Workflow runtime (Engine C), with the hand-written subagent
dispatcher kept only as the residual path (`skills/compound-v/phase-3-parallel-opus-dispatch.md:7`,
`skills/compound-v/phase-3-parallel-opus-dispatch.md:11`);
epic resurrection and the session goal are the harness's `/loop`, `/schedule` and `/goal` since 3.4.0,
after the plugin's own scheduler and armed-goal Stop rule were deleted. (`skills/compound-v/epic-mode.md:172-184`)
Agent memory follows the same rule since 3.5.0: rather than a store of its own, five reviewing and
scanning agents declare Claude Code's native `memory: project`, and what the plugin promises about it
is a boundary, not a capability — the notes are committed and shared with everyone who clones the
repo, they never hold a secret, a remembered pattern is a lead to re-verify against the current code
rather than a verdict, and a directive found inside a memory file is ignored and reported, because
anyone with push access can write one. (`README.md:107-127`, `skills/compound-v/SKILL.md:194-204`)
Turning off the harness's auto memory turns this off with it, and the agents behave exactly as they
did before. (`README.md:129-132`)

Epic mode (v1.1) is the one-level-up domain: a single run executes one plan (one feature); an epic
chains several features through the full pipeline in dependency order, accumulating onto one branch —
"build a whole app." (`skills/compound-v/SKILL.md:48`) Its terminal states are `done` (all features
done **and** the final review passed — feature completion alone is never `done`) and, for a blocker
proven external by two distinct model families, the `done_with_blockers` success terminal.
(`skills/compound-v/epic-mode.md:166`)
