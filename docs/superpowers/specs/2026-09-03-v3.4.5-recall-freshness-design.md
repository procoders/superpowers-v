# v3.4.5 — recall that is fresh by construction (stage 5a: is V-memory recall real?) — design

**Date:** 2026-09-03 · **Stage:** 5a of the post-3.4.0 verification program · **Status:** approved by the orchestrator under the standing directive (fix per cycle, no over-engineering)

## What the probe found

- Every reviewer in the 2026-09-03 epic ran Step 0 faithfully (`search --intent review`, then `recall-check`) and every one of them recalled against an index **110–118 files behind the repository**. The engine printed the staleness itself; the reviewers wrote "treat the empty result as *nothing indexed on this*". Nothing in the pipeline refreshes the index: `refresh` is called only by `/v:memory-refresh`, `/v:init` and `/v:adr`. Recall is real, but it is recall of whatever was indexed the last time a human ran a command — on this repository that was before all 45 commits of stage 5.
- A full FTS5-only refresh of the 128 stale files took **0.38 s** (`refresh`, `--quick` refused it because 128 > 20). The dense lane was not involved (`memory.embeddings` is off in this project). Freshness costs nothing; the only reason it was missing is that nobody wired it.
- `search` warns on *new/removed* files but ignores *changed* ones (`doctor` counts all three).
- `recall-check` does work on real history: `scripts/**` → `tighten` (4 failed records), a single file → `none`. Whether the pipeline ever **applies** it is stage 5b's question, not this one.

## Decision

`search` refreshes the FTS5 lane inline whenever the index is behind, before it recalls. The dense lane is never touched by a search (embedding is the one slow, opt-in path; it stays a `/v:memory-refresh --with-embeddings` job). A search on a repository with no index builds one instead of telling the caller to run something first.

- `search [--no-refresh]` — the opt-out, for callers that want to read exactly what is indexed (the multi-developer "what did my teammate's pull add" case, and the selftest).
- Staleness for the decision = new ∪ changed ∪ removed (the `doctor` definition).
- If the refresh lock is held (another refresh running), search proceeds against the stale index and keeps today's warning; it never waits.
- One stderr line when it refreshed: `V-memory: refreshed N stale doc(s) before recall (FTS5 lane)`.
- Nothing else changes: routing untouched, the conservative-only bridge untouched, `/v:memory-refresh` keeps its job (rebuild, embeddings).

## Decisions forced by pre-flight 1A (docs/superpowers/archaeology/2026-09-03-v3-4-5-recall-freshness.md)

- **Staleness is computed BEFORE the search runs.** Today `cmd_search` computes `index_staleness` after `bm25_search`, so the warning was cosmetic — the reorder is the change, not a decoration.
- **The inline refresh never applies the `--quick` cap** (the motivating incident was 118 stale files) and **never consults `config_wants_embeddings()`** or passes an embedder. Side effect, stated: on a project with embeddings on and bootstrapped, `_persist_chunks` NULLs the vectors of a file the inline refresh re-chunks until the next `/v:memory-refresh --with-embeddings`; the dense lane degrades to FTS5 for that file, never breaks.
- **`cmd_refresh`'s embedding branch keeps its pre-refresh `changed` list** (or the `embedding IS NULL` union) — it must not re-hash after `refresh_fts5` has already rewritten `indexed_files.content_hash`, or it would never embed those files.
- **`refresh_fts5` stamps `chunker_version` itself**, so a project whose only refreshes are search-triggered still gets an identity match when it later bootstraps.
- **Lock held ⇒ silent**: search proceeds stale with today's multi-dev warning; it never prints refresh's "already running — skipped" line.
- **Missing db + `--no-refresh`** keeps today's behaviour exactly: exit 1 with the actionable message. Only a plain search builds the index.
- **`index_staleness` returns `(new, changed, removed)`**; `cmd_search`, the selftest and `doctor` (whose duplicate computation is removed) move together.
- The refresh line goes to `sys.stderr.write` (stdout stays JSON-clean); the selftest calls `cmd_search` with a full args shim (`repo, query, top, intent, json, no_embed, no_refresh`) — it is the first direct call of `cmd_search` in the selftest.

## Files

- `scripts/compound-v-memory.py` — `cmd_search`: staleness → inline FTS5 refresh (shared helper extracted from `cmd_refresh`), `--no-refresh`; `index_staleness` returns changed too; selftest case: a doc added after the index was built is recalled by a plain `search` and NOT by `search --no-refresh` (which warns).

## Acceptance criteria

1. On a repository whose index is behind, `search "<words from a newly added doc>"` returns that doc without any other command having run, and prints the one refresh line on stderr; `search --no-refresh` returns nothing for it and prints the staleness warning.
2. `python3 scripts/compound-v-memory.py --selftest` green (new case included); every other `scripts/compound-v-*.py --selftest` and `tests/*.sh` stay green.
3. A search never embeds: with embeddings bootstrapped and `memory.embeddings` off, the inline refresh reports `(FTS5-only)`; with the project opting in, the search still refreshes FTS5 only and leaves vectors to `/v:memory-refresh`.
4. The three docs say what the engine does; no doc still tells the user to refresh before a search.
