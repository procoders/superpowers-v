# Compound V 3.0 — proportionate triage, scoped tests, native-Workflow orchestration

**Status:** design r7, revised after the three Phase-1 pre-flights, a partition-gate FAIL, a cross-model review that returned DO NOT BUILD AS SPECIFIED, and a hands-on study of the native runtime. Supersedes r1-r3 wholesale.

**Inputs:** [recon](../recon/2026-09-01-v3.0-triage-tests-orchestration.md) · [1A archaeology](../preflight/2026-09-01-v3.0-1a-archaeology.md) · [1B domain](../preflight/2026-09-01-v3.0-1b-domain.md) · [1C runtime contracts](../preflight/2026-09-01-v3.0-1c-docs.md)

## Problem

Three defects, confirmed against this repository, none of them the one we assumed.

**The sizing engine has no caller.** 7,883 lines of deterministic, model-free scoring across six scripts, and `grep -rln "compound-v-preeval" commands/ agents/ hooks/` returns nothing. `docs/superpowers/pre-eval/` has never existed in git history. No `state.json` carries `pre_eval_id`. The logic is sound; it is never consulted.

**Small work is not over-processed — it escapes entirely.** All 10 recorded runs served releases of ≥788 changed lines. All 10 releases under 200 lines ran with no manifest and no run directory. The measured failure is an unrecorded bypass, not excess ceremony.

**Nothing scopes tests, and every job ever scheduled ran on the backend whose scope gate is prose.** The manifest has no test field; `agents/spec-reviewer.md:138` demands the whole suite unconditionally. All 73 jobs declared across the historical run manifests carry `backend: claude` — the one backend where the scope gate is prose the dispatcher must remember to type. **What that number is:** a count of jobs *as declared in manifests* — no `state.json` in this repo records a backend at all, and only 6 of 12 run dirs have one. It supports "no non-`claude` backend was ever scheduled", not "73 jobs each escaped the gate".

**Evidence limit, stated plainly.** The maintainer's "~20,000 tests for a one-word change" was not reproduced by any lane: no downstream repository, CI config or recorded measurement in this repo exhibits it. **Feature B's defaults are therefore chosen on principle, not on measurement.** They must be re-derived against a real instance before anyone claims a measured improvement.

## Goals

1. A three-tier triage decision that is impossible to skip on the dispatch path and recorded everywhere else.
2. Tests proportionate to the change, bought with a floor and with evaluation, not with an argument.
3. Dispatch executed by Claude Code's native Workflow runtime, with the git-derived verdict kept **outside** it.

**The position, corrected.** r2 claimed that making the scope gate a workflow stage "makes it mechanical". A cross-model review refuted that and it is withdrawn: the Gate stage is an `agent()` call, its schema proves the *shape* of the returned JSON and not that `compound-v-scope-check.py` ever ran, and the workflow script itself has no shell with which to check. The workflow gate is **defense in depth; the authority stays in the verification layer**, which re-derives from git outside the run.

What this makes Compound V is worth stating plainly, because it is a smaller and better thing than an orchestrator: **a triage, partition, compilation and verification layer over a runtime somebody else maintains.** Execution mechanics — queueing, the concurrency ceiling, stage ordering, per-agent worktrees, structured-output validation, progress, budget ceilings — are the native runtime's job and stop being ours. File lanes, the git-derived verdict, cross-session recovery, triage and the cross-vendor arbiter have no native equivalent and stay ours.

## Anti-goals

- No coverage instrumentation and no inferred file→test mapping. Mappings are declared, or the tier runs everything.
- No new scoring logic. Only invocation is missing.
- **The hand-rolled orchestration is deleted in 3.0, not deprecated beside a replacement.** Engine C becomes the dispatch path, and the prose that batched jobs, ordered `depends_on`, managed per-job worktrees and retried failures is removed rather than left as a second way to do the same thing. Two live paths for one job is how the audit trail ends up written by whichever one an agent happened to pick.

  Two things do **not** move, and neither is a matter of taste:

  1. **The git-derived integration authority.** A cross-model review established that a workflow Gate stage is an `agent()` call whose schema proves JSON shape, not that the scope check ran, and that the script has no shell of its own. Verification is not orchestration — it is the product — and it stays outside the run.
  2. **A minimal residual dispatch path for the one context that physically cannot launch a workflow.** Probed live under both the public name `Workflow` and the internal `RunWorkflow`: a **subagent** has neither. That is the whole of it — `/v:epic` is *not* on this list, because it invokes `/v:dispatch` as a command executed by the top-level agent, so once dispatch stops delegating to the `parallel-dispatcher` subagent the epic runs on Engine C like everything else. A compatibility shim for a runtime limitation, not a parallel product.
- No auto-arming of any scheduler. The permission-bypass flag is never emitted.
- The unattributed "$47,000" native-workflow cost figure is never cited.

## Scope change: v2.18 is absorbed

Feature C as specified in r1 **already exists** on the unmerged `v2.18-autonomy` branch: `_enforcement_rule` in `hooks/epic-goal-stop.sh` already implements source-change detection, run-record exemption, an `enforcement.*` config key defaulting OFF, a once-per-session marker, `|| true` registration and an unconditional exit-0 EXIT trap.

## Feature A — Triage that cannot be skipped

### A1. A third tier

`compound-v-preeval.py` gains `DECISION_SCOPED`. The band matrix stops collapsing 8 of 9 cells:

| | impact low | impact medium | impact high |
|---|---|---|---|
| **difficulty low** | DIRECT | SCOPED | FULL |
| **difficulty medium** | SCOPED | SCOPED | FULL |
| **difficulty high** | FULL | FULL | FULL |

Unknown bands stay fail-closed to FULL. `DIRECT` additionally keeps the existing Layer-B predicates.

**A low/low change that fails a Layer-B predicate demotes ONE tier, to SCOPED — not to FULL.** r7 left this unspecified and the implementer had to decide it; the reasoning is recorded here because it is a behaviour change from pre-3.0, which returned FULL. The matrix owns the tier and Layer B gates only the DIRECT cell, so demoting to FULL would be a rule living outside the matrix and would re-collapse exactly the cells §A1 exists to un-collapse — low/medium and medium/low are already SCOPED, and a low/low that merely spans two files is not more dangerous than either.

**The kill-switch is absolute.** `fast_path: "off"` forces FULL for SCOPED as well as for DIRECT, explicitly rather than by fall-through: an operator who set that switch asked for the full pipeline, not for a cheaper one they had never heard of.

**The decision string is `SCOPED_PIPELINE`, and the manifest tier token is `SCOPED`.** Consumers read `DECISION_SCOPED` and `DECISION_TO_TIER` from the engine rather than re-spelling either — a duplicated wire vocabulary is how the two halves drift apart.

**The matrix is computed inside the engine, never post-hoc from the verdict dict.** Override #4 (`compound-v-preeval.py:424`) returns genuine `low`/`low` bands alongside `override_fired=4`; a post-hoc reader would grant DIRECT — and with it auto-route — to a record whose own audit trail says a hard override fired. **Any fired override forces FULL.**

Tier meanings end to end:

- **DIRECT** — implement in place, run the floor, commit on the current branch. No manifest, no run directory, no worktree, no PR, and **no reviewer dispatch**.
  A triage record is still written and committed.

  **This does not exempt an unattended landing from `full_command`**, and r7 read as though it did. The two statements sit in different layers: there is no *reviewer agent* at DIRECT, but the auto-route class still has to clear a bar before it commits, and that bar is enforced **mechanically by predicates 7 and 8**, not by a review. §B4's DIRECT row therefore governs the reviews that do happen at DIRECT — an escalated or human-requested one — while the unattended bar lives in the predicate chain. A reviewer that never runs cannot be the enforcement point for the one tier that commits without a human.
- **SCOPED** — manifest, run directory, scope gate, floor, and a single combined SPEC+QUALITY review pass. Recon and the three pre-flights are skipped.
- **FULL** — the current pipeline, unchanged.

### A2. The mechanical consumer

`compound-v-validate-manifest.py` gains a required top-level block:

```yaml
triage:
  tier: SCOPED
  pre_eval_id: <id>
  taxonomy_digest: <sha256 of the taxonomy bytes>
  decided_at: <ISO-8601>
```

A manifest without a well-formed `triage` block fails validation, and `/v:dispatch` already refuses to run on a validator FAIL. A `taxonomy_digest` that does not match the taxonomy on disk also fails, so a record cannot outlive the rules that produced it.

**`/v:dispatch` passes `--require-triage` in every mode.** This is the closure, and it is load-bearing. The partition gate caught the first version of this design granting itself a permanent exemption: `--require-triage` defaulting on only for `--mode pre-dispatch`, and that mode being selected only for `fast_path` manifests, would have let every ordinary future run take the same mode-less pass 3.0 legitimately takes once during bootstrap. The CI historical sweep stays mode-less and keeps its allowlist; live dispatch does not.

**Rollout.** Requiring it turns CI red on 13 committed files (12 run manifests plus `examples/manifest.example.yaml`) — a count that drifts as runs land, so the implementation asserts it against the live tree rather than against this number, and `compound-v-fastpath-materialize.py:build_manifest` emits no `triage` and self-validates in-code, so it breaks at runtime and in its own selftest. Two changes, in this order:

1. `build_manifest` emits a `triage` block. Its selftest is updated in the same commit.
2. The historical manifests are handled by the **allowlist precedent this repo already set** in `.github/workflows/validate.yml:139-151` — listed by id, never back-filled, because "a reconstructed audit trail is the fabricated-evidence pattern, not a repair". The validator gains `--require-triage`, which ships **default-off in every mode** — a mode-scoped default was tried and removed as circular, and the closure is `/v:dispatch` passing the flag explicitly.

### A3. The entry point

New `/v:triage <request>`: resolve localization, classify, score, write and **commit** the record to `docs/superpowers/pre-eval/<id>.json`, print the tier with the predicates that decided it. This is the caller the engine has never had. `/v:orchestrate` invokes it when no record exists.

### A4. The narrow auto-route class

Iron Invariant #4 is amended, not deleted:

> **The score OFFERS by default. It auto-routes only inside the DIRECT auto-route class, whose membership is decided by mechanically checkable predicates and never by model judgement. Every other tier still requires a human offer and acceptance.**

Membership requires **all** of the following. The pre-flights killed the shape-only version of this list: every shipped unattended-landing system (Renovate auto-merge, SRE canarying, ITIL standard change) gates on **checks having passed** and on **demonstrated history**, not on how a change looks.

1. Tier is `DIRECT` and no override fired.
2. Exactly one resolved path, and it is a literal.
3. Taxonomy present and digest-matched — never on a fail-closed `unknown` band.
4. Path matches the taxonomy's `auto_route_allow` set.
5. Path matches **no** entry in the taxonomy's `sensitive` set. The set is **repo-local and taxonomy-driven**, not hardcoded: what is dangerous differs per project. The set **must always include the policy files themselves** — `.claude/compound-v-impact-taxonomy.yaml` and `.claude/compound-v.json` — in every project, because a policy that does not protect itself is not a policy. This repository's taxonomy additionally seeds auth, security, payments, PII, accessibility, CI workflows, `hooks/`, **and `skills/**/*.md`, `agents/*.md`, `commands/*.md`** — because here those files *are* the enforcement layer, so "docs-only" is a self-modification hole rather than a safe class. A downstream project whose markdown is ordinary documentation simply does not list it, and `/v:onboard draft-taxonomy` proposes the set from what the repo actually contains.
6. No test file touched.
7. **The floor has been run and passed.** A DIRECT change may not commit having run nothing. This ordering is the predicate r1 was missing — A4 and B2 were separate features with nothing sequencing them.
8. **Full post-diff re-validation, against the pre-edit policy.** After the edit, **all** of predicates 2, 3, 4, 5, 6 and the line budget (`auto_route_max_lines`, default 20) are re-checked against `git diff --numstat` and `--name-only`. Three properties are load-bearing and each closes a hole a cross-model review found:

   - **Path identity.** The realised path must *equal* the path triage resolved. "One literal path" is not enough: it permits substituting a different file of the same shape.
   - **An immutable pre-edit taxonomy snapshot.** Allowlist and sensitive membership are re-evaluated against the taxonomy as it was **before** the edit, and its digest must be unchanged. Otherwise the authorization can be rewritten by the very change it is authorizing: triage approves `docs/release-note.md`, the implementer instead edits only `.claude/compound-v-impact-taxonomy.yaml` to widen `auto_route_allow` to `scripts/**`, and the realised diff is one literal path, under twenty lines, not a test — and, under a seed that omits the policy file, not sensitive. Predicate 5's mandatory self-protection and this snapshot together close that.
   - **Atomic recheck at commit time.** Predicates 7, 8 and 9 are re-evaluated immediately before the commit, not at the start of the edit. Two concurrent sessions can otherwise both read "armed", the first disarm the breaker, and the second proceed on stale authorization.

   Any failure demotes to SCOPED before commit, and the demotion is recorded.
9. **Miscalibration circuit breaker, counting outcomes rather than shapes.** Auto-route is armed from the first decision — a warm-up gate was considered and **rejected by the maintainer**, on the grounds that it would make the feature's whole point unavailable for weeks. The safety property is therefore reactive rather than preventive.

   r3's version counted **post-diff demotions only**, and a cross-model review showed that this cannot see the failure it exists to catch: a mis-sized change that stays one allowed, non-sensitive, sub-20-line file is never demoted, so twenty bad commits in a row leave the rate at zero and the breaker armed. The numerator is therefore **negative `actual` outcomes**: a demotion, a CI failure on the resulting commit, a revert of it, or a later escalation of the same work to a higher tier. `compound-v-triage-outcomes.py` tracks the rolling rate over the last `auto_route_window` (default 20) DIRECT decisions; above `auto_route_max_demotion_rate` (default 0.25) auto-route **disarms itself** and reverts to offering until a human re-arms it.

   **The residual risk, stated plainly:** with no warm-up, the first miscalibrated DIRECT change commits before any evidence exists that the classifier is calibrated in this repository. Predicates 7 (floor passed) and 8 (full post-diff re-validation) are the only things standing between a mis-sized change and a commit, and the breaker can only fire *after* the first bad commit lands — and now, since the numerator includes CI failures and reverts, only after that commit's consequences are observable, which may be later still. The commit is on a branch and revertable; nothing is pushed automatically.

### A5. Recording the bypass

`docs/superpowers/memory/triage-outcomes.jsonl` starts receiving `predicted` on every decision and `actual` on every completed run — the stream `compound-v-triage-outcomes.py` was written for and has never had a data point.

`compound-v-triage-outcomes.py:733` currently collapses anything that is not fast-path into the `fullpipeline` cohort. SCOPED must become its own cohort, or the fast-path precision figure `/v:status` renders is silently corrupted by the new tier.

### A6. The taxonomy

`.claude/compound-v-impact-taxonomy.yaml` does not exist here, and absent taxonomy is an unconditional fail-closed FULL — so the engine cannot emit a non-`unknown` band in its own repository. `/v:init` does **not** seed it; `/v:onboard draft-taxonomy` does (`compound-v-onboard.py:535,744`), self-validating and behind a human gate. 3.0 runs that command rather than hand-authoring YAML.

## Feature B — Scoped tests, bought with a floor and an evaluation

### B1. Reuse, do not rebuild

`run_test_floor` (`compound-v-fastpath-run.py:308-343`) **already is** the floor: merge-blocking, records the command and its exit code, fail-closed on an empty command. It has never had a producer for `--test-cmd` (`"$CFG_TESTS"` is an unbound placeholder), and it returns at `:343` before `changed_paths` is computed, so it is not diff-proportionate. Feature B supplies the producer and moves the return below the diff computation. It does not introduce a second floor.

### B2. The contract

```yaml
test_contract:
  floor_command: "…"        # always runs, every tier
  full_command: "…"
  impacted_map:
    - when: "scripts/compound-v-*.py"
      run:  "python3 {path} --selftest"
```

```yaml
jobs:
  - id: task-1
    test_scope: impacted     # full | impacted | floor_only
```

`impacted_map` is declarative. A changed path matching no `when` glob resolves to `full_command` — an unmapped file is unknown blast radius, never "nothing to run". `floor_only` means *only the floor*, never nothing.

**The floor is three sets, not one.** Regression-test-selection practice (Azure TIA and the RTS literature) always runs impacted ∪ **previously failing** ∪ **newly added**. r1 had only the first. Previously-failing comes from the last recorded run's results; newly-added from `git diff --name-only --diff-filter=A`.

**What the floor is, said without varnish.** The floor is an **early-feedback optimization. It does not restore what the full suite guaranteed, and CI does.** The union of impacted, previously-failing and newly-added structurally omits every existing, previously-passing test the declared map fails to select: change `src/parser.py`, break `tests/test_cli_integration.py` through an indirect import, and no set selects it — the floor passes and only the merge-blocking CI run catches it. Any wording that implies the floor preserves pre-merge safety is wrong and must not ship.

**Known miss rate, stated with the claim.** Call-graph-derived selection is measured at 0.2% (class-level) to 10.6% (method-level) unsafe per revision, from reflection and library exclusion. A hand-written glob map carries strictly less information than a call graph, so **0.2% is an optimistic floor, not an expectation.**

**Overlapping rules union.** When several `when` globs match a changed path, every matching `run` command is selected. First-match-wins would silently drop coverage the map explicitly declares.

**"Previously failing" needs data that does not exist yet.** An aggregate exit code cannot tell the next run *which* tests failed. `tests.failures[]` (see B3) carries machine-readable identifiers; when a run cannot produce them, the next run's floor **falls back to `full_command`** rather than silently dropping the set.

### B3. Transport and reporting — the gap r1 missed

`schemas/job_result.schema.json:7` is `additionalProperties: false` and has no field for a test command or its exit code (`exit_code` is the worker process's). And there is **no transport**: every worker takes `--prompt-file`, and the `job_spec` contract has no test field — so `test_scope` would reach an external worker only as prose in a prompt, which is exactly the failure A2 exists to prevent.

Both are in scope:
- `job_result.schema.json` gains `tests: {command, exit_code, scope, selected_count, duration_ms, failures[]}`. `duration_ms` and `failures[]` are **measured-only**: absent rather than estimated when the runner does not report them. `duration_ms` exists because decision 4 promises the next release can speak from our own data, and a count without a duration cannot say whether scoping saved time. `failures[]` is what makes "previously failing" computable at all.
- `job_spec` gains a `test_contract` slice, and each worker script passes it through as a real argument, not as prompt text.

### B4. The review gate

`agents/spec-reviewer.md:138` becomes tier-aware: the floor must pass unconditionally; `full_command` is required at FULL and for any job carrying an unmapped path; the declared impacted set suffices at SCOPED and DIRECT. **A job reporting no test command at all is a FAIL**, not a pass — the reviewer reads `tests.command` and `tests.exit_code` from the job result, which is why B3 is a prerequisite rather than a nicety. **Unattended landing (the DIRECT auto-route class) additionally requires `full_command`**, because the floor alone does not carry the guarantee that class is trading on.

### B5. The CI backstop, made real

"The full suite still runs in CI before merge" is fragile as stated: GitHub reports a conditionally-skipped job as `Success`, so a path filter can turn a required check green without running it. The backstop must be a job that always runs and is required, dispatching internally.

Separately, and independently of this feature: until task-0 landed, **no file under `tests/` was executed by CI on this branch** — the only sweep was `for s in scripts/*.py`. Any test written for Feature C would land dead on arrival. That is the v2.14.1 false-green shape recurring and is fixed here.

### B6. The ADR

`docs/superpowers/adr/0003-scoped-tests-with-a-floor.md` supersedes the v2.17 rejection at `2026-07-25-v2.17-cochange-and-evidence-packing-design.md:308-310`. It must state the original rationale (v2.14.1: 25 of 29 selftests silently never running), name the three-set floor, the CI backstop and the measured RTS miss rate as the mitigations, and record what would falsify it.

## Feature C — The bypass rule, inside the existing hook

A rule added to `hooks/epic-goal-stop.sh` (absorbed from v2.18), not a second registration.

- Fires when the turn is ending and tracked, non-exempt files changed with no triage record covering them.
- **`session_id` is on the `Stop` stdin payload** — that is the mechanism r1 said it lacked. It is necessary and not sufficient: the pre-eval record schema has no session field, and `/v:triage` **commits** the record, which removes it from the dirty changed-set the existing hook inspects. So the record itself gains `session_id`, `base_commit` and `declared_paths`, and a DIRECT record additionally binds the realised diff digest.
- Exempt only when a record **covers this diff**: same session, and the changed paths within its declared set. A SCOPED or FULL record does not exempt code unless a corresponding run record exists. Without that binding, one triage of "change README" would exempt an unrelated later edit to `hooks/epic-goal-stop.sh` in the same session.
- OFF by default under `enforcement.triage_gate`.

Mechanics corrected by the pre-flights:

- **`stop_hook_active` is a consecutive-block counter, not a session flag**, and `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` (default 8) makes Claude Code override the hook and end the turn anyway. The rule blocks at most once per session on its own marker; it must not rely on the harness counter.
- **Exit 2 blocks.** Other non-zero exits are non-blocking errors. The `|| true` registration stays load-bearing, but for a narrower reason than r7 claimed: bash parses **incrementally**, so a malformed command only bites when execution reaches it. Probed on bash 3.2 — a parse error injected *below* `trap 'exit 0' EXIT` exits **0**, because the already-installed trap wins; injected *above* the trap it exits **2**, produces nothing on stdout, and only `|| true` saves the turn. The earlier wording, that no in-script trap can run when the script fails to parse, was true only of the second case.
- **All `Stop` hooks share a 1.5s budget.** A `git status` that times out is a *silent* no-op — the dead-guard shape again. The rule must use a bounded, cheap check and must record when it could not complete, rather than passing silently.

## Feature D — Dispatch on the native Workflow runtime

**Naming:** this is **Engine C**, the name used in nine shipped locations. "Engine B" is already taken by the rejected `claude -p` shell-out.

**This reverses a load-bearing guarantee and is treated as one.** `skills/compound-v/workflows-accelerator.md:60-71` states that Engine C "only changes how jobs fan out, never the enforcement or recovery layer" and that "`state.json` resume stays in Engine A". Feature D moves the scope gate and the state write *into* the workflow. `docs/superpowers/adr/0004-workflow-as-the-dispatch-engine.md` records the reversal, its rationale (the gate is currently prose on the only path anyone uses) and its falsification condition.

### D1. The gate is a stage; the authority is not

The script has no filesystem or shell access, but **agents it spawns do have full tools including Bash** — verified four independent ways. That makes the gate *runnable* inside the workflow. It does not make it *authoritative*, and r2 wrongly claimed it did.

```js
await pipeline(jobs,
  j        => agent(implementPrompt(j), {phase: 'Implement', schema: JOB_RESULT}),
  (r, j)   => agent(gatePrompt(j, r),   {phase: 'Gate',      schema: GATE_VERDICT}),
  (v, j)   => agent(recordPrompt(j, v), {phase: 'Record',    schema: RECORD_ACK}))
```

The variadic form and the `(prevResult, originalItem, index)` stage signature are confirmed against the tool contract.

**The Implement stage returns a raw `IMPLEMENT_RESULT`, never `job_result`.** `job_result` carries `blocked`, `files_changed` and `violations`, and this project's own contract says those are git-derived by the caller. Asking the implementer to report them is asking the constrained party to fill in its own enforcement fields — the fabricated-evidence pattern with extra steps.

**The Gate agent is narrowed at spawn, using two runtime options the public tool description does not mention** (found by reading the installed binary, `2.1.238`): `disallowedTools` strips its tool pool to Bash plus structured output, and **`bashCommandClamp`** confines its shell to the scope-check invocation alone. The clamp is genuinely fail-closed: it denies when the permission check crashes, denies commands whose structure it cannot verify, and **refuses to spawn the agent at all** if the clamp can bind nothing. A clamped Gate agent cannot do anything except run the check.

**It still cannot be forced to report honestly.** The clamp limits what an agent *can do*, not what it *returns*; the schema proves shape, not execution. So:

**The verification layer's integration postcondition is the authority.** Every original job must have exactly one gate receipt bound to its baseline commit, its realised commit and a diff digest. Where a receipt is missing, `null`, or its digests disagree with the tree, **the verification layer runs `compound-v-scope-check.py` itself** and that verdict wins. Integration is refused until every job has a valid receipt. The workflow gate is defense in depth and an early exit, nothing more.

Three further properties are mandatory, each closing a defect the pre-flights found:

- **The Gate stage must be total.** A stage that *throws* drops its item to `null` and **skips every remaining stage** — so a Gate exception would mean no `state.json` written, no record committed, and a job silently becoming `null`, precisely on the jobs that went wrong. That is the v2.6.4 audit-trail loss reappearing structurally. The Gate catches everything and returns a verdict; it never throws.
- **`null` is FAIL, never pass.** `agent()` returns `null` when the user skips it or it dies on a terminal API error. A gate that treats `null` as absence of violations is unreachable exactly when the worker died.
- **The Record stage must be idempotent, and so must everything with a side effect.** On relaunch, every agent that started after a failed one re-runs, including completed ones — so a completed job can implement, gate and record a second time. Every attempt and receipt is keyed to an immutable commit hash, each hash is merged **at most once**, and reconciliation skips terminal jobs. Idempotence on Record alone is not enough: it leaves double commits, double worktree integration and duplicate outcome events. Retry, integration, review and cross-session resume stay in the verification layer, which already implements per-failure-class policy the workflow runtime has none of.
- **An Implement-stage throw is not a silent pass.** A throwing stage drops its item to `null` and skips the rest, so a job can vanish before it is ever gated. The postcondition treats a missing receipt exactly like a failed one: it gates that job itself.

### D2. The generator

`scripts/compound-v-emit-workflow.py` turns `manifest.yaml` into the script: `depends_on` → topological staging, `max_parallel` → chunking, backend/tier/effort → `agent()` options. Constraints:

- The runtime makes `Date.now()`, `Math.random()` and no-arg `new Date()` **throw**, and `import()` fails before the run starts. The generator emits none of them; timestamps are passed in via `args`.
- The tool's own guidance is "pass the script inline — do not Write it to a file first", which is the opposite of committing the artifact. `scriptPath` takes documented precedence, so the dispatch prose must force the `scriptPath` form — otherwise the committed artifact is not what ran.
- `CLAUDE_CODE_WORKFLOWS` restricts a session to named workflows and refuses `script`/`scriptPath` outright. The dispatcher probes for it and falls back to the residual subagent path.

### D3. Engine C is the execution engine; two things are not engines

**Engine C is the primary and default way jobs execute in 3.0.** It is not an opt-in accelerator over our own loop, which is what `workflows-accelerator.md` decided in 1.0 and never built. The batching, ordering, worktree lifecycle and concurrency prose in `agents/parallel-dispatcher.md` is **deleted**, not left beside it.

**The seam moves up, and that is what unlocks `/v:epic`.** A subagent has no Workflow tool — probed live under both the public name `Workflow` and the internal `RunWorkflow`. Today `/v:dispatch` delegates the run to the `compound-v:parallel-dispatcher` **subagent**, which is precisely why an epic would otherwise be stuck on the old path. `/v:epic` invokes `/v:dispatch` as a *command*, executed by the top-level agent, so once dispatch stops delegating to a subagent the epic inherits Engine C along with everything else. The armed-goal `Stop` hook is unaffected either way: it reads `epic-state.json` via `--goal-status` and matches `session_id`, and has no coupling to how jobs were executed.

**Two survivors, and neither is an "engine".** Calling them one invited the idea that Compound V ships three competing orchestrators. It ships none:

- **The verification layer.** The git-derived integration postcondition of D1, plus `state.json` and `/v:resume` for cross-session recovery — the native runtime's resume is same-session-only and re-runs completed agents past a failure point. This is the product, not a fallback.
- **The residual subagent path.** A reduced form of the old loop, retained *only* for contexts that physically cannot launch a workflow. On current evidence that is subagent contexts alone: workflows **are** available in `claude -p` and the Agent SDK, contrary to an earlier claim in this spec which is withdrawn. Headless launch needs an allow rule, auto mode or a `PreToolUse` hook, and must never be armed under `bypassPermissions`, where a run could start with no prompt and no spend cap.

### D5. The cross-vendor path, which is not automatically unaffected

Codex and Gemini workers are OS processes launched by `scripts/compound-v-run-*-worker.sh`, and a workflow `agent()` has Bash, so the mechanism survives the move. But "unaffected" is an assertion, and three concrete interactions have to be designed or the second family quietly stops working:

1. **`bashCommandClamp` must admit the worker script.** A clamped Gate or implementer agent whose clamp does not include `scripts/compound-v-run-<backend>-worker.sh` cannot launch the external family at all — and a clamp that can bind nothing makes the runtime **refuse the spawn outright**, so this fails loudly rather than degrading. Any job whose `backend` is not `claude` gets the worker invocation in its clamp, or no clamp.
2. **The lane-guard `PreToolUse` hook matches `Bash` and must not deny the worker invocation.** It also must not attempt to police what the external process writes: that happens in a separate process, in its own worktree, outside any hook this session controls. Those writes are covered the way they are today — by the worker script calling the git-derived scope gate itself, and by the integration postcondition of D1.
3. **No nested worktrees.** The codex worker creates and owns its own worktree, and this repository already carries a downstream incident from getting that wrong: a sandboxed worker could not repair its own git base, and the wrong fix was dropping worktree isolation. A workflow agent that is itself `isolation: 'worktree'` and then spawns a worker that creates a second worktree inside it is untested and not shipped. **Non-`claude` jobs run their workflow agent at `isolation: 'direct'`**, letting the worker script own the isolation exactly as it does today.

The arbiter's own logic — a second, genuinely different model family, the frozen audit, the confirmed-blocker bar — is untouched: none of it lives in the dispatch loop.

### D4. Version floor

Local install is 2.1.238. Floor: **Claude Code ≥ 2.1.219**. The `/workflow-authoring` skill requires 2.1.248 and is unavailable on the development machine, so nothing may depend on it.

## Feature E — Lane enforcement as a native deny, not a post-hoc verdict

The scope gate is Compound V's headline guarantee and today it is a **detector**: a worker writes outside its lane, and afterwards a git diff notices and the result is rejected. On the claude path — 73 of 73 recorded jobs — even that is prose the dispatcher must remember to run.

A live probe ([1D](../preflight/2026-09-01-v3.0-1d-native-enforcement-probe.md)) established that the native runtime offers a **prevention** point instead:

- `PreToolUse` **fires for agents spawned by a workflow**, which was the open question.
- Its stdin payload carries **`agent_id` and `agent_type`**, not just `session_id`, so a tool call can be attributed to one concurrent worker directly.
- `cwd` is that agent's worktree, and `tool_input.file_path` is absolute inside it. Workflow worktrees are linked worktrees at `.claude/worktrees/<runId>-<n>`.
- A hook returns `hookSpecificOutput.permissionDecision: "deny"` with a reason.

### E1. The rule

`hooks/lane-guard.sh`, registered on `PreToolUse`:

1. Resolve the job: `agent_id` → the run's job map; fall back to `cwd` → worktree id → job.
2. Read that job's `write_allowed` from the manifest.
3. Test `tool_input.file_path` against it with the **same matcher `compound-v-scope-check.py` already uses**, imported rather than reimplemented — two glob engines that disagree is a bug factory, and the existing one has reproduced-exploit selftests behind it.
4. Outside the lane → `permissionDecision: "deny"` with the lane in the reason. Inside → stay silent.

### E2. What it does not cover, said plainly

**A `Write|Edit` matcher is trivially bypassed by writing through the shell.** `sed -i`, a heredoc, `cp`, `git checkout`, or a build step never reach those matchers. This is not hypothetical: the probe agent reported that this very environment injects a reminder preferring `cat`/`sed`/heredocs over the `Write` tool.

So Feature E:

- also matches **`Bash`** and inspects the command, and
- pairs with **`bashCommandClamp`** on spawn, which narrows what a worker's shell may run at all, and
- **keeps the git-derived post-hoc verdict as the authority.** Command inspection is a parsing problem with unbounded evasions; a deny that can be walked around is a supplement, never a replacement. Feature E raises the floor from "detected afterwards" to "refused at the point of writing, for the paths a matcher can see" — and the D1 integration postcondition still decides what enters the tree.

### E3. The other enforcement points, now that they are known

The same probe pass over the installed runtime surfaced events this project was not using. Each replaces prose that has demonstrably not been followed:

| Guarantee | Native point | What it replaces |
|---|---|---|
| Triage fires when a change request arrives | **`UserPromptSubmit`** | a skill description that fires four transitions too late — which is why the scorer has never run |
| Lane enforcement | **`PreToolUse` deny** (E1) | git detection after the write |
| Worker cannot reach beyond its job | `disallowedTools`, `bashCommandClamp` at spawn | nothing at all today |
| Position survives a compaction | **`PostCompact`**, which receives the summary | v2.19's `SessionStart` banner, which fires on compact but cannot see what was summarized |
| Bypass and goal continuation | `Stop` | already mechanical |

`PostCompact` is an improvement on work shipped four commits ago and is in scope: the v2.19 banner reconstructs position from disk, while `PostCompact` is handed the summary itself.

## Decisions taken (brainstorm, 2026-09-01)

1. **No warm-up for auto-route.** Armed from the first decision; safety is the reactive circuit breaker in A4.9, not a history precondition. The residual risk is recorded there in the maintainer's hearing rather than mitigated away.
2. **The `sensitive` set is repo-local and taxonomy-driven.** The markdown exclusion is this repository's entry, not a global rule.
3. **Engine C is the primary execution engine in 3.0, not an opt-in accelerator.** The hand-rolled orchestration is deleted in the same release rather than deprecated beside it — two live paths for one job means the audit trail is written by whichever one an agent happened to pick. The two survivors are not engines: the verification layer (which holds the authority) and a residual subagent path for the one context that physically cannot launch a workflow.
4. **`v2.18-autonomy` is absorbed whole**, including its unfinished command wiring (job p5). One Stop script, one release.
5. **Build with the caveat rather than measuring first.** The "~20,000 tests" observation is unreproduced and every cost-governance source found was vendor marketing, so Feature B's defaults are principle-derived and no speed or cost claim ships with this release. AC-23 enforces the wording; the pipeline records selected-test counts and durations (AC-11) so the next release can speak from our own data.
