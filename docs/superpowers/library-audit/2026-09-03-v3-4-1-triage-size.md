## 4. Critical Findings 🔴

### 🔴-1 · The WS-E cross-model receipt cannot validate against `schemas/plan-review.schema.json` as literally specified — the schema forbids the fields the spec also requires on it

**Claim in the spec (WS-E):** *"A new `--require-cross-model-receipt <path>` … verifies the receipt file: valid against `schemas/plan-review.schema.json` plus `run_id`, `pre_eval_id` and `diff_digest` (`sha256:` over the wave's sealed patch bytes) equal to the run's."* The plan this spec produced (`docs/superpowers/plans/2026-09-03-v3.4.1-triage-size.md`, Task E Interfaces) repeats this almost verbatim and additionally implies a `digest` field ("receipt missing/mismatched digest → violation" in the failing-selftest step) that isn't in either reading of the spec text.

**Evidence, this session:**
1. `schemas/plan-review.schema.json`, read in full: `additionalProperties: false`; declared properties are exactly `verdict`, `summary`, `findings`, `blind_spots_checked`. No `run_id`, `pre_eval_id`, `diff_digest`, or `digest` property exists.
2. `scripts/compound-v-codex-review.sh:155`, read in full: the **only** producer of a `plan-review.schema.json`-conformant object runs `codex exec --output-schema "$SCHEMA"` — codex's structured output is *constrained to the schema*, so it is architecturally incapable of emitting `run_id`/`pre_eval_id`/`diff_digest` even if asked, because those are orchestrator-side facts a reviewing model has no way to know and the schema has no slot for them.
3. `schemas/fastpath-review-receipt.schema.json`, read in full: the repo's own working precedent for "a review verdict plus binding IDs" is a **separate, dedicated** schema (`run_id`, `pre_eval_id`, `baseline_sha`, `final_diff_digest`, `digest`, `verdict`, … all flattened into one `additionalProperties: false` object) — not "validate the same object against schema X and also demand three fields X's `additionalProperties: false` forbids."

**Impact.** As written, the only two readings are both broken: (a) literally validate the on-disk receipt object against `plan-review.schema.json` — then a receipt that also carries `run_id`/`pre_eval_id`/`diff_digest` fails schema validation on those three fields alone, so **every real `scoped_plus` receipt would be schema-rejected**, silently hard-blocking the one path (SCOPED+: sensitive-path small edits) this whole spec designed a mandatory extra review gate around; or (b) the implementer notices the conflict mid-task and improvises a wrapper shape that Task E's own acceptance criteria never specified, so two different Claude workers (or one worker across a retry) could each invent an incompatible wrapper and the validator that Step 1's failing-selftest locks in would be pinned to whichever guess landed first — an implementation detail becoming an unreviewed contract.

**Constraint:** before Task E is dispatched, the plan needs an explicit receipt SHAPE — either (i) a new dedicated schema (`schemas/cross-model-review-receipt.schema.json` or similar), modeled on `fastpath-review-receipt.schema.json`'s pattern, that nests the codex `plan-review.schema.json`-conformant object under one property (e.g. `review: {...}`) alongside sibling `run_id`/`pre_eval_id`/`diff_digest` fields, **or** (ii) two separate checks — schema-validate only the codex-produced `review` sub-object against `plan-review.schema.json`, and check the three binding fields as plain equality assertions outside that schema, on a wrapper object the schema itself never sees. Either is cheap; picking neither and leaving it to the implementer is the actual risk.

## 6. Medium Findings 🟡

### 🟡-1 · `--tools ""` is well-evidenced but not independently exercised by a live call from any session that produced this audit chain

See §3's triangulation table. Four independent sources agree the flag exists and that an empty string disables every tool, and two of those are full un-truncated quotes from different origins (not two fetches of the one page that could share a single confabulation). That is materially stronger evidence than this repo's own KB precedent for treating a claim as settled (the `CronCreate` 7-day-expiry finding in the 2026-09-02 audit rested on **one** live `ToolSearch` schema fetch, graded sufficient). Still: this specific subagent has no Bash access to run `claude -p --model sonnet --tools "" --output-format text "ping"` itself and observe the exit code and stdout, and the project's own stated verification style ("prove a runtime/tool can't do X with a live probe before claiming impossible") cuts the other way too — a claim this load-bearing (it is the sole tool-disabling mechanism for a fail-closed classify prompt: WS-D's whole safety story is "the light model has zero tool access, so it cannot do anything but answer the enum") is worth one real invocation before Task D is accepted, not four consistent web sources alone.

**Constraint:** add a live-probe step to Task D's acceptance (the same bar §5 of the 2026-09-02 `v3-4-native-first` audit set for `ProposeGoal`): before merge, actually run `claude -p --model <resolved light model> --tools "" --output-format text "reply with exactly: plumbing"` from a context that *can* shell out, and confirm (a) exit 0, (b) stdout is plain text with no tool-use attempt, (c) the reply parses as the one enum token. This is a ~5-second check that converts a well-triangulated web claim into the kind of live evidence this pre-flight's own `_selftest` for the codex fallback already sets as the bar (`compound-v-classify-request.py`'s existing `_selftest` drives a **fake** codex binary through the real argv-construction code — there is no equivalent fake-`claude` fixture yet for the new headless-claude route, and Task D's own Step 1 plan text says the fake claude prints `plumbing`/garbage/sleeps, which covers the *parsing* contract but not whether `--tools ""` really starves the process of tool access).

Covered in §2's table. Not a currency problem (the package that's already there is fine); it is a scope constraint on *how* Task E implements the new validation, worth stating explicitly so it doesn't quietly become the second hard-dependency exception the 2026-09-02 v3.4-native-first audit already had to flag once for `compound-v-emit-workflow.py`'s `_load_yaml()`.

## 7. Design Constraints for the Plan

**MUST**
1. Define the WS-E cross-model receipt's actual on-disk shape before Task E is dispatched — either a new dedicated schema file (modeled on `schemas/fastpath-review-receipt.schema.json`) or an explicit two-part validation (schema-check a nested `review` object, equality-check the three binding fields separately). `plan-review.schema.json` cannot be the validated object AND carry `run_id`/`pre_eval_id`/`diff_digest` at once while `additionalProperties: false` stands. (🔴-1)
2. Implement WS-E's schema check by reusing/extending `_schema_lite()` (`compound-v-validate-manifest.py:1327`), not by adding a first production `import jsonschema` — the package stays test-only exactly as it is today. (🟡-2)
3. Add one live invocation of `claude -p --model <light> --tools "" --output-format text <prompt>` to Task D's acceptance criteria before merge, confirming exit 0, tool-free plain-text output, and a parseable enum reply — the flag is well-evidenced but has not yet been run by anything in this audit chain. (🟡-1)

**MUST NOT**
4. Ship a validator that schema-checks the WS-E receipt literally against the unmodified `schemas/plan-review.schema.json` while also requiring `run_id`/`pre_eval_id`/`diff_digest` on the same object — that combination rejects every legitimate receipt by construction (🔴-1), which would silently and permanently hard-block the `scoped_plus` path the rest of this spec exists to make safe.
5. Let `schemas/plan-review.schema.json` itself be edited to add `run_id`/`pre_eval_id`/`diff_digest` as a quick fix without also updating `scripts/compound-v-codex-review.sh`'s `--output-schema` contract and `commands/v-review-plan.md` — that schema has an existing consumer (`/v:review-plan`, unrelated to `scoped_plus`) whose codex-constrained output would then be asked to produce fields it cannot know, or the schema would need those three fields marked optional, which the "receipt missing/mismatched digest → violation" acceptance criterion (Task E, plan) already assumes are *required* for the receipt path specifically — the two consumers' needs diverge and a single shared schema edited for one silently changes the other's contract.
