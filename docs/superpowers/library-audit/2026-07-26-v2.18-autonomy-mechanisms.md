### 3.3 `stop_hook_active` producer — binary offset 230333922, verbatim

```js
async function* m8e(e, t, r=Mm, n=!1, o, i, s, a) {
  let l = o ? "SubagentStop" : "Stop";
  ...
  m = o ? {...sm(e,void 0,i), hook_event_name:"SubagentStop", stop_hook_active:n, ...}
        : {...sm(e,void 0,i), hook_event_name:"Stop",         stop_hook_active:n, ...};
```

`n` is `ne`, destructured from the query-loop state `g`. Every continue-branch in that
loop (`compact retry`, `malformed_tool_use_retry`, `thinking_only_retry`, `next_turn`)
propagates `stopHookActive: ne` unchanged; only the block branch **sets it to `!0`**;
and it is initialized false once per query entry (`stopHookActive: e.stopHookActive ?? !1`,
offset 228278819).

## 4. Findings

### 4.1 🔴 CRITICAL — "honor `stop_hook_active`" and "bounded by the cap of 8" are mutually exclusive. As written, Feature A blocks exactly ONCE.

Spec, Feature A:

> **Bounded, three ways:** a `max_continues` counter … the harness's own cap of 8
> consecutive blocks (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`) …
> **`stop_hook_active` is honored** — when the harness reports it, the hook returns
> success immediately.

Traced through the shipped runtime (§3.2, §3.3): once a `Stop` hook blocks, the loop
sets `stopHookActive: !0` and **never clears it for the remainder of that user turn**.
So the very next `Stop` event arrives with `stop_hook_active: true`.

A hook that "returns success immediately when `stop_hook_active` is true" therefore
blocks **at most once per user turn**. `max_continues` never exceeds 1. The harness cap
of 8 is unreachable dead code. The circuit breakers never engage. `/v:epic`'s marathon
gains **one** extra continuation, not a longer unattended run — and the acceptance
criterion "bounded by its own counter" would pass its selftest while the feature is
inert in production.

**The cited working example does the opposite.** `ralph-loop/1.0.0/hooks/stop-hook.sh`
parses `session_id` and `transcript_path` from stdin (lines 32, 68) and **never reads
`stop_hook_active` at all**. Its only bound is its own `max_iterations` frontmatter field
(line 61) plus the harness cap. That is precisely why it can loop. The spec cites
ralph-loop as the pattern for session isolation — correct — but then adopts a
`stop_hook_active` behavior ralph-loop deliberately does not have.

The runtime's own guidance text ("check `stop_hook_active` … and return success while
it's true") is printed **only in the cap-exceeded warning** — it is advice for hooks that
have no bound of their own, not a contract requirement. A hook with a durable counter is
already bounded.

Two mutually exclusive resolutions; the maintainer picks one, **the spec cannot keep both
clauses as written**:

- **(a) Marathon works.** Drop the unconditional early-return. Treat `stop_hook_active`
  as one input among several (e.g. it may still gate side-effectful work inside the hook),
  and let the hook's own `max_continues` counter + the harness cap be the bound. Matches
  ralph-loop. Cost: a hook bug can hold a turn open for up to 8 blocks — bounded, not
  unbounded.
- **(b) Keep the early-return.** Then **delete the claims** that this is bounded "three
  ways" and that the harness cap participates, and restate Feature A honestly as
  "one goal-driven continuation per turn". That is a materially smaller feature than the
  spec's "meaningfully longer unattended runs with a ceiling".

Note this does **not** affect Feature B (enforcement), which blocks at most once per
session by design — for Feature B, honoring `stop_hook_active` is harmless and correct.

### 4.2 🟠 HIGH — the cap of 8 is real but is (a) off by one in the spec's favour and (b) a user-removable kill switch, so it is not a guarantee.

- Default is **8** (`ble(process.env.CLAUDE_CODE_STOP_HOOK_BLOCK_CAP, 8)`). Confirmed
  in the binary; **absent from the public docs entirely** (WebFetch of
  `code.claude.com/docs/en/hooks` returns no cap and no env var). Local runtime wins.
- Arithmetic: `stopHookBlockingCount` starts at 0; the guard is `Wi > Us` where
  `Wi = count + 1`. So **8 blocks are honored and the 9th is overridden**, ending the
  turn with a `warning`-level system message. Not an error, not a crash.
- `if (Us > 0 && ...)` — setting `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=0` (or negative)
  **disables the cap entirely**, making blocking unbounded from the harness side.
  The spec treats the cap as one of three independent bounds; it is an
  environment-dependent default, not an invariant.
- `maxTurns` is checked **before** the cap (`if (c && Io > c)`). Under
  `claude -p --max-turns N` the effective ceiling is `min(N, cap)`.

### 4.3 🟠 HIGH — a `Stop` block is silently DISCARDED on several end-turn paths.

Binary offset 228258074, function `CRs`, verbatim:

```js
if (y.blockingError || y.preventContinuation)
  C(`[end-turn] Stop hook block discarded (turn ended by ${
      d==="tool" ? "tool result" : d==="mcp_meta" ? "MCP end-turn" : "loop tick"
    }, no model re-invoke): ${y.blockingError?.blockingError ?? y.stopReason ?? "preventContinuation"}`)
```

When the turn ends via a tool-result end-turn, an MCP `mcp_meta` end-turn, or a **loop
tick**, the `Stop` hook still fires but its block is dropped with a debug log and no
model re-invocation. The same discard exists for `PostToolBatch` (offset 104857344).

Undocumented publicly. Practical consequence for both Features A and B: **the hook is not
a hard gate on every turn-ending path.** Feature B's "blocks once per session" enforcement
can be bypassed by whichever path lands in `CRs`. Design accordingly — and do not write an
acceptance criterion that claims the hook cannot be bypassed.

### 4.4 🟡 MEDIUM — `matcher` on `Stop` is silently ignored (registration otherwise confirmed).

Docs, verbatim:

> `UserPromptSubmit`, `PostToolBatch`, `Stop`, `TeammateIdle`, `TaskCreated`,
> `TaskCompleted`, `WorktreeCreate`, `WorktreeRemove`, `MessageDisplay`, `CwdChanged`
> don't support matchers and always fire on every occurrence. **If you add a `matcher`
> field to these events, it is silently ignored.**

The working example agrees — `ralph-loop/hooks/hooks.json` registers `Stop` with **no**
`matcher`:

```json
{ "hooks": { "Stop": [ { "hooks": [ { "type": "command",
  "command": "bash \"${CLAUDE_PLUGIN_ROOT}/hooks/stop-hook.sh\"" } ] } ] } }
```

Compound V's existing `hooks/hooks.json` uses `matcher` on `PreToolUse`/`SessionStart`/
`PostToolUse`, where it *is* meaningful. Do not carry the habit to `Stop`.

Valid `Stop` output fields (docs + runtime agree): top-level `decision:"block"` + `reason`;
universal `continue`, `stopReason`, `suppressOutput`, `systemMessage`, `terminalSequence`;
and `hookSpecificOutput.additionalContext` for **non-blocking** feedback (runtime offset
228265067 — `additionalContexts` are yielded as `hook_additional_context` and do **not**
enter `blockingErrors`). **`permissionDecision` / `permissionDecisionReason` are
PreToolUse-only and invalid on `Stop`.** Exit 2 also blocks; for `Stop`, stderr is fed
back as `Stop hook blocking error from command "<name>": <stderr>` (offset 230340978).

### 4.5 🔴 CRITICAL — Feature G's `setsid` does not exist on macOS.

```
$ command -v setsid   →  SETSID: NOT FOUND
$ command -v timeout  →  timeout: NOT FOUND
$ command -v gtimeout →  gtimeout: NOT FOUND
$ command -v nohup    →  /usr/bin/nohup
```

Spec, Feature G: "**Detached launch** (`setsid`, output to the run directory) behind an
explicit `detach: true`". `setsid` is util-linux; macOS ships neither it nor GNU
`timeout`. On this machine — the only machine Compound V has ever run on — a `setsid`
detach path fails at the first line.

The repo already solved the sibling problem correctly and the fix generalizes:
`scripts/compound-v-run-codex-worker.sh:191-194` explicitly avoids external
`timeout`/`gtimeout` in favour of `scripts/compound-v-run-with-timeout.py`, a Python
process-group supervisor that `killpg`s the whole tree. Detachment needs the same
treatment — `os.setsid()` in Python, or `nohup` + `&` with an explicit new process
group — not the `setsid(1)` binary. **Do not let the plan ship a `setsid`-shaped
selftest that passes on CI Linux and fails on the maintainer's Mac.**

Related, already handled — keep it: the worker redirects `</dev/null` (line 341/353)
because `codex exec` otherwise emits `Reading additional input from stdin...`. My live
probe reproduced that message when stdin was left attached. A detached worker **must**
keep the redirect.

### 4.6 🟠 HIGH — Feature D's "read the reset time from the provider's own signal when present": CONFIRMED for Claude, effectively NOT REACHABLE for codex. The clause is half dead code.

**Claude — the signal exists and is machine-readable.** Three independent surfaces in
2.1.216:

- HTTP response headers `anthropic-ratelimit-unified-status`,
  `anthropic-ratelimit-unified-reset` (unix epoch seconds),
  `anthropic-ratelimit-unified-overage-reset`,
  `anthropic-ratelimit-unified-<claim>-utilization` (offsets 86452586, 224095850).
- `GET /api/oauth/usage` → `{percent, utilization, resets_at}` per window (offset 224086525).
- **Emitted into the SDK/stream-json output stream** (offset 238755226):
  `{"type":"rate_limit_event","rate_limit_info":{"status","resetsAt","rateLimitType","utilization","overageStatus","overageResetsAt",...},"uuid","session_id"}`.

That third one is the reachable path for a Compound V `claude` worker. **Caveat: verified
by reading the shipped emitter, not by observing a live 429** — I did not hit a limit to
confirm. Treat as code-verified, not field-verified.

**Codex — the structs exist but the `exec` surface does not expose them.** Live probe on
codex-cli 0.144.1:

```
codex exec --cd <tmp> --sandbox read-only --skip-git-repo-check \
  --model gpt-5.6-luna --json --ephemeral "Reply with exactly: OK"
```

emitted exactly: `thread.started`, `turn.started`, `item.completed`×3, `turn.completed`.
`turn.completed` carries `{"usage":{input_tokens,cached_input_tokens,output_tokens,reasoning_output_tokens}}`
and **no `rate_limits`, no `resets_at`, no reset time of any kind**. The binary does
contain `RateLimitWindow{used_percent, window_minutes, resets_at}`,
`RateLimitWindowSnapshot{limit_window_seconds, reset_after_seconds, remaining}` and
`UsageErrorBody{plan_type, resets_at}` — but they live in the **app-server** protocol
(`app-server/src/request_processors/account_processor/rate_limit_resets.rs`), not the
`exec --json` event stream. The user-facing exec text is prose with no timestamp:
`"You've hit your usage limit for {}. Switch to another model now"`.

So Feature D's "when present" is: **present for `claude`, absent for `codex exec` under
normal operation, and unverified for `codex` on an actual 429.** The clause is not dead
code — but it is dead for the backend the spec's failure policy most often circuit-breaks
(`FALLBACK = {"codex": "claude", ...}` in `scripts/compound-v-failure-policy.py:64`).
The estimate-labelling path is the *primary* path for codex, not the fallback. Say so.

### 4.7 🟡 MEDIUM — `jq` guard, and a free upgrade the spec doesn't use.

- Global constraints require hooks to "not require `jq` to be present without a guard".
  `jq` **is** present here (1.7.1, Homebrew) and the ralph-loop reference implementation
  uses it unguarded (lines 32, 68, 112, 181). Compound V's own constraint is stricter
  than the example it is copying — keep the stricter rule; the working example is not a
  license to drop the guard.
- `last_assistant_message` is available on `Stop`/`SubagentStop` (requires ≥ 2.1.197;
  local is 2.1.216) and removes any need to parse `transcript_path` — ralph-loop's
  100-line jq transcript parse (lines 79-126) is legacy. Feature A's goal condition is
  state-derived and shouldn't need either, but if anything in the plan reaches for the
  transcript, this is the cheaper field.
- `background_tasks` on `Stop` explicitly exists to "distinguish 'session is done' from
  'session is paused waiting for background work'". Directly relevant to Feature G's
  detached codex workers — it is a first-class signal, not something to infer.

## 5. Design constraints for the plan (non-negotiable)

**MUST**
- Resolve §4.1 before writing the plan. If the hook keeps the unconditional
  `stop_hook_active` early-return, the spec's "bounded three ways" and "meaningfully
  longer unattended runs" claims MUST be struck; if the loop is to work, the early-return
  MUST go and the hook's own counter + the harness cap become the bound.
- Register `Stop` with **no `matcher`**, nested exactly
  `hooks.Stop[].hooks[].{type:"command", command}`.
- Read `session_id`, `transcript_path`, `cwd` as **required** stdin fields; `stop_hook_active`
  as a required boolean.
- Block via top-level `{"decision":"block","reason":...}` on stdout with exit 0
  (ralph-loop pattern), or exit 2 with stderr. Never emit `permissionDecision` on `Stop`.
- Implement detach in Python (`os.setsid()`) or `nohup`+new-process-group, **never**
  `setsid(1)`. Keep `</dev/null`. Any detach selftest MUST fail on a `setsid` binary
  dependency, not skip.
- State the harness cap as "8 by default, overridable and disableable via
  `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`" — never as a guaranteed bound. Compound V MUST NOT
  set that env var.
- Feature D MUST label the codex path as estimate-only by default, and MUST NOT claim a
  measured reset time for codex. The `claude` path MAY read `rate_limit_event.resetsAt`
  (epoch seconds) — and MUST be written to degrade to the estimate when the event is absent.
- Keep the `jq`-presence guard in any new hook, despite ralph-loop not having one.

**MUST NOT**
- MUST NOT claim the `Stop` hook is an unbypassable gate (§4.3 discard paths).
- MUST NOT write an acceptance criterion whose selftest can pass on synthetic stdin while
  the production behavior is inert (the §4.1 trap — "bounded by its own counter" is
  exactly such a criterion today).
- MUST NOT cite ralph-loop as the precedent for honoring `stop_hook_active`. It does not.
- MUST NOT rely on GNU `timeout`/`gtimeout`/`setsid` anywhere in the shipped path.

## 6. Open questions for the human

1. **§4.1 — which resolution?** (a) working marathon with the early-return removed and up
   to 8 blocks per turn, or (b) honest one-block-per-turn and a rewritten Feature A
   headline. This is a scope decision, not a technical one. Everything else in Feature A
   is fine.
2. **§4.3 — is a bypassable enforcement gate acceptable for Feature B?** Given
   `enforcement: off` by default this is probably fine, but the acceptance criteria should
   not overclaim.
3. **§4.6 — is codex's estimate-only path acceptable**, or should `wait_until` be
   claude-backend-only until a real codex 429 is captured?
4. **`StopFailure`** is a shipped event (fires when a turn ends in error) that the spec
   never mentions. Should an armed goal survive a failed turn, or disarm? Silent today.
