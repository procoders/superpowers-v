## 3. Sibling Code

### 3a. `classify_via_codex` (`compound-v-classify-request.py:320-372`) — the template WS-D's `--classify-headless` must mirror

This is the ONLY existing "spawn an external CLI, parse a strict enum, fail-closed" path in
the codebase, and WS-D's new headless-claude route is explicitly modeled on it (same file,
same fail-closed contract). Read in full. Entry conditions/shape:

- Builds the prompt via `build_prompt` (shared, bounded — `MAX_PROMPT_CHARS=8000`).
- Resolves the model via `compound-v-resolve-model.py`'s `resolve()`
  (`resolve("codex", "light", config_models=...)` — confirmed the sibling supports
  `resolve("claude", "light", ...)` identically via its `--backend`/`--tier` CLI flags,
  `compound-v-resolve-model.py:457-458`; **no gap here**, WS-D's `compound-v-resolve-model.py
  --backend claude --tier light` is already a supported call shape).
- Spawns via `compound-v-run-with-timeout.py` (the shared process-group supervisor),
  **never** a bare `subprocess.run(timeout=...)`.
- `stdin=subprocess.DEVNULL` **at both layers** (the module's own `subprocess.run` call AND
  the supervisor spawns the child with DEVNULL again — defence in depth, not redundant per
  the module's own comment at line 348).
- Exit-code handling: `TIMEOUT_EXIT_CODE=124` → `unknown, timed_out=True`; any other
  non-zero → `unknown, timed_out=False`; missing last-message file → `unknown, error:
  "no_reply"`; anything parseable → `parse_category(reply)`.
- Result shape: `_result(category, **extra)` always emits `{"category", "backend":
  "codex", ...extra}` — WS-D's spec text "Output JSON `{category, backend, timed_out,
  exit_code, model}` as the codex mode already prints" is **accurate**: this is exactly
  the shape `classify_via_codex` already returns (`backend` hardcoded to `"codex"` inside
  `_result`, so the headless-claude route needs its own `_result`-equivalent or a
  `backend=` parameter added to the shared one — today `_result` cannot express
  `backend: "claude"` without a signature change).
- **Known latent bug-shaped edge, not a bug today:** `build_codex_command` hardcodes
  `--sandbox read-only` and `network_access=false`. WS-D's claude route uses `--tools ""`
  instead of a sandbox flag (Claude CLI has no `--sandbox` concept) — the two routes are
  NOT parallel at the argv level even though they share the wrapping/timeout/parse
  machinery. A naive copy-paste of `build_codex_command` would pass Claude a `--sandbox`
  flag it does not understand and fail every call. The plan must treat "the codex-route
  shape" and "the codex-route *argv*" as separate things to reuse.

### 3b. The `needs_t3` hand-off contract (`triage_request` docstring, `compound-v-preeval.py:1309-1336`) — what WS-D's hook rewrite can rely on for free

Read in full, cross-checked against `run_preeval` (`:993-1174`). The resume/re-entry
machinery **already exists and already works** for exactly the shape WS-D needs:

- `run_preeval`'s `needs_t3` branch (`:1122-1131`) returns **before** writing the record or
  appending `predicted`, but **after** writing the intent record, the localization artifact,
  and the taxonomy snapshot (`:1050-1074`, unconditionally, ahead of the `score()` call).
- A second call with the **same request text** (same normalized fingerprint) and a
  `t3_category` now supplied will, via `find_pre_eval_id_by_request` (`:717-736`), rediscover
  the **same** `pre_eval_id` rather than minting a new one, re-run localization (recomputed,
  not cached — a real but pre-existing cost, not a new one), find `write_intent_record` and
  `write_taxonomy_snapshot` idempotent no-ops, and then proceed straight through `score()`
  to a real record.
- **Conclusion for WS-D: the engine needs zero changes to support "run classify-headless,
  then re-invoke `triage --t3-category <enum>`."** The only genuinely new code is (a) the
  `--classify-headless` CLI mode in `compound-v-classify-request.py`, and (b) the hook's
  control flow in the `needs_t3` branch. The `_triage_cli` argparse (`:1405-1428`) has no
  `--pre-eval-id` flag and doesn't need one — resume-by-fingerprint already does the job, but
  **only if the hook passes the identical request text on both calls** (the same
  `CV_TRIAGE_REQUEST` value) — a design constraint worth stating explicitly since nothing
  enforces it structurally.

### 3c. The `needs_t3` branch in `hooks/triage-prompt-nudge.sh` (lines 489-493) — read in full, this is what WS-D replaces

```bash
if [ "$needs_t3" = "true" ]; then
    _log "the request needs the T3 classify step — degrading to the reminder"
    _emit "$(_reminder_text)"
    return $?
fi
```

Entry condition: `needs_t3` field of the engine's JSON result is `"true"`. Today this is an

parameter threaded through it; today's function signature has no such parameter.

**The load-bearing regression risk sibling-reading this file surfaces (see §5 for the full
write-up): the hook is registered with `"timeout": 10` in `hooks/hooks.json:49`.** The
spec's WS-D asks for the classify-headless call to run "bounded (30 s + 3 s grace, inside its
own budget)" — a 33-second internal bound sitting inside a hook whose *entire process* is
killed by the harness at 10 seconds. This is not a hypothetical interaction; it is read
directly off two files that must both be true simultaneously for WS-D to work as described.

## 5. Regression Surface

1. **The `UserPromptSubmit` hook timeout is the single biggest regression risk in this
   spec.** `hooks/hooks.json:49` registers `triage-prompt-nudge.sh` at `"timeout": 10`
   (seconds). WS-D adds a `--classify-headless` call bounded at "30 s + 3 s grace" *inside*
   that same 10-second envelope, on top of the hook's existing overhead (early-exit gates,
   the records scan, the `resume --open-jobs` query, and a full `localize()` pass that can
   itself spend up to `SEARCH_TIMEOUT_S=8` seconds *per token* across up to `MAX_TOKENS=6`
   tokens sequentially in the worst case — `compound-v-localize.py:96-98`). **If the hook's
   registered timeout is not raised as part of this change, the practical effect of WS-D is
   not "the hook no longer degrades to a reminder" but "the hook now degrades to nothing at
   all" on any `needs_t3` prompt that takes the classify path** — today's contract is an
   *unconditional* reminder in that branch (§3c); a harness-level kill produces **no**
   `additionalContext`, and the doc's own stated fail-open direction
   ("degrading from 'sized for you' to 'please size it' is the right direction; the wrong
   one is a hook that says nothing") is exactly the wrong direction this creates if the
   external timeout is left at 10. This is a regression against the hook's own documented
   contract, not merely against the feature's aspiration, and the spec text does not mention
   `hooks.json`'s timeout value at all.
2. **Every existing `triage.tier` reader that treats `tier` as a closed 3-value enum keeps
   working unmodified** — `flavor` is deliberately additive (spec: "No new tier token"), and
   `DECISION_TO_TIER` (`compound-v-preeval.py:151-155`) is untouched by this spec. Confirmed
   safe: nothing currently branches on the *presence* of an unrecognised key in the `triage`
   block except `_validate_manifest.py`'s own unknown-key rejection loop
   (`:1985-1990`, walks `TRIAGE_REQUIRED_KEYS` — see §7, this is also where `flavor` must be
   threaded through as *allowed-but-not-required* or every legacy manifest without it starts
   failing the "missing required field" check it is not subject to).
3. **`cross_model_review_for()` (`compound-v-preeval.py:174-204`) currently hard-codes
   `DECISION_SCOPED → (False, ...)`.** SCOPED+ is a `flavor` of `DECISION_SCOPED`, not a new
   decision value, so this lookup table — read by whatever currently calls
   `cross_model_review_for` to decide whether a cross-model pass is asked for — will keep
   answering `False` for a `scoped_plus` record unless the plan either (a) makes this
   function flavor-aware (needs a second parameter, since the function's only inputs today
   are `decision_or_tier`), or (b) makes WS-E's `--require-cross-model-receipt` gate entirely
   independent of this function and driven solely by `/v:dispatch` step 8 inspecting
   `manifest.triage.flavor` directly. The spec's WS-E text describes the latter (dispatch
   inspects `flavor` itself), which is consistent with leaving `cross_model_review_for`
   unchanged — but this function's existence and its current `False` answer for SCOPED is a
   real, adjacent thing whose staleness a future reader could reasonably interpret as "SCOPED+
   still says no cross-model review needed" if the plan does not explicitly say why it was
   left alone.
4. **The literal-path fast path in `compound-v-localize.py` (`:410-434`) currently demotes a

## 6. DRY Findings

1. **Three overlapping "is this a test file/path" heuristics after this change** (§3e):
   `is_test_path`/`_TEST_PATH_SEGMENTS` (`compound-v-preeval.py`), the test-noise filter
   (`compound-v-fastpath-run.py`), and WS-C's new `referencing_tests` test-directory set. The
   first two serve genuinely different questions (predicate-6 "is this itself a test" vs.
   "is this bookkeeping noise to exclude from a diff"), so collapsing them is out of scope —
   but the **third is a near-duplicate of the first** and the plan should either (a) have
   `referencing_tests` import/reuse `is_test_path`'s directory-segment list rather than
   restating a slightly different one inline, or (b) if the sets must differ (WS-C's spec
   text does list `specs/` as its own segment where `_TEST_PATH_SEGMENTS` already has both
   `spec` and `specs`), say explicitly why, rather than let two similar-looking constants
   silently diverge in one file update and not the other.
2. **Two different "spawn one external CLI, parse a strict enum, fail-closed" implementations
   after WS-D**: `classify_via_codex` (existing) and the new `--classify-headless` claude
   route. They already share `build_prompt`/`parse_category`/the supervisor pattern; the only
   genuinely new code should be the `claude -p` argv assembly and its own thin
   result-wrapper (today's `_result()` hardcodes `backend: "codex"` — see §3a — so it cannot
   be reused verbatim; it needs a `backend=` parameter or a sibling function, not a full
   duplicate of `classify_via_codex`'s ~50-line body). The DRY risk here is copy-pasting the
   whole function instead of extracting the ~15 lines that are genuinely codex-specific
   (`build_codex_command`'s `--sandbox`/`network_access` flags) from the ~35 that are not
   (supervisor wiring, exit-code triage, file read, `parse_category` call).
3. **The manifest validator already has an established "REQUIRED vs ALLOWED key list" pattern
   to reuse, and A6/WS-E's `flavor` key must follow it, not the `TRIAGE_REQUIRED_KEYS`
   pattern it would naively be added to.** `compound-v-validate-manifest.py` already
   distinguishes a `TEST_CONTRACT_ALLOWED_KEYS` (optional-key) list from required-field
   checks elsewhere in the same file. `TRIAGE_REQUIRED_KEYS` (`:806`) is walked **both** to
   check missing required fields **and**, unmodified, to reject any key not in it
   (`:1985-1990`, "unknown key" check). Naively appending `"flavor"` to
   `TRIAGE_REQUIRED_KEYS` would make it **required on every manifest**, breaking every
   existing DIRECT/FULL manifest with no `flavor` key. The correct move — mirroring the
   `test_contract` precedent already in this file — is a **new** `TRIAGE_ALLOWED_KEYS =
   TRIAGE_REQUIRED_KEYS + ("flavor",)` used only by the unknown-key loop, leaving
   `TRIAGE_REQUIRED_KEYS` itself untouched for the missing-field loop. This is not a
   hypothetical DRY nicety; get it wrong and every existing SCOPED/FULL manifest in this
   repo's own `docs/superpowers/execution/**` history fails `--require-triage` retroactively.
4. **`schemas/plan-review.schema.json` is `"additionalProperties": false` and cannot host
   WS-E's three extra binding fields (`run_id`, `pre_eval_id`, `diff_digest`) directly.** The
   spec's literal wording ("valid against `schemas/plan-review.schema.json` plus `run_id`,
   `pre_eval_id` and `diff_digest`... equal to the run's") is not directly implementable as
   one flat document against that schema — `additionalProperties: false`
   (`schemas/plan-review.schema.json:7`) rejects any key outside `verdict`/`summary`/
   `findings`/`blind_spots_checked`. **This repository already has the correct precedent
   one file over**: `schemas/fastpath-review-receipt.schema.json` is exactly this shape —
   a flat, `additionalProperties: false` schema that bakes binding fields (`run_id`,
   `pre_eval_id`, `manifest_digest`, `baseline_sha`, `final_diff_digest`, `attempt_id`, plus
   a review verdict and a self-digest) into **its own** schema rather than trying to be
   simultaneously valid against a narrower, unrelated schema. `compound-v-codex-review.sh`
   confirms this independently: it passes `plan-review.schema.json` to `codex exec
   --output-schema`, so codex's structured stdout **is already, by construction, the bare
   `plan-review` shape with no binding fields** — the binding has to be added by the
   *caller* (`/v:dispatch` step 8) wrapping that output, not by codex emitting a
   schema-violating document. The plan should follow the `fastpath-review-receipt.schema.json`
   pattern: a **new** schema (e.g. `cross-model-receipt.schema.json`) that is its own flat,
   fully-specified document, not a literal re-use of `plan-review.schema.json`'s validator
   against a superset payload.

## 7. Design constraints for the spec

Non-negotiable; each traces to a finding above.

1. **`hooks/hooks.json`'s `UserPromptSubmit` registration (`"timeout": 10`) MUST be revisited
   in the same change that adds the `--classify-headless` call**, or WS-D's stated goal ("the
   hook no longer has to degrade to a reminder on `needs_t3`") inverts into "the hook now
   silently produces nothing on `needs_t3`" whenever the classify call runs anywhere near its
   stated 30 s+3 s-grace budget. This is the single highest-severity finding in this audit
   (§5.1); the plan must state the new timeout value and reconcile it with the file's own
   documented principle that the hook "must never be the reason a turn stalls."
2. **`score()`'s T3-request logic needs a third branch, not a parameter tweak.** A2's
   demotion is reachable only from a state (`difficulty_band` already real, non-None) that
   today's code never asks T3 about unprompted. The new branch must sit **before** the
   existing override-#4 `elif` (`compound-v-preeval.py:568`) and must retain, not discard,
   each `match_path()` row per resolved path so "every T1 row is broad" is answerable (today
   the two-generator-expression T1 computation throws the row list away — §1a/§2).
3. **`_content_raises_impact`'s `_IMPACT_RAISING_FLAGS` frozenset MUST gain
   `"content_scan_incomplete"` explicitly** (`compound-v-preeval.py:241`) — the function's
   existing `startswith("content:")` branch will not catch this flag by accident.
4. **The Layer-B DIRECT predicate block MUST gain an explicit `confidence != "new_file"`
   guard** (`compound-v-preeval.py:599-605`) — nothing today stops a `new_file` localization
   with `fan_out=1` from reaching DIRECT once T1 bands it low/low from a directory-level glob
   match (glob matching does not require the file to exist).
5. **`NEVER_DEMOTE_GLOBS` needs a concrete home and matching mechanism**, evaluated *before*
   A3's SCOPED+ conditional override #2 branch runs, so `.pem/.key/.env`/`.github/**` always
   fall through to plain FULL regardless of T3 category or fan_out. The taxonomy module
   already has one precedent for a code-level (not YAML-level) hard floor —
   `MANDATORY_SENSITIVE` in `compound-v-taxonomy.py:173-176` — but that floor governs
   auto-route *eligibility* (`match_auto_route`), a different call path from override #2's
   sensitivity check (`match_path`). The plan must decide explicitly whether
   `NEVER_DEMOTE_GLOBS` lives beside `MANDATORY_SENSITIVE` in `compound-v-taxonomy.py` (reuse
   the existing glob-floor pattern) or as a new constant in `compound-v-preeval.py` (the
   spec's own words: "a hard list in the engine") — and if the latter, name why it doesn't
   reuse the taxonomy module's existing analogous mechanism.
6. **`fan_out ≤ 2` (A2, A3) is a new, hardcoded literal, distinct from the existing
   config-driven `fan_out_threshold` (default 1, `pre_eval.fan_out_threshold`) that already
   gates DIRECT eligibility.** `score()`'s signature already has a `fan_out_threshold`
   parameter (`compound-v-preeval.py:424-426`) wired from project config
   (`run_preeval:1037`); the demotion/SCOPED+ threshold of 2 is a **separate** number the
   spec hardcodes rather than deriving from that existing parameter. The plan must say
   whether "2" is a new engine constant (like `ADVISOR_HOT_THRESHOLD`, `:929`) or should
   itself be config-driven, and must not silently reuse the variable name
   `fan_out_threshold` for two different numbers.
7. **`compound-v-validate-manifest.py`'s `flavor` key MUST be added via a new
   `TRIAGE_ALLOWED_KEYS` (required-plus-optional) list consumed only by the unknown-key
   rejection loop (`:1985-1990`), never by appending to `TRIAGE_REQUIRED_KEYS` (`:806`)
   itself** — the latter would retroactively fail every existing manifest in this
   repository's own execution history under `--require-triage` (§6.3).
8. **The `flavor` present ⇒ `tier == "SCOPED"` conditional must be validated explicitly** —
   there is no existing "if key X present then field Y must equal Z" pattern in the triage
   block validator to extend (`_validate_triage`, `compound-v-preeval.py:1937-2002`, has no
   analog); it must be added as new logic, and it must compare against the manifest's
   **tier string** (`"SCOPED"`), not the engine's decision constant
   (`DECISION_SCOPED`) — those are different vocabularies on either side of
   `DECISION_TO_TIER` (§1a).
9. **`--require-cross-model-receipt`'s validation target CANNOT be "valid against
   `schemas/plan-review.schema.json` plus three extra fields" as literally stated** — that
   schema is `additionalProperties: false` (§6.4). The plan must define a new, self-contained
   schema (following the `fastpath-review-receipt.schema.json` precedent) rather than attempt
   to validate an envelope against a schema that structurally forbids the envelope's own
   binding fields.
10. **`scripts/compound-v-lane-guard*` in A6's sensitive-path list matches no file in this
    repository** (§2, confirmed via `Glob "**/*lane-guard*"`) — the real artifact is
    `hooks/lane-guard.sh`, already covered by the pre-existing `hooks/**` row. The plan must
    either drop this glob or replace it with whatever file was actually intended.
11. **`cross_model_review_for()` (`compound-v-preeval.py:174-204`) is left answering `False`
    for plain `DECISION_SCOPED` regardless of `flavor`.** If WS-E's cross-model gate is driven
    entirely from `/v:dispatch` step 8 reading `manifest.triage.flavor` (which the spec's
    text supports), the plan must say so explicitly rather than leave a reader of this
    function to assume it is flavor-aware when it is not (§5.3).
12. **The literal-path fast-path fix (WS-B amendment 2) changes an existing, explicitly-named
    selftest assertion** (`compound-v-localize.py`'s HIGH-8(c) block) from asserting
    `ambiguous` to (post-fix) needing to assert `exact` + `content_scan_incomplete` — this
    selftest rewrite is not incidental cleanup, it is the direct, required consequence of the
    behaviour change and must land in the same commit (spec's own global constraint,
    confirmed against the literal current assertion text).
13. **`agents/spec-reviewer.md` §3.3's evidence table and `skills/compound-v/execution-manifest.md`
    must both gain the `impacted+referencing` scope value** (§5.6) with an explicit statement
    of what "the tier owes" when the referencing heuristic contributes vs. when it finds
    nothing (floor-only, per WS-C's own "unmapped: referencing tests found none — floor only
    at tier SCOPED" note) — today's table only knows three scope values and gives no guidance
    for a fourth.
14. **`commands/v-dispatch.md` step 9's literal current text ("Write `phase: MERGED` into
    `state.json` **first**") is stale against the finalizer behaviour the `[Unreleased]`
    CHANGELOG entry already describes**, and WS-E's own text commits to fixing it — the plan
    should treat this as a concrete, already-identified pre-existing doc drift to close, not
    rediscover it as a new defect.
15. **`resolve_test_commands` needs a `tier` parameter threaded all the way from
    `resolve_from_manifest`, which already extracts `tier` at line 766 but currently only
    feeds it to `default_scope_for`, never onward to `resolve_test_commands` itself**
    (`:801`, the exact call site that needs the new argument) — this is a one-hop wiring gap,
    not a new concept.
16. **`referencing_tests` has no existing sibling to extend and must reuse
    `compound-v-scope-check.py`'s glob-matching authority for any pattern work it does**,
    per this file's own stated principle against a second, weaker matcher (§3d) — it cannot
    be built as a copy of `_impacted_for`, which matches against a *declared* map, not
    against file *content*.
