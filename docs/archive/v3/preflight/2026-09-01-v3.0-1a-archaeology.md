## 1. Matrix

### 1.1 Dimension: `decision` value × consumer branch shape

The spec's Feature A1 adds a third value (`SCOPED`) to a vocabulary that is a hard two-value enum in five places. Every consumer, and what it does when `SCOPED` arrives:

| # | Consumer | Anchor | Branch shape | Behaviour on `SCOPED` |
|---|---|---|---|---|
| 1 | Scorer's own Layer-B gate | `scripts/compound-v-preeval.py:448` | `DECISION_FASTPATH if eligible else DECISION_FULL` | The producer. Must be rewritten to a 3×3 matrix. |
| 2 | Record JSON Schema | `schemas/pre-eval-record.schema.json:84` | `"enum": ["FASTPATH_ELIGIBLE", "FULL_PIPELINE"]` | **HARD FAIL.** Every SCOPED record fails schema validation. |
| 3 | Fast-path materializer | `scripts/compound-v-fastpath-materialize.py:304-306` | `if record["decision"] != DECISION_FASTPATH: raise` | Fails closed. SCOPED refused, with a message that says "not fast-path eligible" — correct outcome, misleading text. |
| 4 | Manifest validator, fast_path binding | `scripts/compound-v-validate-manifest.py:1450-1453` | `if str(rec.get("decision")) != "FASTPATH_ELIGIBLE": problems.append(...)` | Fails closed. Only reached on a `fast_path` manifest. |
| 5 | Tier-2 cohort split | `scripts/compound-v-triage-outcomes.py:733-734` | `is_fastpath = decision == FASTPATH_DECISION and not _is_escalation_child(slot)` | **SILENT MISROUTE.** A SCOPED run lands in the `fullpipeline` cohort. See §2.1. |
| 6 | `/v:orchestrate` Step 0 | `commands/v-orchestrate.md:13,18` | prose: "decision is `FASTPATH_ELIGIBLE`" → fast-path branch, else the plan flow | Falls through to the plan flow. Under-specified, not wrong. |
| 7 | `/v:status` step 7 | `commands/v-status.md:57` | prose: shows `decision` (`FASTPATH_ELIGIBLE` \| `FULL_PIPELINE`) | Renders an undocumented value. Cosmetic. |
| 8 | `compound-v-postdiff-reclassify.py` | — | **Does not read `decision` at all.** It returns `{"escalate": bool, "reasons": [...]}` (`:18`) and is invoked with a diff, not a record. | No impact. The dispatcher brief listed it as a consumer; it is not one. |
| 9 | `compound-v-fastpath-run.py` | — | **Does not read `decision` at all.** Only `:69` mentions "decision" in an unrelated sentence about merge authority. | No impact. Also not a consumer. |

**Direct answer to the brief's question — "would SCOPED silently misroute into the FULL branch, or worse into the fast path?"** No consumer routes SCOPED into the *fast path*: rows 3 and 4 are `!= FASTPATH` guards and fail closed. Rows 5, 6, 7 are `== FASTPATH ? A : B` binaries that silently absorb SCOPED into the **FULL/non-fastpath** arm. Row 5 is the only one where that silence has consequence (a corrupted calibration cohort). Row 2 is the hard stop that makes SCOPED unemittable until the schema is amended.

**Finding (design-time bug).** Override #4 at `:424-426` returns `diff=difficulty_band or "unknown"`, `imp=impact_band or "unknown"` — real, possibly-`low` bands beside `override_fired=4`. That is an auto-route granted on a record whose own audit trail says a hard override fired. The 3×3 lookup must be applied **only** at `:442-450`, after every `return` above, never as a post-hoc re-read of the verdict dict.

## 2. Shared State

### 2.1 `decision` — the Tier-2 cohort variable

```
scripts/compound-v-triage-outcomes.py:103   FASTPATH_DECISION = "FASTPATH_ELIGIBLE"
scripts/compound-v-triage-outcomes.py:733     decision = pred.get("decision") if isinstance(pred, dict) else None
scripts/compound-v-triage-outcomes.py:734     is_fastpath = decision == FASTPATH_DECISION and not _is_escalation_child(slot)
```

- **Set by:** `append_predicted(..., decision=...)` at `:209-231`, called by the scorer's end-to-end path.
- **Read by:** `_cohorts()` (`:704-745`) → the `fastpath` / `fullpipeline` split → `tier2_lookup` → `min_sample_status` → back into `score()` as the Tier-2 health signal (`compound-v-preeval.py:387-391`).
- **Gap:** `SCOPED` is neither. It falls into `fullpipeline` — the cohort whose docstring at `:711-713` says it means *"declined/missing predicted → fail-closed, or an escalation child"*. AC-6 ("`triage-outcomes.jsonl` receives a `predicted` event per decision") will therefore start writing SCOPED predictions into a cohort that means something else. Fast-path precision (`/v:status`, `state-machine.md` "Unbound pre-eval discovery") is computed off this split and would be silently diluted by a tier that is not the fast path.
- **Not a crash — a measurement corruption.** The spec's own justification for A5 is "turns the invisible bypass into a measurable one." It measures it into the wrong bucket.

### 2.2 `override_fired` — schema doc vs. emitted range

```
schemas/pre-eval-record.schema.json:79-81
  "override_fired": { "type": ["integer","null"],
     "description": "The Layer-A hard-override row id (1-6, spec §2) that forced FULL_PIPELINE…" }

- **Latent doc/code drift, pre-existing.** The scorer emits `override_fired=7` (advisor-hot, added in v2.12); the schema description still says `1-6`. Flagged because A1/A4 will re-read this field: A4 predicate 3 ("never on a fail-closed `unknown` band") and the validator's fast-path override gate (`compound-v-validate-manifest.py:1481-1484`) both key on `override_fired`, and anyone implementing against the schema description will build a `1..6` check that misses `7`.

### 2.5 Session identity — what a `Stop` hook actually receives

Verified from the only Stop hook that exists anywhere in this repo's history (`v2.18-autonomy:hooks/epic-goal-stop.sh`, `hook_main`):

| Field | Present | Anchor |
|---|---|---|
| `hook_event_name` | yes | `jq -r '.hook_event_name // empty'` |
| `session_id` | yes | `jq -r '.session_id // empty'` |
| `stop_hook_active` | yes | `jq -r 'if .stop_hook_active == true …'` |
| `cwd` | yes | `jq -r '.cwd // empty'` |

- **The hook has a `session_id`. The pre-eval record has nowhere to put one.** `schemas/pre-eval-record.schema.json:7` is `"additionalProperties": false`, and its `required`/`properties` list (`:8-21`, `:33-...`) contains `pre_eval_id, run_id, request_slug, ts, status, taxonomy_version, taxonomy_ref, taxonomy_digest, difficulty, impact, tiers_signalled, localization, override_fired, decision, min_sample_status, confidence, digest` — **no session field, and none can be added without amending the schema.**

## 3. Sibling Code

### 3.1 Sibling: `hooks/epic-goal-stop.sh` `_enforcement_rule` (branch `v2.18-autonomy`) — Feature C is a near-duplicate of it

**This is the headline finding of the audit.** Feature C describes a hook that already exists, in full, unmerged.

| Feature C requirement (spec §C) | `_enforcement_rule` on `v2.18-autonomy` |
|---|---|
| fires when tracked non-doc source changed | `git diff --name-only HEAD` ∪ `git ls-files --others --exclude-standard`, then `grep -v '^docs/superpowers/'` |
| passes when a triage/run record exists | `grep -E '^docs/superpowers/(execution/[^/]+/state\.json\|pre-eval/.+)$'` → return |
| blocks once with `{"decision":"block","reason":…}` | `jq -n … '{decision:"block", reason:$reason, systemMessage:$msg}'` |
| OFF by default, keyed in `.claude/compound-v.json` | `jq -r '.enforcement.pipeline_bypass // false'`, default `false` |
| blocks at most once per session | temp-dir marker `enforce-<sha256(proj\|sid)>`, set **before** emitting |
| registered `… \|\| true` | `hooks/hooks.json` `"…/epic-goal-stop.sh" \|\| true` |
| unconditional `trap 'exit 0' EXIT` | line 1 of the executable body |
| its `reason` names the sanctioned shortcut | names the Stage −1 Pre-Evaluation fast-path, asserted by `tests/test-epic-goal-stop.sh` |

The only genuine deltas Feature C adds are (a) the config key name (`triage_gate` vs `pipeline_bypass`), (b) a DIRECT-auto-route-class exemption, and (c) a session opt-out. **Writing `hooks/triage-stop.sh` from scratch is a third implementation of a two-implementation problem.**

**Entry conditions of the sibling** (`hook_main`, evaluated in order): `jq` present → non-empty stdin → `hook_event_name == "Stop"` (the SubagentStop gate, without which every Compound V subagent trips it) → non-empty `session_id` → resolvable `cwd` → nearest `.git` ancestor (≤40 levels).

**Edge cases the sibling handles that the spec does not mention:**
1. `set -e`/`set -u` are **deliberately absent** — the header states `|| true` around a function call does not save you from `set -u`. Every existing hook in `hooks/` (`plan-saved-nudge.sh:16`, `session-banner.sh:12`) uses `set -euo pipefail`. **A new Stop hook copying the established `hooks/` idiom would be wrong and would wedge sessions.**
2. `stop_hook_active` is read and logged but **never returned on** — returning on it caps the feature at exactly one block while a synthetic-stdin selftest still passes.
3. `docs/superpowers/**` is excluded from "source", so arming/recording does not self-trigger.
4. The store dir is excluded when `TMPDIR` happens to sit inside the worktree.
5. Marker written **before** emitting: "a correction we could not bound stays silent."

**Latent-bug flag on the sibling — the `|| true` claim in the spec is false at HEAD.** Feature C says the fail-open contract is *"already documented in `hooks/hooks.json`"*. On this branch, `hooks/hooks.json` has **no `Stop` key at all** and no `$comment_stop`. That documentation exists only at `v2.18-autonomy:hooks/hooks.json` (`"$comment_stop"`). **Recon amendment:** the recon did not cover this; the spec's premise is branch-conditional.

**Do two `Stop` hooks compose?** Mechanically, yes — `"Stop": [ { "hooks": [ … ] } ]` accepts multiple entries and each hook process owns its own stdout, so `tests/test-epic-goal-stop.sh`'s `json_docs "$OUT" == 1` assertion (line 429) is not broken by a second registration. **Semantically, no.** v2.18 put the goal rule and the enforcement rule in ONE script specifically to enforce precedence, with the header stating *"two blocks on one event is undefined behaviour"* and test §13 asserting *"exactly ONE JSON response when both rules are eligible"* plus *"exactly ONE state update."* Two independent registrations have no shared marker and no precedence: on a turn where an epic goal is unmet **and** source changed with no triage record, both fire and two `decision:block` documents reach the runtime. Feature C's "two registrations, each independently fail-open" preserves fail-open but discards the precedence invariant v2.18 paid for.

**Two more assertions in the sibling's test a second registration must satisfy:**
- line 445: `jq -e '[.hooks.Stop[]? | has("matcher")] | any | not'` — **no** `Stop` group may carry a `matcher`.
- lines 439-443: the `epic-goal-stop` command string must still be discoverable and still carry `|| true`.

### 3.2 Sibling: `run_test_floor` — Feature B's floor already exists

```
scripts/compound-v-fastpath-run.py:308-343

**Entry condition:** called by `parallel-dispatcher.md:240` Step 2e-1, fast-path runs only.

### 3.3 Sibling: `fast_path` review declaration — Feature A's SCOPED tier already exists in shape

The spec's SCOPED tier is *"a manifest and a run directory, the scope gate and the floor, and a **single combined** SPEC+QUALITY review pass. Recon and the three pre-flights are skipped."* That is, field for field, the shipped fast-path run:

- combined review as a dispatcher phase outside `jobs`: `execution-manifest.md:165`, materialized at `compound-v-fastpath-materialize.py:446`.
- pre-flights skipped as **block-YAML skip-records**, validated at `compound-v-validate-manifest.py:1372-1391` (`{skipped: true, reason, localization, taxonomy_version}`; flow-`{}` rejected because the no-PyYAML fallback drops flow mappings).
- the authoritative fast-path tail: `parallel-dispatcher.md:228-266`.

**Design consequence:** SCOPED is not a new pipeline. It is the fast-path pipeline with a relaxed eligibility gate. Building it as a parallel third path duplicates the receipt/attempt/escalation machinery in `compound-v-fastpath-run.py` (1493 lines) and `compound-v-validate-manifest.py`'s `--mode post-review` receipt gate.

### 3.4 Sibling: the Engine-A dispatch tail — what Feature D's three-stage pipeline must replace

`agents/parallel-dispatcher.md` is not a fan-out loop. Its steps: Step 0 materialize · Step 1 Task 0 serial · Step 2 parallel batches · **Step 2b** scope gate + `state.json` after every job · **Step 2c** backend-failure classify→decide→act with per-`(job, class)` retry counters and cooldowns · **Step 2d** liveness sweep for parked jobs · **Step 2e** fast-path tail · Step 3 reviewer batches · Step 4 per-task fix loops · Step 5 final integration review · Step 6 post-run memory · Step 7 advance to `MERGED` and commit the run substrate.

Feature D1's `pipeline(jobs, implement, gate, record)` covers Step 2, 2b and part of 7. **Steps 2c, 2d, 2e, 3, 4, 5, 6 have no stage in the proposed pipeline and no stated home.** Step 2c in particular is the retry/backoff engine; a Workflow whose resume "re-runs every agent that started after a failed one, including completed ones" (recon fact, `workflows-accelerator.md:67-69` corroborating) has no place to put a per-class attempt counter.

**What in the current path assumes a subagent:** nothing structural. `agents/parallel-dispatcher.md` *is* a subagent (frontmatter `model: opus`) and it spawns further agents — `skills/backend-launcher/adapter-claude.md:13-36` maps `job_spec` → one nested subagent call with `run_in_background` and a `model` override. The dependency is the other way round: **the Workflow tool is what is missing from a subagent** (live-probed above), not the spawn tool. So the seam is a *capability* boundary, not an architectural one.

## 5. Regression Surface

Ordered by blast radius. Each line: what breaks for whom.

1. **`compound-v-validate-manifest.py` requiring `triage` → CI red for the whole repo.** `.github/workflows/validate.yml:120-133` runs the validator over `examples/manifest.example.yaml` (`:126`) and then loops `for m in docs/superpowers/execution/*/manifest.yaml` (`:130`). **11 files fail immediately** (10 committed run manifests + the example), and the step is `set -e`. A compatible rollout must reuse that precedent: an allowlist of pre-3.0 run-ids, or a `manifest_version` discriminator, never a back-fill.
   Exact failing set: `docs/superpowers/execution/{2026-06-30-v-onboard, 2026-07-01-v2.4.0-stance-aware-models, 2026-07-10-research-grounded-brainstorm, 2026-07-11-session-aware-workers, 2026-07-11-v2-8-hardening, 2026-07-11-v2.9-pre-evaluation, 2026-07-13-usage-and-advisor, 2026-07-14-v2.14-blockers-and-headless, 2026-07-15-v2.16-decision-preferences, 2026-07-25-v2.17-cochange}/manifest.yaml` + `examples/manifest.example.yaml`. ## 6. DRY Findings

### 6.1 Feature C ≈ `_enforcement_rule` on `v2.18-autonomy` — **do not write a third hook**

Full mapping in §3.1. **Decision: EXTEND the existing hook, do not add a second registration.** Add the DIRECT-class exemption and the session opt-out as additional conditions inside `_enforcement_rule`, and rename the config key or accept both. This preserves v2.18's single-response precedence invariant, its marker, its test file, and its SubagentStop event gate — the last of which is not optional: without it, every subagent Compound V dispatches shares the session id and trips the hook.
*If a separate script is chosen anyway, the justification must state explicitly how two simultaneous `decision:block` documents on one `Stop` event are resolved, because v2.18's own header calls that undefined behaviour.*

### 6.2 Feature B's floor ≈ `run_test_floor` — **extend, do not re-implement**

`compound-v-fastpath-run.py:308-343` already is a merge-blocking, command-and-exit-code-recording, empty-command-fail-closed test floor with a three-tier fallback ladder. Feature B's `floor_command` is its tier-1 `test_cmd`, and its "`floor_only` never resolves to nothing" is its tiers 2-3. **Decision: give `test_cmd` the producer it has never had** (a `test_contract.floor_command` manifest field feeding `--test-cmd`), fix the `:343` early return so the diff-proportionate tiers still run, and lift the whole ladder out of the fast-path-only call site at `parallel-dispatcher.md:240`. Writing a second floor leaves two floors, one of which (the shipped one) still has no caller for its tier-1.

### 6.3 Engine naming collides head-on with the shipped Engine A/B/C vocabulary
