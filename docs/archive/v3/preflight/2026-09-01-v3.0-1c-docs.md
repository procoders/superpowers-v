## 3. API Signatures Verified

Recovered verbatim from the `RunWorkflow` tool description embedded in Claude Code `2.1.238` — `BINARY`.

### Script body API

```
agent(prompt: string, opts?: {label?: string, phase?: string, schema?: object,
      model?: string, effort?: string, isolation?: 'worktree', agentType?: string}): Promise<any>

pipeline(items, stage1, stage2, ...): Promise<any[]>
parallel(thunks: Array<() => Promise<any>>): Promise<any[]>
log(message: string): void
phase(title: string): void
args: any
budget: {total: number|null, spent(): number, remaining(): number}
workflow(nameOrRef: string | {scriptPath: string}, args?: any): Promise<any>
```

| Element | Verified semantics (`BINARY`, verbatim where quoted) |
|---|---|
| `pipeline` stages | **"Every stage callback receives `(prevResult, originalItem, index)`"** — the spec's D1 signature is **exactly right**. Also: "run each item through all stages independently, **NO barrier between stages**". |
| `pipeline` failure | **"A stage that throws drops that item to `null` and skips its remaining stages."** ← see 🟠-2 |
| `parallel` | Barrier. "A thunk that throws (or whose agent errors) resolves to `null` … the call itself never rejects". Runtime error strings enforce the shape: `"parallel() expects an array of functions, not promises. Wrap each call: () => agent(...)"` |
| `agent` return | Without `schema`, final text as string. With `schema` (JSON Schema), "the subagent is forced to call a StructuredOutput tool and `agent()` returns the validated object". Returns `null` if skipped or terminally errored. |
| `opts.effort` | `'low' \| 'medium' \| 'high' \| 'xhigh' \| 'max'` |
| `opts.isolation` | Only `'worktree'` in this build. `agent({isolation:'remote'}) is not available in this build`. |
| `opts.agentType` | **"resolved from the same registry as the Agent tool; composes with schema"** ← green light for reaching `compound-v:spec-reviewer` |
| `opts.phase` | "use this inside `pipeline()`/`parallel()` stages to avoid **races on the global `phase()` state**" — D2's emitter must set `opts.phase` per agent, not rely on `phase()`. |
| `budget` | "The target is a **HARD ceiling, not advisory**: once `spent()` reaches `total`, further `agent()` calls **throw**." `total` is `null` unless the user set a `+500k`-style directive. |
| `workflow()` | Nested workflow, **"Nesting is one level only: `workflow()` inside a child throws."** |
| Determinism | **"`Date.now()`/`Math.random()`/argless `new Date()` … throw (they would break resume)"** |
| Script language | "plain JavaScript, NOT TypeScript". No `import()`. **"No filesystem or Node.js API access."** |

`script` · `name` · `scriptPath` · `args` · `resumeFromRunId` (`^wf_[a-z0-9-]{6,}$`) · `remote`

> "**Path to a workflow script file on disk.** … Takes precedence over `script` and `name`." — `BINARY`

## 4. Critical Findings 🔴

### 🔴-1 · Feature D3's headless justification is **false**. `-p` and the SDK *can* launch workflows.

The spec (D3) and recon claim (h) both state launch "is deliberately not honored from `-p`, SDK, scheduled or
webhook routes." The doc says this of the **`ultracode` keyword**, not of workflow launch:

> "The keyword is an opt-in only in a prompt you type yourself … It doesn't start a workflow when it reaches
> the session another way: a prompt passed with `-p`; a prompt an Agent SDK application sends without stamping
> it as human input; a scheduled task prompt; a webhook payload…" — `FETCHED`

Two paragraphs later the same page says the opposite of the spec's generalisation:

> "Workflows are available in the CLI, the Desktop app, the IDE extensions, **non-interactive mode with
> `claude -p`, and the Agent SDK**." … "In `claude -p` and the Agent SDK, Claude Code never shows this prompt.
> It runs the Workflow tool call through the same permission evaluation as the rest of the session… **To let
> the workflow start in these runs, use one of these: Permission rule: `Workflow` in your allow rules … Auto
> permission mode … Bypass permissions mode … A `PreToolUse` hook … `--permission-prompt-tool`.**" — `FETCHED`

**Impact.** AC-12 requires `/v:dispatch` to "select Engine A in a subagent, headless, scheduled and `/v:epic`
context" — the *behaviour* may still be what we want, but the stated reason is wrong, and a reviewer checking
the premise will find it refuted. Worse, "Engine B is impossible headless" is exactly the kind of false
constraint that gets re-litigated later. Decide Engine A for headless on **operational** grounds (no
cross-session resume, no `state.json` authority, allow-rule dependency) and say so.

**Constraint:** the spec must not assert that `-p`/SDK cannot launch a workflow.

### 🔴-2 · A throwing Gate stage destroys the audit record — on the failure path only

D1's three-stage `pipeline(jobs, implement, scopeGate, record)` inherits:

> "A stage that throws drops that item to `null` and **skips its remaining stages**." — `BINARY`

If the Gate stage throws — `agent()` returning `null` on a terminal API error, a schema-validation failure, or
`budget` exhaustion (which throws, see 🟡-1) — the **Record** stage never runs for that job. No `state.json`
entry is committed, and the job silently becomes `null` in the results array. That is the v2.6.4 audit-trail
data-loss failure mode reappearing structurally, and it is worst exactly where it matters: on the jobs that
went wrong.

Note this is not the BLOCKED case. A BLOCKED verdict *returned* as a value is fine and flows to Record. The
hazard is an **exception**, which is indistinguishable from a clean run at the pipeline level.

**Constraint:** the Gate stage MUST NOT be able to throw. Wrap it so every outcome — PASS, BLOCKED, and
"gate itself failed" — is a returned `GATE_VERDICT` value. The Record stage MUST treat a `null` prevResult as
a recordable terminal state, not as a skip. AC-11 must test the throwing-gate case.

### 🔴-3 · The `stop_hook_active` mechanism in Feature C is wrong, and there is an undocumented block cap

The spec states: *"Blocks at most once per session. `stop_hook_active` is never cleared once set, so a hook
that blocks unconditionally is a trap."*

The conclusion (self-limit your blocks) is right. The stated mechanism is not, and the real one is stricter:

```js
// BINARY, verbatim from 2.1.238
let $o = V.CLAUDE_CODE_STOP_HOOK_BLOCK_CAP ?? 8;
if ($o > 0 && Ms > $o) return N("tengu_stop_hook_block_count", {count: Ms, …, hit_cap: true}),
  yield Cs(`A hook blocked the turn from ending ${Ms} consecutive times — overriding and ending turn. `
    + "For Stop/SubagentStop hooks, check stop_hook_active in the input and return success while it's true. "
    + "Set CLAUDE_CODE_STOP_HOOK_BLOCK_CAP to raise this limit.", "warning"), {reason: "completed"};
```

- **There IS a documented-in-product cap: `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`, default `8`.** Claude Code
  overrides the hook and ends the turn on the 9th **consecutive** block. It does not appear on the public
  hooks page.
- The counter (`Ms`) is **consecutive, not per-session**: the surrounding control flow resets it whenever a
  Stop pass returns no blocking errors (`if(_e>0 && ia.blockingErrors.length===0)` closes the run). So
  `stop_hook_active` tracks *"has a Stop hook blocked in this continuation run"*, not *"ever, this session"*.
- The product's own guidance is exactly the spec's intent, and should be quoted in the hook: *"check
  `stop_hook_active` in the input and return success while it's true."*

**The genuinely valuable part:** the spec says Feature C "needs to know 'does a triage record exist for THIS
session' and currently has no stated mechanism." **`session_id` is on the Stop hook's stdin payload**
(`BINARY`, zod base schema). That is the mechanism — key the triage record by `session_id`. Also available:
`transcript_path`, `cwd`, `permission_mode`, and `last_assistant_message`.

**Constraint:** Feature C's once-per-session guarantee must be enforced by a **session-keyed marker file**
(from `session_id`), not by assuming `stop_hook_active` persists. The hook must additionally return success
whenever `stop_hook_active` is true.

### 🔴-4 · Feature C cites a fail-open contract that does not exist

The spec: *"Registered as `"…/triage-stop.sh" || true` with an unconditional `trap 'exit 0' EXIT` inside — the
same two-part fail-open contract **already documented in `hooks/hooks.json`**."*

`hooks/hooks.json` at HEAD contains **no `|| true` anywhere**, registers **no Stop hook**, and its `$comment`
explicitly says the opposite of a live blocking contract:

> "Compound V currently emits `additionalContext` ONLY — **zero blocking enforcement at the harness level**.
> Restoring a blocking Stop hook is v2.18 work." — repo, `hooks/hooks.json:2`

All four current registrations are bare quoted commands. The pattern the spec claims to be following is not
there to follow.

**Constraint:** AC-10 must state that the `|| true` registration convention is **introduced** by this change,
and the ADR/test must establish it rather than cite it. (Whether the `v2.18-autonomy` branch has it is a
Phase 1A question — but it is not on this branch, which is what `hooks/hooks.json` names.)

**Constraint:** the spec MUST state a Claude Code version floor for Feature D. `>= 2.1.219` covers everything
the design uses. Do **not** make the design depend on `/workflow-authoring` — it is unavailable at the
version we are developing on, so it cannot be dogfooded (compare AC-13's dogfooding requirement).

### 🟠-2 · The tool instructs the model *not* to write the script to a file — D2 does exactly that

> "**Pass the script inline via `script` — do not Write it to a file first.** Every invocation automatically
> persists its script to a file under the session directory and returns the path in the tool result. To
> iterate on a workflow, edit that file with Write/Edit and re-invoke Workflow with `{scriptPath: "<path>"}`" — `BINARY`

D2 emits `manifest.yaml` → a script in the run directory, commits it, and runs it. This **works** — `scriptPath`
is a first-class input that "takes precedence over `script` and `name`" — but it is the non-default path the
tool actively steers away from. A launching agent following the tool description will inline the script, and
the committed artefact will then not be the thing that ran, defeating D2's stated purpose ("the exact
orchestration that ran is part of the audit trail").

Also relevant: "Claude can start a workflow only from a script file the session is already allowed to read."
Run directories under `docs/superpowers/execution/` are inside the working directory, so this is satisfied.

**Constraint:** `/v:dispatch`'s Engine-B path MUST launch as `Workflow({scriptPath: <emitted path>})` and MUST
verify the returned script path matches the emitted one. AC-11 should assert the invocation form, not just the
emitted content.

### 🟠-3 · `CLAUDE_CODE_WORKFLOWS` can make Engine B structurally unavailable

> "This session restricts the Workflow tool to named workflows (`CLAUDE_CODE_WORKFLOWS` is set). Not allowed
> here: `script` / `scriptPath` / `resumeFromRunId` / `remote`. **Invoke as `{name, args}` only.**" — `BINARY`

In such a session, D2's generated per-run script cannot launch at all. Two further hard disables exist:
`disableWorkflows` in managed settings, and `CLAUDE_CODE_DISABLE_WORKFLOWS=1`.

**Constraint:** the D3 engine probe MUST treat "workflow tool present" as insufficient. It must fall back to
Engine A on a `script`/`scriptPath` refusal, not fail the run. This is a third failure mode beyond the two the
spec anticipates (subagent, headless).

### 🟠-4 · Recon claim (a) — "a subagent cannot launch a Workflow" — is reproduced but **undocumented**

`PROBE`, from inside this Phase-1C subagent, extending the recon's probe to the real internal tool name:

- `ToolSearch "select:Workflow,RunWorkflow"` → **"No matching deferred tools found"**
- `ToolSearch "workflow orchestrate subagents dynamic script"` → 8 unrelated tools, no workflow tool

So the recon's conclusion holds, and holds for the correct name (the recon probed only `Workflow`; the tool's
internal identifier is `RunWorkflow` — had the gating been name-related, the original probe would have been
invalid). But I found **no documentation and no gating predicate in the binary** stating that subagents are
excluded. The only diagnostic is generic: *"Dynamic workflows are not enabled for this session (org policy,
**launch gate**, or the 'Dynamic workflows' setting in /config)"* — "launch gate" is not further defined
anywhere I could reach.

**Constraint:** D3 may rely on this (two independent probes agree), but the spec must label it
**observed, not contracted** — an undocumented behaviour can change without a release note. The engine probe
must therefore be a *runtime capability check*, never a hardcoded "if subagent then Engine A" assumption.

## 6. Medium Findings 🟡

**🟡-1 · Recon claim (g) "no token spending cap" is half wrong.** A `budget` global is injected, and where the
user set a `+500k`-style target it is a **hard ceiling — exceeding it makes `agent()` throw** (`BINARY`).
Default `budget.total` is `null` (uncapped), so the recon's practical point stands. But combined with 🔴-2, a
budget exhaustion mid-pipeline throws → skips Record → loses the audit trail. The emitter should read
`budget.remaining()` and stop scheduling rather than let it throw.

**🟡-2 · Concurrency is not a flat 16.** `BINARY`: "Concurrent `agent()` calls are capped at
**`min(16, available CPUs - 2)`** per workflow"; the doc adds "fewer when Claude Code has fewer CPUs
available, including inside a CPU-limited container." D2 maps `max_parallel` → chunking; on a 4-CPU CI runner
the effective cap is 2. Chunk size must be advisory, and throughput claims must not assume 16.

**🟡-3 · `.claude/workflows/` is real — but not where D2's artefact belongs.** `FETCHED`: it is the save
location for **named, reusable** workflows (project) alongside `~/.claude/workflows/` (personal), and project
workflows load from every `.claude/workflows/` between cwd and repo root, nearest wins. D2's per-run generated
script is single-use and belongs in the run directory, launched via `scriptPath` — **this does not change the
D2 design.** It does open a separate option the spec never considered: registering a stable
`compound-v-dispatch` *named* workflow taking the manifest path via `args`, which would sidestep 🟠-2 and 🟠-3
entirely. Worth an explicit accept/reject.

**🟡-4 · Recon claims confirmed verbatim.** (b) script has no filesystem or shell access — *"No filesystem or
Node.js API access"* `BINARY`; *"No direct filesystem or shell access from the workflow itself | Agents read,
write, and run commands"* `FETCHED`. (c) **agents spawned by the script have full tools including Bash** —
confirmed by the same doc row, by `opts.isolation:'worktree'` existing for agents that mutate files, by
*"Workflow agents can reach all session-connected MCP tools via ToolSearch"*, and by the internal option keys
`disallowedTools` / `bashCommandClamp` (which only make sense if Bash is on by default). **D1's
scope-gate-as-a-stage design is sound on this axis.** (d) resume same-session-only — confirmed twice.
(e) on relaunch, agents that started after a failed one re-run even if completed — confirmed verbatim, with
the doc's worked A/B/C/D example. (f) caps 16 / 1000 / 4096 — confirmed, with the 🟡-2 nuance.

**🟡-5 · Undocumented `agent()` options exist; do not use them.** The binary's option-validation key list is
`schema model effort isolation agentType disallowedTools bashCommandClamp` — but `disallowedTools` and
`bashCommandClamp` appear in **neither** the public doc nor the tool's own reference text (which documents
`label, phase, schema, model, effort, isolation, agentType`). They are tempting for tightening the scope gate.
`UNVERIFIED` — building on them is building on sand.

**🟡-6 · A `remote` launch mode exists** (`remote_launched`, CCR session URL, "runs against a fresh clone of
the pushed branch", resume handle is the session URL not a run id). Out of scope for 3.0, but it is a third
execution context the D3 table does not enumerate.

**🟡-7 · Multiple `Stop` hooks compose exactly as Feature C hopes.** Control flow (`BINARY`): all matching
hooks run, results are aggregated, and `if (ia.blockingErrors.length > 0)` blocks the turn. **Any one hook
blocking wins over any number exiting 0.** A separate `ia.preventContinuation` path (a hook setting
`continue: false`) force-*ends* the turn with `{reason: "stop_hook_prevented"}` — the inverse power, which the
spec does not mention and should not use. The spec's "composes with, and does not replace, the v2.18 hook"
claim is **TRUE**.

**🟡-8 · `phase()` races inside pipeline stages.** `BINARY` warns to use `opts.phase` "to avoid races on the
global `phase()` state". D2's emitter must stamp `phase` per `agent()` call.

## 7. Design Constraints for the Plan

Non-negotiable, each traced to a finding above.

**MUST**
1. State a Claude Code **version floor of `>= 2.1.219`** for Feature D. (🟠-1)
2. Make the Gate stage **total** — every outcome returned as a `GATE_VERDICT` value; the stage must be
   incapable of throwing. Record must handle a `null` prevResult as a terminal recordable state. (🔴-2)
3. Launch Engine B as **`Workflow({scriptPath})`** and verify the returned script path equals the emitted
   path. (🟠-2)
4. Key Feature C's once-per-session guarantee to **`session_id` from the Stop payload**, via a session-keyed
   marker. (🔴-3)
5. Have `hooks/triage-stop.sh` **return success whenever `stop_hook_active` is true** — the product's own
   guidance, and the only thing standing between a buggy hook and the default 8-block override. (🔴-3)
6. Make the D3 engine probe a **runtime capability check with fall-back to Engine A** on any refusal —
   covering `CLAUDE_CODE_WORKFLOWS`, `disableWorkflows`, `CLAUDE_CODE_DISABLE_WORKFLOWS`, and the subagent
   case. (🟠-3, 🟠-4)
7. Ensure `compound-v-emit-workflow.py` emits **no `Date.now()`, `Math.random()`, or argless `new Date()`**,
   no TypeScript annotations, and no `import()`. Timestamps (incl. `triage.decided_at`) must arrive via `args`
   or be stamped after the workflow returns. (§3 determinism)
8. Set **`opts.phase` on every emitted `agent()` call**; never rely on the global `phase()` inside stages. (🟡-8)
9. Emit `meta` as a **pure object literal** with `name` + `description`, and keep `meta.phases[].title`
   exactly equal to the `phase()`/`opts.phase` strings. (`BINARY`)

**MUST NOT**
10. Assert that `-p`/SDK/scheduled routes cannot launch a workflow. Justify Engine A there operationally. (🔴-1)
11. Cite `hooks/hooks.json` as already documenting the `|| true` fail-open contract. It does not. (🔴-4)
12. Claim `stop_hook_active` "is never cleared once set". (🔴-3)
13. Use `disallowedTools` or `bashCommandClamp` as `agent()` options. (🟡-5)
14. Assume 16 concurrent agents when sizing `max_parallel`. (🟡-2)
15. Depend on the `/workflow-authoring` skill (v2.1.248 > local 2.1.238). (🟠-1)
16. Let a `budget` ceiling be hit by an unguarded `agent()` call inside a pipeline. (🟡-1)

## 8. Open Questions for the Human

1. **Named workflow instead of a generated one?** Registering one stable `.claude/workflows/compound-v-dispatch.js`
   that takes the manifest path via `args` would survive `CLAUDE_CODE_WORKFLOWS` restriction, need no
   per-run script approval, and still be committed and auditable — at the cost of D2's "the exact
   orchestration that ran is in the run directory" property. D2 currently assumes the generated-script route
   without recording that the alternative was considered. Which property matters more? (🟡-3)
2. **Does `agentType` resolve plugin-namespaced agents?** The reference gives unprefixed examples
   (`'general-purpose'`, `'code-reviewer'`) and says "resolved from the same registry as the Agent tool". Our
   agents are `compound-v:spec-reviewer`. This is a one-line live probe and it gates whether D1's Gate/Record
   stages can reuse our registered agents or must inline their prompts. **`UNVERIFIED` — probe before
   planning.**
3. **Is Engine B worth it given resume?** Engine B's resume is same-session-only *and* re-runs completed
   agents that started after a failure. For a 16-job dispatch where job 3 fails, jobs 4–16 re-run even though
   they succeeded — paying full token cost twice. Engine A's `state.json` + `/v:resume` does not. Is Engine B
   the inner loop for *all* dispatches, or only for dispatches under some job count?
4. **Version floor vs. the user base.** Setting a `>= 2.1.219` floor makes Feature D silently unavailable to
   anyone on an older Claude Code. Should `/v:dispatch` warn, or fall back to Engine A silently?
