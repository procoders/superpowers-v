## QUALITY

### 2.1 Code quality

`refresh_fts5` is a clean extraction — it is the FTS5 body and nothing else, and its docstring states
the one structural guarantee that matters ("NEVER touches an embedder"). The `if embedder is None:` /
`else:` split in `cmd_refresh` replaced two separate `if embedder is not None` tests scattered through
the old body; the result reads in one pass instead of three. The comment at `:749-755` records *why*
the pre-refresh `changed` list must survive — the single highest-risk fact in the change, written down
at the exact line where a future editor would break it. That is the right place for it.

Two low-severity notes, neither blocking:

- **`cmd_search:980-988` releases the lock without `try`/`finally`**, unlike `cmd_refresh:723-806`
  which wraps its whole body. If `refresh_fts5` raises, `release_lock` never runs. In practice the
  process exits immediately and the OS drops the `flock`, so the blast radius is a leaked fd on a
  dying process — real asymmetry, negligible consequence.
- **The inline refresh hashes the corpus twice.** `index_staleness` (`:945-959`) runs
  `tracked_files()` + `file_sha()` over every tracked doc to decide, then `refresh_fts5` (`:704-708`)
  runs `tracked_files()` + `file_sha()` again to act. Measured on this repo (275 tracked docs):
  `index_staleness` mean **0.091 s** (best 0.070 s) against **0.059 s** (best 0.047 s) for the old
  path-set-only form — so the doubled pass costs roughly another 0.09 s on a search that actually
  refreshes. `cmd_refresh`'s FTS5 path pays the same double-derivation (pre-flight 1A §3.10
  anticipated exactly this). At this corpus size it is noise; at 10× it would not be. Recorded, not
  demanded.

#### AC 3 — a search never embeds, and the ordering hazard does not bite

Three separable claims. The first two by inspection, the third by live probe.

*(a) The inline refresh is structurally FTS5-only.* `refresh_fts5:711` calls
`reindex_file(conn, root, f, None)`; `reindex_file:670-672` sets `vecs = None` whenever
`embedder is None`. `config_wants_embeddings` is never called from `cmd_search` or `refresh_fts5`
(`grep -n embed` over `:968-1002` returns only the two query-side `no_embed`/`dense_search` lines and
two comments). The stderr line says `(FTS5 lane)` unconditionally. ✅

*(b) The `--quick` cap cannot reach the inline path.* The gate lives at `cmd_refresh:745-748`, outside
the extracted helper, and `refresh_fts5` has no `quick` parameter to pass. ✅

*(c) `cmd_refresh --with-embeddings` after a search-triggered refresh still embeds what search
re-chunked.* This is pre-flight 1A's "single highest-risk spot in the whole change" — the failure
mode is silent, permanent, and no existing test would catch it. I probed it directly with a stubbed
embedder (`is_bootstrapped`/`ensure_embedder`/`embed_texts`/`_embedder_src_hash` monkeypatched; a real
git repo; two docs):

```
== 1. refresh --with-embeddings (populate vectors)
V-memory: indexed/updated 2, removed 0, unchanged 0, 2 chunks total (2 with vectors)
   vectors: {'…/a.md': 1, '…/b.md': 1}

== 2. edit b.md, then a SEARCH triggers the inline FTS5-only refresh
   vectors after search: {'…/a.md': 1, '…/b.md': 0}     ← b.md's vector NULLed, exactly as documented

== 3. cmd_refresh --with-embeddings AFTER the search refresh
V-memory: indexed/updated 1, removed 0, unchanged 1, 2 chunks total (2 with vectors)
   vectors after refresh: {'…/a.md': 1, '…/b.md': 1} | embedder calls: [1]
RESULT: PASS — the search-re-chunked file WAS re-embedded
```

The hazard does not bite, and the mechanism is the one pre-flight 1A endorsed as option (b): after
`refresh_fts5` rewrites `content_hash`, `to_index = list(changed)` is indeed empty for `b.md`, but
`b.md`'s chunks carry `embedding IS NULL`, so the `missing` union at `:754-758` picks it up. The
belt-and-braces case also holds: on a project whose *only* refreshes were ever search-triggered,
`embed_model` meta is unset, `identity_matches` reads False, and `to_index` becomes the whole corpus.
Both roads lead to the file being embedded. Step 2 also confirms the documented side effect is real
and temporary, not hypothetical.

*Routing and the conservative bridge untouched:* the diff touches no routing file, and `recall-check`
is not in it. ✅

## Findings

### 1. ACCEPTANCE_GAP — `skills/compound-v/phase-0-recon.md:45` still orders a refresh before a search

```
- **If the output warns the index is behind** ("index is N new / M removed docs behind the repo")

  otherwise recent recon docs false-miss.
```

This is the exact instruction the feature exists to delete, and it is wrong twice over now. The
message it quotes no longer exists — the warning gained a `changed` field and is now
`N new / M changed / K removed`, so the condition never matches its own literal text. And the action
it prescribes is obsolete: a plain `search` has already refreshed by the time any output is read. The
one surviving path that *does* print that warning is the lock-held branch — where "run refresh first"
is the worst possible advice, since the lock that stopped the inline refresh will stop the explicit
one too, and `cmd_refresh` will simply print `refresh already running — skipped`.

This defeats manifest AC 4 and design-spec AC 4, both of which say "no doc". It also falsifies
pre-flight 1A §5's completeness claim — "grepped the whole repo for that exact phrase and variants —
it appears in exactly one prose file, matching the plan's Task B list". It appears in two. The audit
searched for the `v-remember.md` phrasing and missed the same instruction worded differently, and the
partition map inherited the gap: `phase-0-recon.md` is in **neither** job's `write_allowed`, so no
implementer could have fixed it and neither is at fault.

→ Delete the refresh-first clause from `phase-0-recon.md:45`; if a staleness note is still wanted
there, it should say that a plain `search` refreshes itself and that the warning now means the lock
was held. Needs a follow-up job — the file is outside both existing lanes.

### 2. INTEGRATION_MISMATCH — `skills/compound-v/memory.md:141` describes a mechanism the engine changed

```
- **Freshness by construction:** `search` checks (cheaply, one `git ls-files`) whether the FTS5
  index is behind the working tree …
```

The parenthetical is a survivor from the old text and is no longer true. `index_staleness` used to be
a path-set diff — one `git ls-files`, no file reads. It now SHA-256s **every tracked doc on every
search** (`:945-959`, `file_sha(os.path.join(root, f))` per file), because the spec's own decision
made staleness `new ∪ changed ∪ removed` and "changed" cannot be known without hashing. Measured on
this repo, 275 tracked docs:

| | mean | best of 5 |
|---|---|---|
| `index_staleness` today (hashes every file) | 0.091 s | 0.070 s |
| the old path-set-only form | 0.059 s | 0.047 s |

So ~32 ms marginal per search — genuinely cheap, and the doc's *conclusion* ("cheaply") survives. Its
*reason* does not, and the reason is the load-bearing part: a reader sizing this for a large corpus
will assume the check is O(1) in file content when it is O(total bytes of tracked prose). Pre-flight
1A §5 flagged precisely this cost as un-benchmarked; the number above is that benchmark, and it says
the design is fine and the sentence is wrong.

This is the parallel seam doing what parallel seams do: Task B was correctly forbidden from reading
Task A's worktree, so it preserved a phrase that Task A's change falsified. Neither job is at fault
individually; the composite is wrong.

→ Replace "cheaply, one `git ls-files`" with an accurate description — a `git ls-files` plus a content
hash of each tracked doc, ~0.09 s for this repo's 275 docs. `skills/compound-v/memory.md` **is** in the
`docs` job's lane, so this is a one-line fix in an existing partition.

### Low-severity, recorded not demanded

3. `cmd_search:980-988` releases the refresh lock outside a `try`/`finally`, unlike `cmd_refresh`.
   An exception in `refresh_fts5` leaks the fd; the process is dying anyway, so the OS drops the
   `flock`. Asymmetry, not a bug.
4. The inline path derives the tracked-file list and hashes the corpus twice — once in

5. The lock-held branch and the ordering hazard have no automated guard. I probed both by hand above;

   selftest lacks, and building them is the over-engineering the standing directive forbids. Flagged
