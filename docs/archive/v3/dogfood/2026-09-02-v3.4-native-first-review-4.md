### ISSUE 1 — QUALITY: the narrowed carve-out still hides a forged `.pyc`, and that `.pyc` executes as the lane guard's own matcher — demonstrated end to end

[`scripts/compound-v-scope-check.py:197-202`](../../../scripts/compound-v-scope-check.py) justifies
dropping bytecode with a safety claim:

```
# A .pyc is never merged (merge-back lands only approved paths), so dropping it
# here narrows nothing an attacker could use.
```

The first clause is true and I verified it. The second does not follow from it, because **a `.pyc`
does not have to merge in order to run.** Three facts, each checked here rather than assumed:

1. **Where it lands.** `hooks/lane-guard.sh:164-167` picks its interpreter with `command -v python3`.
   On this machine that resolves to `/opt/homebrew/bin/python3` → **3.14.7**, and
   `importlib.util.cache_from_source` for a repo script then returns
   `scripts/__pycache__/compound-v-scope-check.cpython-314.pyc` — **inside the repo**. (That is the
   same interpreter family that produced the real `cpython-314.pyc` the third pass found blocking a
   job.) Apple's `/usr/bin/python3` 3.9.6 redirects its cache outside the tree, so this is
   interpreter-dependent, not universal — the default one on PATH is the one that lands in-repo.
2. **Nothing reports it.** The gate drops it (`is_bytecode_noise` → `True` on the extension), and
   `.gitignore:60-61` keeps it out of `git status`. Before 3.4.0 the gate's third term reported that
   exact path as a violation and the job was BLOCKED. After 3.4.0 there is no signal at all.
3. **It executes, in-process, on the next tool call.**
   [`hooks/lane-guard.sh:551-556`](../../../hooks/lane-guard.sh) loads the matcher with
   `spec_from_file_location` + `exec_module` on `$CV_SCOPE_CHECK` —
   `scripts/compound-v-scope-check.py` — on **every** `Write`/`Edit`/`MultiEdit`/`NotebookEdit`/`Bash`
   call, in every session. `compound-v-integration-gate.py:635-645` loads the same module the same
   way, deliberately (*"The SAME matcher the scope gate uses — never a second one"*).

**Executed, not argued.** A forged **unchecked hash-based** `.pyc` (flags `0b01`: hash-based,
`check_source=0`, so CPython never validates it against the source) was planted beside a **copy** of
the real `compound-v-scope-check.py` in a temp directory, then loaded through lane-guard's own three
lines. Nothing in this repository was touched:

```
python                : 3.14.7
PYTHONDONTWRITEBYTECODE: 1 / -B on the command line
planted               : scripts/__pycache__/compound-v-scope-check.cpython-314.pyc
forged code executed  : True
is_allowed('/etc/passwd', ['docs/**']) -> True      # the real module returns False
```

The forged module ran and replaced `is_allowed` with a function that returns `True` for every path —
i.e. the lane guard's matcher now approves every out-of-lane write, and so does the integration
gate's. Note the second line: **`-B` and `PYTHONDONTWRITEBYTECODE=1` do not help.** They stop Python
*writing* a cache; they do not stop it *reading* one. The mitigation `.gitignore:59-61` and
`lane-guard.sh:159-162` both name is hygiene against this, and it is not.

**Honest bounding, so the finding is not oversold.** The pre-3.4.0 gate was *detection*, not
prevention — it ran after the write, and the forged `.pyc` could already have executed. `Write`/`Edit`
to that path is still denied by the lane guard. What 3.4.0 removed is the **only** signal that
remained for the Bash path the guard's own header says walks past it: a loud BLOCK naming the file,
in a tree where `git status` is silent by design. That is a real reduction in the authority of the
plugin's central control, taken to fix an ergonomic problem (`__pycache__` blocking honest jobs)
that had a documented alternative.

→ Do not leave the rationale comment standing as written; it is the load-bearing false statement. If
the extension exemption stays, replace `:201-202` with what is actually true — a `.pyc` never merges,
**but it is executed in place by `lane-guard.sh:551` and `integration-gate.py:641`, so this exemption
trades a detection for ergonomics** — and add the one control that closes it cheaply: have the gate
(or the guard) refuse to load a matcher whose `__pycache__` entry is a hash-based pyc with
`check_source=0`, or run the two loaders under a `sys.dont_write_bytecode` + `SourcelessFileLoader`-free
path that reads the source directly. Alternatively narrow the exemption to `.pyc` files whose
basename matches an existing sibling source (`x.cpython-NNN.pyc` ⇔ `../x.py`), which covers every
honest case in the r5 incident and none of this one.
