#### 1 — **HIGH · PASS 1** · `/v:init` recommends the value that turns the shorter system prompt **off**

`commands/v-init.md:711-714` tells the user:

> *"the harness ships a shorter system prompt that some users report reinforces that. If you want
> it, add `"CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT": "0"` …"*

The variable is real. Its meaning is the opposite. From the binary this release is pinned against
(`/Users/oleg/.local/share/claude/versions/2.1.238`, the same 2.1.238 the job's own manifest body
cites as source B), the resolver — offset **285 081 100** — reads verbatim:

```js
function UKb(e){ if(!e)return!1;
  if(Un(V.CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT))return!0;
  if(Sf(V.CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT))return!1;
  … }
class eep{ … leanPrompt=qd(UKb) }
```

and the two predicates, at offsets 279 354 756 / 279 354 898:

```js
function Un(e){ … return ["1","true","yes","on"].includes(t) }
function Sf(e){ … return ["0","false","no","off"].includes(t) }
```

So `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT="1"` forces the lean prompt **on**; `"0"` forces it **off**,
overriding whatever the default would have been. There is exactly one use site — I grepped the
binary; the other two hits are the env-name table and the export map.

The claim is repeated in two more places written by this same job:
`CHANGELOG.md:57` and the spec amendment (`…-native-first-design.md:169`).

This is not a measurement problem, and the honesty note does not cover it. The note says *"this
project has measured no before/after difference"* — correct and well said. But the **direction** of
an environment variable is not a thing you measure, it is a thing you read, the job's own stated
method was to read the binary, and this is the one claim in the job that was never checked against
it. As written, a user who accepts the offer gets the opposite of what the release's whole thesis
asks for.

→ Either flip the value to `"1"` and keep the community-claim framing, or drop the offer. Correct
`v-init.md`, `CHANGELOG.md` and the spec amendment together — three files now carry it.

#### 2 — **MEDIUM · PASS 2** · a job type containing `review`, `quality` or `integration` silently loses the role, the cap and the guidance

`scripts/compound-v-emit-workflow.py:573-587`, `agent_role_for`, falls through to `None` for any
type matching `REVIEWER_TOKENS = ("review", "reviewer", "spec_review", "quality", "integration")`
(`:787`). The docstring justifies it — a reviewer must not be told to write inside a lane — and for
`integration_review` that is right. The substring is the problem. Driven live:

```
bounded_crud         role=implementer   agentType=superpowers-v:implementer   note=None
review               role=spec-reviewer agentType=superpowers-v:spec-reviewer note=None
review_fix           role=None          agentType=None                        note=None
integration_slice    role=None          agentType=None                        note=None
quality_gate         role=None          agentType=None                        note=None
data_integration     role=None          agentType=None                        note=None
```

`review_fix` is not hypothetical. **This same commit** adds, in three files, the instruction that
the orchestrator mint a *"fix job minted from a review finding"* (`routing-policy.md:216`,
`execution-manifest.md:46`, `v-orchestrate.md:64`). A `review_fix` job is an implementer in every
respect — it writes code inside a lane — and it arrives with no role, no `maxTurns: 60`, no scope /
cadence / deliverables guidance, and, because `agent_type` is `None`, **no `agent_definition` for
the inline fallback to carry either**. It falls all the way back to the anonymous prompt this
release exists to replace.

And it is silent. `resolve_agent_type` returns `note=None` on that path, so nothing appears in the
plan entry and nothing reaches the log. Compare the fallback path, which the same commit
deliberately made loud (`:1617-1622`, *"its maxTurns cap of 60 is LOST on this path"*). The
degradation the author chose to announce is announced; this one is not.

The file already carries the precedent, in `_is_reviewer_job`'s own docstring: *"The looser
substring scan classified a job titled 'Writes the thing the reviewer reviews' as a reviewer."*
The same trap, one function over, now gated on the type instead of the title.

→ Either match reviewer types exactly (an explicit set) rather than by substring, or — at minimum —
return a `reason` from `resolve_agent_type` on this branch so a job that loses its role says so.

#### 4 — **LOW · PASS 2** · a malformed manifest `max_turns` is silently ignored — the exact shape the lint check was added for

`job_turn_cap` (`:900-907`) accepts the manifest value only when
`isinstance(declared, int) and not bool and > 0`; anything else falls through to the tier default
with no note. And `compound-v-validate-manifest.py` accepts any unknown per-job key — verified, not
assumed:

| manifest | validator |
|---|---|
| `max_turns: 12` | `valid` |
| no `max_turns` | `valid` |
| `frobnicate: 9` | `valid` |

So `max_turns: "60"` or a typo'd `max_turn: 60` produces a job silently running on the tier default.
That is precisely the reasoning the same commit used to justify the new frontmatter check —
*"a typo is silent: a string, a float or a negative is ignored by the runtime, so the agent runs
uncapped while its file says otherwise"* (`lint-frontmatter.py:161-163`) — applied on one side of
the same feature and not the other.

`execution-manifest.md:47` does state the validator's permissiveness honestly, so this is a
consistency gap rather than a false claim.

→ Have `job_turn_cap` emit a note when `max_turns` is present but unusable, the way
`resolve_job_model` degrades open loudly.
