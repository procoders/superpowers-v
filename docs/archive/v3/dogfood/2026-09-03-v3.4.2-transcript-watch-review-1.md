### The reproduced defects

Everything below was run on the merged tree; output is quoted verbatim.

**Issue 1 — `out-of-lane` fires on `2>/dev/null` and on every path outside the repository.**
`out_of_lane_targets` at `scripts/compound-v-transcript-watch.py:645-650`: when `_repo_relative`
returns `None` (the path is under no known root), the target is emitted anyway. `bash_write_targets`
extracts `/dev/null` from `2>/dev/null` — correctly, as a redirect target — and the caller then has
no way to say "not a repository path, therefore not a lane question." Against this run's own
transcripts that produced five out-of-lane signals across the two merged jobs, every one of them
`Bash /dev/null`, from commands as ordinary as
`ls -la <run-dir> && cat <run-dir>/manifest.yaml 2>/dev/null | head -100`
(agent `a4681541`, transcript line 12). The same code reported my own scratchpad writes — outside
the repo, outside any lane, and entirely legitimate — as out-of-lane.

This is not merely noisy. `commands/v-dispatch.md:180-185` now instructs the orchestrator to
`TaskStop` the workflow and re-orchestrate on an out-of-lane signal. As shipped, the first such
signal in every run is `/dev/null`.

**Issue 2 — `denied` is the generic substring match archaeology §7.2 forbade by name.**
`is_lane_denial` at `:686-687` is `bool(text) and DENY_LITERAL in text`. It fires on any tool result
that *contains* the literal, including every result that merely quotes it. I confirmed the match
offsets directly in the transcript: line 13 at offset 4752 (the manifest, quoting the job acceptance),
line 15 at 4681 (the design spec's amendment 2), line 17 at 3571 (the plan's Task A Step 2), line 24
at 3874 (the archaeology audit's §3), line 34 at 1661 (`hooks/lane-guard.sh`'s own source). Five
false denials, all from an agent *reading its own instructions*.

**Issue 2b, same root, different pattern set** — `error_evidence` fires the same way. `ERROR_PATTERNS`
includes `\bBLOCKED\b` and `Traceback (most recent`, and this repository's documentation is largely
*about* blocked jobs and tracebacks. Observed: `error PASS exit code 0 is not an error, exit code 1
is` — the watcher's own selftest output matching its own `exit code [1-9]` pattern — and
`error 3. **Render the run-level phase.** Show the phase (one of SPEC_READY → … → REV…`, which is
`commands/v-status.md` listing `BLOCKED` as a phase name.

**And the evidence line does not point at the match.** `:751` renders
`text.strip().splitlines()[0]` — the *first* line of the result, not the matching one. So the reader
sees `denied total 184` and `denied #!/usr/bin/env python3`, with no way to tell what fired.
Contrast `error_evidence:671-684`, which correctly walks back to the matching line's boundaries. The
two detectors disagree about their own contract; the `denied` one is wrong.

**Issue 3 — a tick boundary between a `register-lane` and its result unregisters the agent permanently.**
`tool_names` (`:701`) and `pending_register` (`:702`) are locals of `analyze_agent`, re-created every
call, while only `job`/`reg` survive in the state file. `tick` resumes each agent at
`start_line=rec["line"]` (`:833-838`). So when a poll lands between a tool_use and its tool_result,
the result arrives orphaned: the register-lane is never resolved, `job` stays `None`, and the agent
is `(unregistered)` for the rest of the run — after which *every in-lane write it makes is reported
out-of-lane*, and every Bash failure is missed, because `tool_names.get(use_id)` is `None` and the
`error` branch at `:754` never runs.

Reproduced on a synthetic fixture, same transcript read two ways:

```

watching wf_1 (1 agent transcripts) for r1

=== CONTROL: ONE pass over the SAME, now-complete transcript ===
watching wf_1 (1 agent transcripts) for r1
jobs: a=?  agents: 1 live, 0 returned
```

`src/ok.py` is squarely inside job `a`'s `write_allowed: ["src/**"]`. Read whole: silence, correctly.
Read across a boundary: a false out-of-lane against a phantom `(unregistered)` agent. This is the
`--every` mode — the mode `commands/v-dispatch.md:175` now prescribes — and the boundary is most
likely to fall exactly where it hurts most, because `register-lane` is the first command every job
runs and a long Bash step (a test suite) is precisely what a 120-second poll interrupts.

## Verdict

**ISSUES — 10.** Ranked by what blocks the run first. Nothing here is a scope violation, a fabricated
metric, or a reward hack; the run is honest work with a matcher that is too loose and a suite that
cannot see it.

1. **`out-of-lane` fires on `2>/dev/null` and on every non-repo path** — `scripts/compound-v-transcript-watch.py:645-650`.
   `_repo_relative` returning `None` means "not a repository path", and the code treats it as
   "outside the lane". Five false signals on this run, all `Bash /dev/null`; the scratchpad writes
   too. **Fails feature AC 2** and makes the one signal `v-dispatch.md:180` says justifies a
   `TaskStop` fire on the most common idiom in the repo.
   → A path with no repo-relative form is not a lane question. Skip it (or route it to a distinct,
   clearly-named signal); do not report it as out-of-lane.

2. **`denied` is the generic substring match archaeology §7.2 forbade by name** — `:686-687`.
   `DENY_LITERAL in text` fires on any result that *quotes* the literal: the manifest (line 13,
   offset 4752), the spec (line 15, 4681), the plan (line 17, 3571), the archaeology audit (line 24,
   3874), `hooks/lane-guard.sh`'s source (line 34, 1661). Twelve false denials across the run's three
   agents (five, five and two), every one of them from an agent reading its own instructions.
   **2b, same root:** `ERROR_PATTERNS:100-108` (`\bBLOCKED\b`,
   `exit code [1-9]`, `Traceback`) fires on this repo's documentation and on the watcher's own
   selftest output. **And `:751` renders `splitlines()[0]`** — the first line of the result, not the
   matching one — so the reader cannot tell what fired; `error_evidence:671-684` already does this
   correctly and is the model to copy.
   → Anchor the denial to the position it actually occupies (`is_error` on the result, or the literal
   at the start of a line, or the result of a tool call that was refused) rather than anywhere in the
   body; render the matching line as evidence in both detectors.

3. **A tick boundary between a `register-lane` and its result unregisters the agent permanently** —
   `:701-702`, `:735-752`, `:833-838`. `tool_names` and `pending_register` are per-call locals while
   `start_line` advances across ticks, so an exchange split across a poll orphans the result: `job`
   stays `None`, the agent is `(unregistered)` for the rest of the run, every in-lane write it makes
   is reported out-of-lane, and every Bash failure is silently missed. Reproduced above: the same
   transcript yields **0** signals read whole and a **false out-of-lane on an in-lane write** read
   across a boundary. This is the `--every 120` mode `v-dispatch.md:175` prescribes.
   → Persist the pending tool_use table (id → name, and the parsed register-lane) in the state file
   alongside `line`/`job`/`reg`, or hold back the last incomplete exchange until its result lands.

4. **Traceback and exit 1 on a documented advisory path** — `:454` via `:211`. `repo_root_for`
   returns `None` outside a git checkout; `_real(None)` raises `TypeError`, which `:209-213` does not
   catch, and the `or repo_root or ""` guard written for this case never executes. Contradicts spec
   Decision 1, **feature AC 3**, library-audit MUST(1), and the module's own docstring at `:17-21`.
   `--transcripts` masks it; default discovery does not.
   → Catch `TypeError` in `_real`, or guard `session_roots` on a falsy `repo_root` before the call.

5. **Archaeology §7.8 unmet — `/v:status --live <run-id>` does not resolve, and carries no degrade
   contract** — `commands/v-status.md:7`, `:12`, and the new section at `:109`. The file states
   `{{args}}` is the run-id and step 1 builds `docs/superpowers/execution/{{args}}/`; with
   `--live <run-id>` that is `docs/superpowers/execution/--live <run-id>/`. The audit required
   explicit parsing prose for exactly this, **and** the same "if the probe errors or is missing,
   show `—`/skip — never break the render" contract every other optional section in the file carries
   (Liveness at `:39`, Epic progress at `:80`). Neither was written.
   → Amend step 1 to strip a leading `--live`, and give the section the file's standard degrade line.

6. **The suite cannot catch 1–4** — `tests/test-transcript-watch.sh`. Every invocation passes
   `--transcripts` (`:220`, `:257`, `:266`, `:275`, `:283`, `:308`, `:339`), so `session_roots` — the
   default discovery path, where issue 4 lives — runs in **no test in this repository**. No fixture
   contains a `2>/dev/null`, a result that merely quotes the denial literal or `BLOCKED`, or a tick
   boundary (the dedup case at `:257` re-reads a complete transcript). The `"EXACTLY six signals"`
   assertion at `:245` is the right instinct aimed at a fixture where nothing can go wrong.
   → One fixture per false-positive class, one test that exercises discovery via `CLAUDE_CONFIG_DIR`
   rather than `--transcripts`, and one that appends to a transcript between two `--once` calls.

7. **AC 2's "names every agent of the run with its job" is not met** — 8 agent transcripts in
   `wf_b544c252-dc8`, 3 named in the output. Only signal-emitting agents appear; the summary gives
   counts, not a roster. Spec §Decisions 4 never promised one, so spec and AC disagree — but the AC
   is the run-level gate.
   → Either add a one-line-per-agent roster to the summary, or amend the criterion to say what the
   spec actually contracts. Do not leave the two disagreeing.

8. **Archaeology §7.7 overridden without answer** — `commands/v-dispatch.md:171` appends the watch
   guidance to step 6's prose; the audit required it be its own step, on the grounds that step 6
   ("Launch it by `scriptPath` — this form is mandatory") is narrowly scoped and already
   load-bearing. **Not the implementer's fault** — the manifest's own acceptance for `docs-release`
   instructed "step 6 documents the background watch", so the job did exactly what it was told. The
   defect is upstream: an audit MUST was dropped during orchestration without its reasoning being
   addressed.
   → Either promote it to its own step, or record why the audit was overruled.

9. **`watch-script` ran `impacted` under a manifest declaring `triage.tier: FULL`** —
   `results/watch-script.json` (`tests.scope: "impacted"`, `selected_count: 3`); `full_command` never
   ran for that job, and `docs-release` reached the full suite only by an unmapped `CHANGELOG.md`.
   The receipt names the rule: the default consulted `impacted_map` and never consulted
   `triage.tier`. **Not `BUILD_RED`** — I ran `full_command` on the merged tree myself and it printed
   `all-tests-ok` — but the next FULL run will under-test the same way, silently.
   → Make the resolver's default honour `triage.tier: FULL`, or require an explicit per-job
   `test_scope` when a manifest declares FULL.

10. **Minor dead code** — `save_state:804-805` is `if exc.errno not in (…): pass`, a no-op in both
    branches (and the sole reason for the `errno` import at `:79`); `tick:820` takes an unused
    `run_dir` parameter.

### What is right, and worth keeping intact through the fixes

The architecture is correct and several of its decisions were hard-won. One matcher and one YAML
loader, both imported by path from the repo's own — proven by grep *and* by behaviour, with no second
implementation to drift. Job resolution off the agent's own `register-lane --job-id`, never off
`lane-map.json`'s cwd map, which is the finding-68 shape the archaeology caught mid-audit. The
succeeded-call rule, tested. All four `message.content` shapes handled, including `attachment` lines
with no `message` key. Read-only proven twice over, by `git status` and by a run-directory file-list
diff. Discovery genuinely works with no `--wf` and no new state field. And a real lane-guard denial
was caught end-to-end, closing archaeology §7.9's open verification item with live evidence.

Fix the matchers, persist the pending-exchange table, guard the null repo root, and give the suite
fixtures drawn from real traffic rather than from the happy path. The bones are good.
