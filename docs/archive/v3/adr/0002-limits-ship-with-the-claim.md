# 0002. Any published number about Compound V ships with its limits in the same document

- **Status:** Accepted
- **Date:** 2026-07-25
- **Deciders:** Compound V v2.17 design (co-change advisory + evidence packing)

## Context

Compound V's entire value proposition is that it *verifies* rather than *asserts*. The scope gate is
git-derived, not model-self-reported ([`scripts/compound-v-scope-check.py`](../../../scripts/compound-v-scope-check.py));
CI actively greps `scripts/` and `docs/` for invented cost and token figures
([`.github/workflows/validate.yml:160`](../../../.github/workflows/validate.yml), the "No fabricated
cost/token metrics (anti-ruflo gate)" step). A project built on that stance cannot publish numbers the
way a marketing page does.

But the anti-ruflo gate only catches *fabricated* numbers. It cannot catch the more common and more
insidious failure: a number that is **entirely real** and still misleads, because the reader has no way
to see what it was measured on.

v2.17's own co-change work is the worked example. The feature mines ordered rules like
`plugin.json → CHANGELOG.md` at rate 0.92 with a 95% Wilson lower bound of 0.78. Every one of those
digits is real. And every one of them is also:

- measured on **one repository**, whose commit shape set the `--narrow-max-files 10` bar
  ([spec `:91`](../specs/2026-07-25-v2.17-cochange-and-evidence-packing-design.md), "Declared
  portability limit"), so a young repo, a squash-merge-only history, or a wide monorepo will
  legitimately produce *no* rules at all;
- a **correlation**, not a causal or contractual claim — the pair moves together historically, which
  is not the same as "must move together";
- inflated by **release commits** if you read the headline support in isolation — which is exactly why
  the tool reports `release_commits` and `bulk_commits` alongside `support`.

The same shape recurs across the project's history. Three earlier drafts of the v2.17 spec each carried
a true-sounding number whose limits were missing, and each was corrected only because a cross-model
reviewer went looking: r2's headline `AGENTS.md ↔ GEMINI.md` pair turned out to be an artifact of wide
doc sweeps and does not clear the bar at all; r2 also called ten unilateral file touches "violations"
when they were unadjudicated historical signals. Nothing in either case was invented. The measurement
was real and the framing was wrong.

The forcing question that produced this ADR: *what stops the next honest number from being the next
misleading one?* Reviewer vigilance had been the only answer, and reviewer vigilance is not a mechanism.

## Decision

**Any published number about Compound V — in a spec, an ADR, a CHANGELOG entry, the README, a run
report, or agent output — ships with a "What this does not show" note in the same document, next to
the claim.**

"Published" means it leaves the author's head and enters a committed artifact. "In the same document"
is the load-bearing half: a limit that lives in a different file, a footnote, or a follow-up commit is
a limit the reader will not have when they act on the number.

A "What this does not show" note answers, at minimum:

1. **What was it measured on?** Which repo, which window, which commit count, which HEAD.
2. **What would change it?** The population, threshold, or configuration the number is contingent on.
3. **What does it explicitly *not* license?** The inference a reader might reasonably but wrongly draw.

Alternatives weighed and declined:

- **Put the rule in [`CONVENTIONS.md`](../../../CONVENTIONS.md).** This was the original v2.17 plan
  (r1) and it is *wrong*, verifiably. That file opens with a generated-file header at lines 1-6
  (`generated by /v:onboard from cited evidence on 2026-06-30; refresh with /v:onboard --refresh`) and
  is rewritten wholesale by `/v:onboard --refresh`. A hand-written rule placed there would be silently
  erased on the next refresh, with no conflict and no warning — the worst failure mode available, since
  the team would believe the rule was in force. Declined for that reason alone; the file is a generated
  *derivation* of the repo, not a place to author policy.
- **A CI grep that fails a build on an unaccompanied number.** Declined: not mechanizable without
  large false-positive damage. A regex cannot distinguish a claim ("0.92 of commits") from a version
  string, a line reference, a threshold constant, or a config default — and the repo is dense with all
  four. The existing anti-ruflo gate works precisely because it targets a *narrow*, unambiguous phrase
  set; widening it to "any number" would fail on nearly every file and get disabled within a week. The
  right lesson from v2.14.1 — where a silently-dead link guard and 25 never-run selftests were found —
  is that a guard nobody trusts is worse than no guard.
- **Rely on cross-model review to catch it each time.** Declined: this is the status quo, and it is
  what produced the three corrections described above. It works, but only reactively, only when a
  reviewer is run, and only at the cost of a full extra round each time. A written rule lets the author
  get it right the first time; review then verifies rather than discovers.
- **A separate "limitations" document that all claims link to.** Declined: it defeats the purpose. The
  reader who acts on a number is the reader who did not follow the link. Co-location is the mechanism.
- **Publish no numbers at all.** Declined as an over-correction. The measurements are genuinely
  useful — the co-change rules are the reason a partition reviewer can spot a forgotten partner at all.
  The problem was never the numbers; it was numbers arriving without their context.

## Consequences

- **Every claim carries its own falsifier.** A reader can tell, without leaving the page, whether a
  number applies to their situation. This is the point.
- **The rule is self-applied and enforced by review, not by CI.** Honestly stated: this ADR creates no
  hard gate. It is a convention that a human or a cross-model reviewer checks. That is a real weakness,
  accepted deliberately over a grep that would be either useless or unbearable. If a mechanical check
  ever becomes feasible for a narrow class of claim, it can be added without amending this decision.
- **Our marketing sounds weaker, and takes longer to write (the real cost).** "Fires on six ordered
  rules with a 0.78+ Wilson lower bound" is a stronger sentence than the same clause followed by "on
  one repository, over 380 commits, with a bar calibrated to this repo's commit width, and a young or
  squash-merged repo will legitimately produce nothing." The second is what we will write. Every
  published figure now costs an extra paragraph of thinking about what it does not establish, and the
  result reads more cautiously than a competitor's equivalent claim. We accept a weaker-sounding,
  slower-to-produce claim over a stronger one a reader could be burned by — but the cost is not
  hypothetical and should not be described as free.
- **Existing artifacts are not retroactively rewritten.** The rule applies going forward. Sweeping the
  back catalogue would be a large, low-value edit; the numbers already published are mostly inside
  specs that carry their own correction history.
- **It gives the ADR corpus a second entry, which matters more than it looks.** ADR relations
  (`supersedes` / `refines` / `conflicts_with`) and staleness scoring were explicitly rejected for
  v2.17 on the grounds that the corpus held exactly one node
  ([spec, "Rejected candidates"](../specs/2026-07-25-v2.17-cochange-and-evidence-packing-design.md)).
  Two nodes does not change that verdict — the revisit bar remains ~10 — but it is the first step
  toward the corpus size at which the question is worth reopening.
- **It becomes recallable only once committed.** Per
  [ADR 0001](0001-fts5-not-vector-db.md), V-memory indexes git-tracked files, so this rule is
  invisible to `/v:remember` until it is committed. Write-then-commit, as always.

### What this does not show

This ADR is a decision about how we write, and it is applied to itself: the reasoning above cites
one repository's history and this project's own review record. It does not establish that the rule
improves reader outcomes — no such measurement was taken, and none is planned. It does not claim the
three corrections described in Context would have been prevented by the rule; they were caught by
cross-model review, and the counterfactual is unknown. It offers no evidence about how the convention
holds up under deadline pressure, which is the condition where a review-enforced rule is most likely
to be skipped.
